# Market positioning landscape: "Airflow / CI for AI agents", agent control planes, and scheduled code-maintenance pipelines (as of October 2026)

Scope note: findings below separate (a) what vendors *claim* from (b) what their docs/announcements *verify*. Dates are given where found. "Secondary" marks aggregator/blog coverage that could not be checked against a primary source. All Russian-language sources are summarized in English.

## Key Question 1: Who, if anyone, already owns the phrase "Airflow for agents" (or "CI for agents" / "Kubernetes for agents") and what do they actually offer vs the claim?

### Takeaway
Nobody owns "Airflow for agents" as a brand; the phrase is occupied *literally* by Apache Airflow itself (official `common-ai` provider + Astronomer's `@task.agent` tutorials), while "Kubernetes for agents" is attached by press to Steve Yegge's Gas Town, and "CI for agents" is being absorbed by GitHub Agentic Workflows / Cursor Automations / Claude Code Routines as "agents running inside CI". The Prefect–Dagster merger (July 2026) is the loudest explicit bet that the *data-orchestrator* category is pivoting to agents. None of these ship a DAG whose nodes are full coding-agent sessions with typed artifacts, approvals and pluggable agent runtimes.

### Cited Findings

**Apache Airflow / Astronomer (the literal "Airflow for agents")**
- Apache Airflow released `apache-airflow-providers-common-ai` 0.1.0, adding LLM and agent operators built on Pydantic AI with 20+ model providers; its `HookToolset` lets agents call existing Airflow connections directly instead of standing up separate MCP servers — [Apache Airflow blog](https://airflow.apache.org/blog/common-ai-provider/)
- Astronomer's earlier `airflow-ai-sdk` (the `@task.agent` decorator) is being phased out in favor of the official provider — [GitHub astronomer/airflow-ai-sdk](https://github.com/astronomer/airflow-ai-sdk)
- Astronomer defines "agent orchestration" as a model-and-tool-calling loop that runs *as a single Airflow task*, where "neither the number of model calls nor the sequence of actions is known before the task runs" — [Astronomer docs](https://www.astronomer.io/docs/learn/ai-orchestration-agent)
- Airflow 3.1 added human-in-the-loop operators that pause a DAG until a decision is approved and resume along different paths — [Medium, Sebastian W.](https://medium.com/@sebastianwtr/orchestrating-agentic-ai-with-airflow-3-1-bringing-human-in-the-loop-to-enterprise-workflows-86b4400fa52e) (secondary)
- Red Hat is cited by Astronomer as running "AI agents at scale" on Airflow/Astro — [Astronomer blog](https://www.astronomer.io/blog/airflow-in-action-red-hat/) (vendor-framed)

- What this verifies vs the claim: Airflow's agent story is "an LLM/agent loop as one task inside a data DAG", with Airflow connections as tools. It does not model a *coding-agent session in a sandboxed repo* as the unit of work, has no git/PR semantics, and the HITL operator is a generic approval pause, not a code-review gate.

### Inferences
- The phrase "Airflow for agents" is effectively *unclaimed as a product brand*: Airflow itself occupies it with "agent-as-a-task", and Prefect/Dagster are positioning for the category but have shipped only a merger narrative. A product that owns "the DAG whose nodes are coding-agent sessions" would face no direct incumbent on the phrase, but would compete for mindshare with Airflow's own AI provider.
- The market has split into three layers that do not meet: (1) data/durable orchestrators (Airflow, Prefect/Dagster, Kestra, Temporal, Inngest) with DAGs/retries/HITL but no agent-session or repo semantics; (2) model-vendor managed runtimes (Managed Agents, AgentCore, Agent Engine, Foundry) with single sessions and sandboxes but no cross-session DAG; (3) ~260 coding-agent "run many sessions" tools, mostly kanban/worktree/tmux, where DAG + typed artifacts + approvals appears only in small projects (Bernstein, Archon, Crewplane, tutti, Open Multi-Agent, kandev). The exact gap named in the brief ("DAG of full coding-agent sessions with approvals, retries, typed artifacts, pluggable runtimes") is addressed only by small solo-maintained OSS.
- Pluggable runtimes are becoming table stakes in layer (3) (Bernstein 49 adapters, Emdash 34, Paperclip ~10, gh-aw 5+), so vendor lock-in to one agent is a weakness mainly of the vendor-native schedulers (Routines, Cursor Automations, Jules, Codex, Devin, Factory).

## Key Question 2: What are the 5–8 most cited pain points of productionizing coding-agent sessions in 2025–2026, with sources?

### Takeaway
The dominant, best-measured pain point is the human review/validation bottleneck (Harvard/Jellyfish: +30% LOC, flat shipped output, +49% PR merge time; Faros: review time up sharply; Opsera/LinearB: AI PRs wait 4.6x longer). Behind it: cost opacity and token blow-ups from many short sessions; non-determinism/flaky validation poisoning agent loops; lack of structured approvals and scoping (architectural drift across parallel worktrees); weak observability of what a run actually did ("green" ≠ task succeeded); and environment/isolation friction (ports, DBs, worktree setup). The framing consensus (Anthropic, 12-factor, Thoughtworks, Dropbox, Bernstein) is "deterministic control flow + agent steps + mechanical verification gates".

### Cited Findings

**1. Review / validation is the throughput ceiling**
- Harvard job-market paper "Artificial Intelligence in the Firm: Bottlenecks in Software Production" (Chen & Stratton, version dated August 4, 2026), using ~300M Jellyfish work events from 725,938 workers at 718 firms (Jan 2021–Mar 2026): after adopting Claude Code/Cursor/Devin-class tools, LOC per worker +~30% (~1,500 extra lines/month), commits +20%, PRs +23%, but Jira resolution and completed epics did not rise significantly; PR submit-to-merge time +49%, revision requests nearly doubled, comments per PR +35% — [AI Weekly summary](https://aiweekly.co/alerts/harvard-study-ai-coding-agents-lift-code-30-shipped-output-flat), [Borncity](https://borncity.com/news/harvard-studie-zu-ki-agenten-pull-requests-brauchen-49-prozent-laenger/) (secondary; paper not opened)
- Faros AI "Acceleration Whiplash" 2026 report (secondary summary): median PR review time +441.5% under high AI adoption, bugs per developer +54%, incidents per PR +242.7%, alongside tasks per developer +33.7% and PR merge rate +16.2% — [Vibe Graveyard](https://vibegraveyard.ai/story/faros-ai-acceleration-whiplash-study/); conflicting figure of +91% review time appears on Faros's own pages per search — treat 441% as unverified
- Opsera 2026 AI Coding Impact Benchmark: AI-generated PRs wait 4.6x longer for review while time-to-PR accelerates 48–58% — [TechEdge AI](https://techedgeai.com/opsera-report-reveals-ai-coding-boosts-speed-but-raises-security-and-governance-risks/) (secondary); LinearB publishes a near-identical "4.6x longer wait, reviewed 2x faster once picked up" — [LinearB](https://linearb.io/state-of-software-delivery-2025/)
- Simon Willison (Oct 5, 2025): "the natural bottleneck on all of this is how fast I can review the results"; he can only review and land one significant change at a time; parallel agents suit research/PoCs, code understanding, small maintenance (deprecation warnings), carefully specified work, and "scouting" — [simonwillison.net](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)
- HN threads on parallel agents: review is "hands down the biggest bottleneck"; "the real issue isn't human review per se, it's unstructured review" (narrow scope, invariant tests, small diffs); reviewing AI code "can bias you" — [HN: Embracing the parallel coding agent lifestyle](https://news.ycombinator.com/item?id=45489884), [HN: Conductor](https://news.ycombinator.com/item?id=44594584), [HN comment](https://news.ycombinator.com/item?id=47220440)
- "You are the queue": each switch between agents' outputs has a resumption cost; pressure leads to merging diffs without reading — [DEV, Gabriel Anhaia](https://dev.to/gabrielanhaia/five-parallel-coding-agents-wont-make-you-5x-faster-you-are-the-queue-4peo)
- Staging/validation queue grows non-linearly with PR volume even for correct code — [Bunnyshell](https://www.bunnyshell.com/blog/ai-writes-code-in-minutes-your-team-waits-days-for-staging/) (vendor)

**2. Cost opacity and blow-ups**
- Cost spikes come from many short sessions each reloading full context without cache hits; on Anthropic Enterprise there is no cost API, spend lives only in the admin dashboard; compaction and retry loops are invisible without tooling — [Product Hunt: Claudoscope](https://www.producthunt.com/p/claudoscope/claudoscope), [Hackernoon: Argus](https://hackernoon.com/this-free-vs-code-extension-shows-where-your-claude-code-tokens-are-going), [Tribe.ai OTel guide](https://www.tribe.ai/applied-ai/a-quickstart-to-measuring-the-return-on-your-claude-code-investment)
- LangWatch founder: "subscriptions hide the number, and local trackers only see one machine" — [hunted.space/langwatch](https://www.hunted.space/product/langwatch)
- Durable engines (Temporal/Inngest) meter on units that multiply inside agent loops — [WeTheFlywheel](https://wetheflywheel.com/en/comparisons/temporal-vs-inngest/) (secondary)
- Scale datapoint: Bun's Zig→Rust port consumed ~5.9B uncached input tokens and 690M output tokens (~$165k at API pricing) — [claude.com blog](https://claude.com/blog/ai-code-migration)
- Budget primitives are appearing as a response: gh-aw per-run/per-day AI-credit caps — [gh-aw](https://github.github.com/gh-aw/); Paperclip budgets with hard stops (lagging enforcement) — [Paperclip](https://github.com/paperclipai/paperclip); Ellipsis "hard spend caps" — [Ellipsis](https://www-origin.ellipsis.dev/blog)

**3. Non-determinism and flaky verification poisoning loops**
- "Flaky Tests Poison Agent Loops Faster Than They Ever Hurt Humans" — [tianpan.co](https://tianpan.co/blog/2026/07/02/flaky-tests-poison-agent-loops)
- Google's migration paper: hallucinations (reformatting, comment-only edits, irrelevant changes); pre-existing test failures blocked promotion of otherwise-good LLM changes; golden-file tests unsupported; developers "couldn't predict how many retries to try before switching to manual work" — [arXiv 2504.09691 HTML](https://arxiv.org/html/2504.09691v1)
- Dropbox Nova lesson: letting agents manage test execution "could leave sessions waiting for hours or validate against the wrong tests"; triggering CI deterministically and bringing the agent back on failure worked better — [Dropbox Tech](https://dropbox.tech/machine-learning/introducing-nova-our-internal-platform-for-coding-agents)
- Risk of agents overfitting to the test suite without parity checks — [Augment Code migration guide](https://www.augmentcode.com/guides/ai-code-migration) (vendor)
- Thoughtworks Radar vol. 34 (April 2026) theme "putting coding agents on a leash" and "feedback sensors for coding agents": deterministic quality gates (compilers, linters, type checkers, test suites, mutation testing like cargo-mutants, fuzzers) wired into agent workflows so failures auto-correct before human review — [Thoughtworks podcast on Radar 34](https://www.thoughtworks.com/insights/podcasts/technology-podcasts/themes-technology-radar-34), [Radar](https://www.thoughtworks.com/en-gb/radar)

**4. Missing approvals / scoping / coordination across parallel sessions**
- Worktrees solve file collisions but not "architectural drift" (two agents renaming the same type differently); fixes proposed: shared decision log or an orchestrator assigning non-overlapping scope — [HN](https://news.ycombinator.com/item?id=45489884)

**5. Observability: "green" does not mean success**
- Claude Code Routines: "A green status in the run list means the session started and exited without an infrastructure error. It does not mean the task in your prompt succeeded." — [Claude Code docs](https://code.claude.com/docs/en/routines)

- Uber's talk lists an "AI assistant" and MCP gateway with >40% fleetwide token reduction as platform-level observability/cost work — [AI Engineer talk](https://ai.engineer/talks/agentic-sdlc-at-uber-building-blocks-for-uber-s-software-factory)

- Worktrees lack untracked files (`.env.development.local`); port conflicts, shared DBs/migrations; one team reverted to one agent at a time after test-data isolation blocked them — [HN](https://news.ycombinator.com/item?id=45489884)

- Routines wrap API-fire text in a `<routine-fire-payload>` block labeled untrusted — [Claude Code docs](https://code.claude.com/docs/en/routines)

**The "determinism layer + agentic layer" framing**
- Anthropic "Building effective agents" (Dec 19, 2024): workflows = LLMs/tools "orchestrated through predefined code paths"; agents = LLMs choose their own process; patterns: prompt chaining (with programmatic checks between steps), routing, parallelization (sectioning/voting), orchestrator-workers, evaluator-optimizer; use workflows for predictability, agents for open-ended problems; agents "cost more in latency and money and can compound errors" — [Anthropic](https://www.anthropic.com/research/building-effective-agents)
- 12-Factor Agents (HumanLayer; Apache-2.0 code, 26.7k stars): factors include "Own your control flow", "Launch/Pause/Resume with simple APIs", "Contact humans with tool calls", "Small, Focused Agents", "Make your agent a stateless reducer", "Trigger from anywhere"; author argues most "agents" are mostly deterministic code with LLM steps at key points — [GitHub humanlayer/12-factor-agents](https://github.com/humanlayer/12-factor-agents)
- LangChain "Introducing ambient agents" (Jan 14, 2025): agents that respond to ambient signals and ask for input only when needed; "ambient does not mean fully autonomous"; interaction patterns: approve, edit, answer question, review — [LangChain blog](https://www.langchain.com/blog/introducing-ambient-agents)
- OpenAI "A practical guide to building agents" (PDF, April 2025): when to use a deterministic workflow vs an agent, manager vs handoff multi-agent patterns, layered guardrails with HITL — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Stripe Minions run "blueprints" — code-defined workflows mixing deterministic routines with flexible agent loops — [InfoQ](https://infoq.com/news/2026/03/stripe-autonomous-coding-agents/)
- Anthropic migrations: "Make reviews adversarial and verification mechanical"; deterministic scripts for dependency mapping and queue management; "output file exists" = done; compilers/test runners as referees — [claude.com blog](https://claude.com/blog/ai-code-migration)
- Bernstein's design: "no model in the coordination loop" — [awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators)

### Inferences
- The two best-measured pain points (review bottleneck, cost opacity) are both *aggregation* problems across many sessions, which is exactly what a session-level product (Routines, Cursor Automations) cannot see and a DAG-level product with per-node budgets and batched review could.
- The industry has converged on a recipe (deterministic outer loop, agent inner steps, mechanical gates, adversarial review, resumable queues) but it is being re-implemented bespoke per company (Google, Airbnb, Anthropic, Dropbox, Stripe, Uber) — a signal of latent demand for a reusable orchestration layer.

### Gaps
- Primary Harvard paper, Faros report and Opsera report were not opened; figures are from secondary coverage and conflict (441% vs 91%).
- No dedicated HN thread specifically on *cost blow-ups* from orchestrating many sessions was found; cost evidence is mostly from tool-launch pages.
- No survey (e.g., Stack Overflow/DORA 2026) numbers on coding-agent orchestration pain were retrieved.

## Key Question 4: What do published case studies of agent-driven code migrations/optimizations say about structure (parallel hypotheses, validation gates, human review ratios, success rates, cost)?

### Takeaway
Across Google, Airbnb, Anthropic/Bun, Dropbox, Stripe, Uber and Sourcegraph the structure is strikingly uniform: deterministic targeting/queueing → per-unit agent attempt with a bounded retry loop → cheap-to-expensive mechanical gates (parse → build → tests/CI, sometimes 100+ runs) → batched human review → slow manual rollout. Reported automation rates: Google 74% of changes LLM-generated but only 36% untouched by humans; Airbnb 75% of files in 4 hours, 97% after tuning, 3% manual; Bun 1M lines in <2 weeks for ~$165k with 19 post-merge regressions; Stripe 1,300 PRs/week all human-reviewed; Uber >70% of PRs agent-attributed. Parallel-hypothesis generation appears mainly in Anthropic's write-up (adversarial reviewers, fan-out batches) and Google's "3 attempts, pick one".

### Cited Findings

**Google — "Migrating Code At Scale With LLMs At Google" (FSE 2025)**
- 39 migrations by three developers over 12 months; 595 code changes with 93,574 edits; 74.45% of changes and 69.46% of edits LLM-generated; developers estimated ~50% time reduction vs manual — [arXiv abstract](https://arxiv.org/abs/2504.09691)
- Pipeline: (1) Kythe-based location discovery following references up to distance 5 (conservative superset); (2) categorization into not-migrated / irrelevant (regex, 100% confidence) / relevant (to LLM) / left-over (to developers via config, applied on next nightly run); (3) edit generation by internal Gemini fine-tuned on internal code (DIDACT), temperature 0.0, three attempts per file with one success picked at random, diffs applied fuzzily; (4) validation cheapest-first: Success → Whitespace → AST parse-and-differs → "Punt" (ask LLM if change needed) → Build → Tests; failures marked for manual; (5) nightly runs, passing changes grouped, visually reviewed, code owners accept via Critique — [arXiv HTML](https://arxiv.org/html/2504.09691v1)
- Human involvement: LLM-only 214 changes (35.97%), LLM-then-human 229 (38.48%), human-only 152 (25.55%); human edits = 30.54% of all edits — [arXiv HTML](https://arxiv.org/html/2504.09691v1)
- Lessons: context-window overflow on big files; hallucinated reformatting; Dart weaker than Java/C++/Python; pre-existing test failures blocked promotion; golden-file tests unsupported; the two largest IDs rolled out slowly with no automation support — [arXiv HTML](https://arxiv.org/html/2504.09691v1)
- Earlier migrations included JUnit3→JUnit4 and Joda→java.time; the prior manual 32→64-bit migration took two years — [The Register](https://www.theregister.com/2025/01/16/google_ai_code_migration/)

**Airbnb — Enzyme → React Testing Library (March 2025)**
- ~3,500 test files; estimated 1.5 years manual, completed in 6 weeks; each file an independent unit in a step-based state machine (Enzyme→RTL refactor → Jest fixes → lint → TypeScript → final approval), advancing only on step success, enabling concurrency across hundreds of files — [InfoQ](https://www.infoq.com/news/2025/03/airbnb-llm-test-migration/)
- Retry loop: on validation failure the LLM is re-prompted with all errors, up to 10 iterations; this migrated 75% of files in four hours, leaving ~900 long-tail files; "retrying beat better prompting" ("brute force"); prompts grew to 40k–100k tokens with up to 50 related files and few-shot examples; "sample, tune, sweep" raised completion from 75% to 97%; remaining 3% done manually from LLM output — [InfoQ](https://www.infoq.com/news/2025/03/airbnb-llm-test-migration/), [ZenML summary](https://www.zenml.io/llmops-database/large-scale-test-framework-migration-using-llms); primary post: [Airbnb Tech](https://airbnb.tech/?p=366) (Medium copy returned 403)

**Anthropic — "How Anthropic runs large-scale code migrations with Claude Code" (July 16, 2026)**
- Bun Zig→Rust (~1M lines, 1,448 files) in under two weeks with 100% of existing test suite passing in CI before merge; 19 post-merge regressions all fixed; ~5.9B uncached input + 690M output tokens (~$165,000 at API pricing); ~4% of Rust in `unsafe`; memory on a 2,000-build benchmark 6,745 MB → 609 MB — [claude.com blog](https://claude.com/blog/ai-code-migration)
- Python CLI → ~165k lines TypeScript over a weekend, ~27M tokens; compile 8 min/platform → ~2 s; 12 Sonnet subagents — [claude.com blog](https://claude.com/blog/ai-code-migration)
- Structure: prerequisite "judge" (tests rewritten to run against both codebases, checked against deliberately broken code; 7-scenario parity harness); six steps: rulebook + dependency map + gap inventory (rulebook reviewed by 8 subagents) → stress test on 3 files with 3 agent roles, output discarded → translate in fan-out batches with two adversarial reviewers + a third tie-breaker, unresolved items flagged `// TODO(port)` → compile with orchestrator + fixer agents → smoke test with crashes grouped by root cause → behavior match with a single build daemon batching fixer patches; the end-to-end run was executed three times discarding output; Claude built its own e2e suite that ran autonomously four nights — [claude.com blog](https://claude.com/blog/ai-code-migration)
- Tooling/lessons: Claude Fable 5 / Opus 4.8 for planning, delegation and review, smaller models for implementation; deterministic scripts for dependency mapping and queue management ("output file exists" = done); cargo kept out of the loop for speed; "front-load human effort on the rulebook and stress test; the rest is mostly queues"; "fix the process that produced the bugs, not individual failures" — [claude.com blog](https://claude.com/blog/ai-code-migration)

**Dropbox — Nova internal coding-agent platform (May 21, 2026)**
- Isolated sandbox per session at a specific commit; caller supplies task + optional validation commands; failed validation is fed back up to a max iteration count; web UI + CLI/API for parallel jobs from scripts/services; "async workflow" helpers; each session limited to a single branch so publication is deterministic — [Dropbox Tech](https://dropbox.tech/machine-learning/introducing-nova-our-internal-platform-for-coding-agents)

### Inferences
- The recurring structural template — deterministic targeting, bounded retries per unit, cheapest-first mechanical gates, batched human review, slow manual rollout — maps directly onto a DAG with typed artifacts (target list → candidate diff → validation report → approved changeset → rollout record). Every case study built it ad hoc.
- "Parallel hypotheses + pick best" is rare in published pipelines (Google: 3 attempts pick one; Anthropic: adversarial reviewers + tiebreaker; Dropbox: multi-agent review experiment). Benchmark-driven selection (e.g., query-optimization with measured latency) is not described in any retrieved case study — a possible white space.
- Human-review ratios remain high even in the most automated pipelines (Google 64% of changes touched by humans; Stripe 100% reviewed), so review batching/triage is the main lever, consistent with Question 2.

### Gaps
