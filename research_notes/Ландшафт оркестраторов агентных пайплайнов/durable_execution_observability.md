# Durable-execution engines and observability/cost tooling for LLM-agent workflows (as of 2026-10-14)

Scope note: notes compiled from primary vendor docs (Temporal, Inngest, Restate, DBOS, Hatchet, Trigger.dev, Cloudflare, AWS), the OpenTelemetry GenAI semconv repo, observability-vendor docs (Langfuse, LangSmith, Braintrust, Phoenix, AgentOps, Helicone, Datadog, Honeycomb, Fiddler), Anthropic/OpenAI docs, and 2026 practitioner posts. Where a page was truncated or a claim comes from a secondary source, it is flagged.

## KQ1. What is the minimal "durable step" contract in Temporal / Inngest / Restate / DBOS (and Hatchet, Trigger.dev, Cloudflare, Step Functions), and how do they recommend handling non-deterministic, long-running LLM work?

### Takeaway
Every engine converges on the same contract: an orchestrator function that must be deterministic/replayable, plus named side-effecting "steps" (Temporal Activity, Inngest `step.run`, Restate `ctx.run`, DBOS `@DBOS.step`, Hatchet task, Trigger.dev task, Cloudflare `step.do`, Step Functions Task) whose results are journaled so they are not re-executed on replay; retries are configured per step with exponential backoff (initial interval, multiplier, max interval, max attempts, non-retryable error class), and long waits are modelled as durable timers, signals/events/awakeables/task tokens. All of them say the same thing about LLM calls: an LLM call is a non-deterministic side effect, so it goes inside a step/activity, never in orchestrator code; the orchestrator holds the agent loop, tool selection and conversation state.

### Cited Findings

**Temporal (Activities + RetryPolicy + timeouts + heartbeats)**
- Retry policy fields and defaults: Initial Interval 1s; Backoff Coefficient 2.0; Maximum Interval 100× initial (100s); Maximum Attempts unlimited (0 = unlimited, 1 = no retries); Non-Retryable Error Types matched against the `type` of an ApplicationFailure. Retry interval = min(initial × coefficient^retries, max interval). Activities get a retry policy by default; Workflows have none by default and docs advise retrying Activities rather than whole Workflows. Workflow Task failures retry with exponential backoff up to a 10-minute max interval until the Workflow Execution Timeout. — [Temporal: Retry policies](https://docs.temporal.io/encyclopedia/retry-policies)
- Activity timeout types: Schedule-To-Start (default ∞, non-retryable, used to detect crashed/slow worker fleets), Start-To-Close (no default; "strongly recommended"; required unless Schedule-To-Close is set; reset per attempt), Schedule-To-Close (default ∞; caps total across attempts), Heartbeat (default disabled `0s`; capped at Start-To-Close). Heartbeats can carry an application payload so the next attempt can resume from recorded progress; the Worker throttles heartbeats to min(0.8×heartbeat timeout or 30s default, 60s max) but the final heartbeat before failure is not throttled. — [Temporal: Detecting activity failures](https://docs.temporal.io/encyclopedia/detecting-activity-failures)
- Python snippet (verbatim from docs):
  ```python
  retry_policy = RetryPolicy(
      initial_interval=timedelta(seconds=10),
      backoff_coefficient=3.0,
      maximum_interval=timedelta(minutes=5),
      maximum_attempts=20,
  )
  result = await workflow.execute_activity(
      call_external_service, order,
      start_to_close_timeout=timedelta(seconds=30),
      retry_policy=retry_policy,
  )
  # non-retryable by type:
  RetryPolicy(non_retryable_error_types=["InvalidCardFormat","InsufficientFunds","AccountClosed"])
  ```
  — [Temporal Python: Failure detection](https://docs.temporal.io/develop/python/failure-detection)
- Determinism rule: "Workflow code must be deterministic to support replay"; API calls, LLM calls and DB queries go in Activities. Safe changes without versioning: activity/child-workflow inputs, return values, timeouts and timer durations; unsafe: reordering/adding/removing Timers, Activities, Child Workflows, Signals, Nexus ops. Branching on local time/random inline is "intrinsic non-determinism"; use SDK replay-safe time/random. — [Temporal: Workflow definition](https://docs.temporal.io/workflow-definition)
- Versioning: two methods: Worker Versioning (Deployment Versions; pinned workflows avoid patching) and Patching via `workflow.patched("my-patch")` → `workflow.deprecate_patch("my-patch")` → remove; `patched()` writes a marker into Event History and a replaying worker that doesn't produce the same marker fails the task. The experimental pre-2025 Worker Versioning is to be removed from Temporal Server in March 2026. Replay testing is recommended to check whether a patch is needed. — [Temporal Python: Versioning](https://docs.temporal.io/develop/python/versioning)
- OpenAI Agents SDK integration (Python): requires Python 3.10+ and Temporal Python SDK 1.33.0+; package `temporalio-openai-agents` (v1.0.0 moved it out of the SDK; imports changed from `temporalio.contrib.openai_agents` to `temporalio.openai_agents`). The plugin turns each model call into an Activity: "Model Activities retry durably and are not repeated during replay." `OpenAIAgentsPlugin(model_params=ModelActivityParameters(start_to_close_timeout=timedelta(seconds=30)))`; `start_to_close_timeout` default 60s; other `ModelActivityParameters`: `schedule_to_close_timeout`, `schedule_to_start_timeout`, `heartbeat_timeout`, `retry_policy`, `cancellation_type`, `versioning_intent`, `task_queue`, `priority`, `summary_override`, `use_local_activity`, `streaming_topic`, `streaming_batch_interval`. Plugin also takes `mcp_servers`, `sandbox_clients`, `mcp_connection_idle_timeout`, `use_otel_instrumentation` (OTel integration is Public Preview; sandbox pre-release; streaming experimental). Tool rules: `activity_as_tool(get_weather, start_to_close_timeout=timedelta(seconds=10))` runs in an Activity (I/O); `@function_tool` runs in Workflow and must do no network/db/file I/O; OpenAI-hosted tools run at the provider; `LocalShellTool`/`ComputerTool` unsupported; `SQLiteSession` unsupported (local file). `on_approval_request` runs in Workflow context, must be deterministic, and "can wait on a Signal or Update for external input." Conversation history lives in Workflow state rebuilt with `result.to_input_list()`; for long sessions use Continue-as-New after `is_continue_as_new_suggested()` and `all_handlers_finished()`. — [Temporal: OpenAI Agents SDK integration (Python)](https://docs.temporal.io/develop/python/integrations/openai-agents)
- Temporal's "Durable AI" page lists integrations: Python — OpenAI Agents SDK, LangGraph, Pydantic AI, Strands Agents, Google ADK, Google GenAI, Deep Agents; TypeScript — Vercel AI SDK, OpenAI Agents SDK, Google ADK, Strands, Mastra; Go — Google ADK; Java — Spring AI. Design patterns catalogued: Approval, Saga, Long-Running Activity (heartbeats and resumption), Entity Workflow, Local Activities. — [Temporal: Durable AI](https://docs.temporal.io/ai)
- The launch blog described the Python OpenAI Agents SDK integration as Public Preview at announcement; the TypeScript docs mark the TS integration pre-release and support `agentAsTool`. — [Temporal blog: Production-ready agents with the OpenAI Agents SDK + Temporal](https://temporal.io/blog/announcing-openai-agents-sdk-integration); [Temporal docs tag](https://docs.temporal.io/tags/open-ai-agents-sdk)
- Temporal Code Exchange sample combining OpenAI Agents SDK + Temporal Python + MCP + optional Pydantic Logfire (planner → parallel web search → writer → verifier). — [Temporal Code Exchange: MCP durable agents](https://temporal.io/code-exchange/mcp-temporal-durable-agents)

**Inngest (step.run / step.ai / AgentKit)**
- `step.run` memoizes each step's return value; on rerun the SDK returns the saved result without calling the callback; code outside steps may re-execute; step IDs must stay stable across deployments. Steps do not guarantee exactly-once external effects — "use idempotency keys for payments, messages, and similar writes." `step.sleep`/`step.sleepUntil` (max 1 year; plan caps Free 30d / Pro 90d / Business 366d); `step.waitForEvent("wait-for-payment", {event: "payment/succeeded", timeout: "1d"})` returns `null` on timeout; `step.waitForSignal` resumes a specific run; `step.invoke` calls another function and waits; `step.sendEvent` is a reliable step. Limits: step runs up to 2 hours; 1,000 steps per function; 4 MiB per step result; 32 MiB run state; JSON-serializable results. Changing a step ID makes it new work for active runs. — [Inngest: Steps & workflows](https://www.inngest.com/docs/features/inngest-functions/steps-workflows)
- Retries: default four retries after the initial attempt; `retries: 0` disables; TS SDK v4 accepts 0–20; each `step.run` has its own retry counter; standard errors use backoff with jitter (exact schedule not documented on page); `NonRetriableError` for permanent failures, `RetryAfterError` for rate limits; handler receives zero-indexed `attempt`. — [Inngest: Retries](https://www.inngest.com/docs/features/inngest-functions/error-retries/retries)
- `step.ai.infer("call-openai", {model: step.ai.models.openai({model:"gpt-4o"}), body:{...}})` routes the model request through Inngest infrastructure so the (serverless) function is paused and not billed while waiting; providers: OpenAI (+ OpenAI-compatible), Gemini, Anthropic, Grok, Azure OpenAI; "Inngest never logs or stores your API keys." `step.ai.wrap("using-vercel-ai", generateText, {...})` (TS only) memoizes an existing SDK call as a step with prompt/token observability and allows editing prompts and re-running from a step in the Dev Server/Cloud (requires JSON-serializable args). Streaming "coming soon." — [Inngest: step.ai orchestration](https://www.inngest.com/docs/features/inngest-functions/steps-workflows/step-ai-orchestration)
- AgentKit: agents (name, system prompt, model, tools), networks with routers, shared State, MCP servers as tools; models OpenAI/Anthropic/Gemini/OpenAI-compatible; integrations E2B, Browserbase, Smithery, Daytona. — [AgentKit overview](https://agentkit.inngest.com/overview)
- Router types: code-based (deterministic, no LLM), routing agent (LLM picks next agent; default routing agent used if none given; cannot have tools), hybrid; `RouterArgs {network, stack, callCount, lastResult}`; docs recommend starting with code-based routing for "deterministic, predictable behavior." — [AgentKit: Routers](https://agentkit.inngest.com/concepts/routers)
- `createNetwork({agents, defaultModel, router, maxIter, defaultState})`; a network is "a while loop with memory"; loop ends when router returns no agent or `maxIter` is reached; docs recommend `maxIter` with LLM routers to prevent endless loops. — [AgentKit: Networks](https://agentkit.inngest.com/concepts/networks)

**Restate (ctx.run journal + awakeables + immutable deployments)**
- `ctx.run` records results in an execution log for replay; nested context ops are not allowed inside the wrapped fn; failures retry by default; `TerminalError` stops retries. Retry policy snippet (verbatim):
  ```typescript
  const myRunRetryPolicy = {
    initialRetryInterval: { milliseconds: 500 },
    retryIntervalFactor: 2,
    maxRetryInterval: { seconds: 1 },
    maxRetryAttempts: 5,
    maxRetryDuration: { seconds: 1 },
  };
  await ctx.run("write", () => writeToOtherSystem(), myRunRetryPolicy);
  ```
  Exhausted policy throws `TerminalError` (catch and compensate, see Sagas). Default: if a service emits no journal entry for >1 minute Restate suspends and retries the invocation — "for slow work, such as an LLM call that may take up to three minutes, increase the service's inactivity and abort timeouts." Deterministic helpers seeded by invocation ID: `ctx.rand.uuidv4()` (stable, usable as idempotency key), `ctx.rand.random()`, `ctx.date.now()`. — [Restate: Durable steps](https://docs.restate.dev/develop/ts/durable-steps)
- Awakeables = task-token pattern: `const {id, promise} = ctx.awakeable<string>(); await ctx.run(() => requestHumanReview(name, id)); const review = await promise;` resolved via `ctx.resolveAwakeable(id, ...)`/`rejectAwakeable` or HTTP `curl localhost:8080/restate/awakeables/<ID>/resolve --json '"Looks good!"'`; resolve/reject only once; workflow promises (`ctx.promise<string>("review")`) retained 24h by default; long waits should be combined with a durable timer for timeout. — [Restate: Awakeables](https://docs.restate.dev/develop/ts/awakeables)
- Idempotency: `restate.rpc.opts({ idempotencyKey: "my-idempotency-key" })` on calls; with a key you can later attach to the invocation and retrieve its result; one-way and delayed sends (`sendOpts({delay:{hours:5}})`). — [Restate: Service communication](https://docs.restate.dev/develop/ts/service-communication)
- Versioning: deployments are immutable; "requests start and end on the same version"; register new code at a new endpoint (`restate deployments register http://greeter-v2/`); old deployments drain then `restate deployments remove <id>`; editing code in place causes journal mismatch (RT0016) non-determinism errors; targeted fix: `restate invocations pause <id>` then `resume --deployment <new>` (must remain journal-compatible). — [Restate: Versioning](https://docs.restate.dev/operate/versioning)

**DBOS (Postgres-backed decorators)**
- `@DBOS.workflow()` + `@DBOS.step()`; on interruption resumes from last completed step; workflows must make the same step calls in the same order (`DBOSStepNondeterminismError` otherwise); non-deterministic work (random, DB, API calls, time) goes in steps. Idempotency: `with SetWorkflowID("very-unique-id", workflow_id_reuse_policy="reject")`; durable `DBOS.sleep()` stores wake time in DB; steps run at-least-once and are not re-executed once complete; uncaught workflow exception sets status `ERROR` and is not recovered. — [DBOS: Workflows](https://docs.dbos.dev/python/tutorials/workflow-tutorial)
- Step signature: `@DBOS.step(retries_allowed: bool = False, interval_seconds: float = 1.0, max_attempts: int = 3, backoff_rate: float = 2.0, should_retry: Optional[Callable[[BaseException], bool|Awaitable[bool]]] = None)`; `timeout_seconds` for async steps (per attempt; retry gaps don't count); exhaustion raises `DBOSMaxStepRetriesExceeded`; timeout raises `DBOSStepTimeoutError`; steps must have serializable outputs; a step called from a step is not separately checkpointed; `DBOS.run_step({"name": ...}, lambda: ...)` wraps without decorator. — [DBOS: Steps](https://docs.dbos.dev/python/tutorials/step-tutorial)
- Human input / messaging: `DBOS.send(destination_id, message, topic)` / `DBOS.recv(topic, timeout_seconds=60)` (returns `None` on timeout; exactly-once from workflows, exactly-once from plain code only with `idempotency_key`); `DBOS.set_event(key, value)` / `DBOS.get_event(workflow_id, key, timeout_seconds=60)`; streams `DBOS.write_stream`/`read_stream` (writes from workflow exactly-once; from a step at-least-once). — [DBOS: Workflow communication](https://docs.dbos.dev/python/tutorials/workflow-communication)
- Versioning: each workflow tagged with application version (default = hash of workflow source; override via `application_version` config); recovery only recovers workflows whose version matches the running code; blue/green via `SetEnqueueOptions(app_version=latest)`; `DBOS.list_workflows(app_version="1.0.0", status=["ENQUEUED","DELAYED","PENDING"])` to check before retiring; `DBOS.set_latest_application_version("1.0.0")` for rollback. — [DBOS: Upgrading workflows](https://docs.dbos.dev/python/tutorials/upgrading-workflows)

**Hatchet**
- Positioned as "a durable execution platform"; each completed step "creates a new checkpoint (an entry in a durable event log)"; durable tasks only do two things: wait (sleep or event) or spawn child tasks, combinable with "or groups"; agentic workflows named as a primary use case, incl. human-in-the-loop approvals that are not replayed on resume. — [Hatchet: Durable execution](https://docs.hatchet.run/home/durable-execution)
- Retries: `@wf.task(retries=3)`; `ctx.retry_count`; backoff `backoff_factor=2.0, backoff_max_seconds=10` (TS: `backoff: {factor: 2, maxSeconds: 10}`); `NonRetryableException` (Py) / `NonRetryableError` (TS); `RetryAfterException(..., after=timedelta(seconds=2))`. — [Hatchet: Retry policies](https://docs.hatchet.run/home/retry-policies)
- Durable event waits: `@hatchet.durable_task` with `await ctx.aio_wait_for_event("user:update")`; TS `hatchet.durableTask({ name, executionTimeout: '10m', fn: async (_, ctx) => ctx.waitForEvent(EVENT_KEY) })`; CEL filter expressions on payload (`input.user_id == '1234'`); lookback windows with scopes to avoid races. — [Hatchet: Durable event waits](https://docs.hatchet.run/home/durable-event-waits)

**Trigger.dev**
- `task({id, run})`; default 3 attempts; retry config `{maxAttempts: 10, factor: 1.8, minTimeoutInMs: 500, maxTimeoutInMs: 30_000, randomize: false}`; `maxDuration` (unbounded by default); `machine: {preset: "large-1x"}` (4 vCPU/8 GB); `queue`/`concurrency`; `ttl`; lifecycle hooks `onStartAttempt`, `onWait`/`onResume`, `onSuccess`/`onFailure`, `catchError`, `onCancel` (must finish within 30s). — [Trigger.dev: Tasks](https://trigger.dev/docs/tasks/overview)
- Human-in-the-loop via waitpoint tokens: `wait.createToken({timeout: "10m", idempotencyKey, idempotencyKeyTTL, tags})` → `wait.forToken<T>(token.id)` returns `{ok, output|error}` → `wait.completeToken(token.id, output)` from anywhere (HTTP `/complete` with public access token or webhook URL). — [Trigger.dev: Wait for token](https://trigger.dev/docs/wait-for-token)
- Idempotency: `idempotencyKey` on `trigger()`/`triggerAndWait()`/`batchTrigger()` dedupes the trigger (not the body of `run()`); scopes `run` (default; key + parent run id), `attempt`, `global`; keys stored 30 days by default (`idempotencyKeyTTL`); failed runs clear their key; derive provider idempotency keys from `ctx.run.id`. — [Trigger.dev: Idempotency](https://trigger.dev/docs/idempotency)
- Child tasks: `triggerAndWait().unwrap()`, `batchTriggerAndWait()` (up to 1,000 runs per batch on SDK ≥4.3.1, 500 earlier; payloads >512KB offloaded to object storage, hard limit >10MB; outputs capped 100MB; Cloud max run TTL 14 days); trigger options `delay`, `ttl`, `queue.concurrencyLimit`, `concurrencyKey`, `maxAttempts`, `tags`, `metadata`, `maxDuration`, `priority`, `region`, `machine`. — [Trigger.dev: Triggering](https://trigger.dev/docs/triggering)

**Cloudflare Workflows + Agents SDK**
- `step.do(name, {retries: {limit: 5, delay: "10 seconds", backoff: "linear"}, timeout: "2 minutes"}, fn)`; `ctx.attempt`; optional rollback callback run in reverse on failure; `step.sleep`/`sleepUntil` (don't count toward step limit); `step.waitForEvent(name, {type, timeout})` default timeout 24h, throws on timeout; `NonRetryableError` from `cloudflare:workers`; `instance.sendEvent({type, payload})`; `restart({from})` reuses cached step results. Limits: 10,000 steps default (configurable to 25,000; Free 1,024); step return ≤1 MiB serializable; names ≤256 chars. — [Cloudflare Workflows: Workers API](https://developers.cloudflare.com/workflows/build/workers-api/)
- Agents SDK (Durable-Object based): `this.state`/`setState`, embedded SQLite via `this.sql`, `schedule()/scheduleEvery()`, WebSocket hooks, `@callable()` methods, `runWorkflow()`/`waitForApproval()`, durable-execution methods `runFiber()`, `startFiber()`, `stash()`, `onFiberRecovered()`, `keepAlive()`; page last updated Aug 4, 2026. — [Cloudflare Agents API](https://developers.cloudflare.com/agents/api-reference/agents-api/)
- Agents→Workflows: `this.runWorkflow(name, payload, {id, metadata, agentBinding})`; inside workflow `await this.waitForApproval<T>(step, {timeout: "7 days"})` throws `WorkflowRejectedError` on rejection; agent calls `approveWorkflow(instanceId, {reason, metadata})`/`rejectWorkflow`; callbacks `onWorkflowProgress/Complete/Error/Event`; durable idempotent reporters (`step.reportComplete`, `step.sendEvent`) vs non-durable `reportProgress()`; limits: 10,000 steps default (up to 25,000), event wait up to 1 year, 30 min per step. Page last updated Oct 12, 2026. — [Cloudflare Agents: Run Workflows](https://developers.cloudflare.com/agents/api-reference/run-workflows/)
- Fibers (last updated Aug 20, 2026): `runFiber(name, fn)` registers a row in SQLite (`cf_agents_runs`), holds `keepAlive()` (30 s alarm heartbeat), returns result; `startFiber(name, fn, {idempotencyKey, metadata, waitForCompletion})` returns `{fiberId, status, accepted}`; `ctx.stash(data)` writes a JSON snapshot (full replace); `onFiberRecovered(ctx)` runs once per orphaned fiber with `{name, snapshot, status, idempotencyKey, metadata, createdAt, recoveryReason}`; fibers do NOT retry automatically — retry logic belongs in `onFiberRecovered`; recovery backoff capped at 5 min; rows older than `fiberRecoveryMaxAgeMs` (default 24h) discarded; "the original closure cannot be replayed, so recovery depends on the snapshot." Guidance: fibers for work inside the agent's own execution; Workflows for independent multi-step orchestration with per-step retries. — [Cloudflare Agents: Durable execution](https://developers.cloudflare.com/agents/api-reference/durable-execution/)

**AWS Step Functions (ASL)**
- Retrier schema: `ErrorEquals` (required array), `IntervalSeconds` (default 1, max 99,999,999), `MaxAttempts` (default 3; 0 = never retry), `BackoffRate` (default 2.0), `MaxDelaySeconds` (>0 and <31,622,401; unbounded if omitted), `JitterStrategy` (`FULL`|`NONE`, default `NONE`). Catchers: `ErrorEquals`, `Next`, `ResultPath`. Built-in errors: `States.ALL`, `States.Timeout`, `States.TaskFailed` (wildcard except Timeout), `States.HeartbeatTimeout`, `States.Runtime` (not retriable), `States.DataLimitExceeded`, `States.Permissions`, `States.ExceedToleratedFailureThreshold`. Retries count as state transitions (billing). Redriven executions reset retry counts. Example:
  ```json
  "Retry": [ { "ErrorEquals": ["States.Timeout"], "IntervalSeconds": 3, "MaxAttempts": 3,
               "BackoffRate": 2, "MaxDelaySeconds": 5, "JitterStrategy": "FULL" } ]
  ```
  — [AWS: Handling errors in Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)
- Integration patterns: Request Response; `.sync` (wait for job); `.waitForTaskToken` (pause until `SendTaskSuccess`/`SendTaskFailure` with `$$.Task.Token`, up to the one-year execution quota; `HeartbeatSeconds` + `SendTaskHeartbeat` to avoid stuck waits → `States.Timeout`). Express workflows support only Request Response. Bedrock has `.sync` and `.waitForTaskToken`; Bedrock AgentCore only Request Response. — [AWS: Service integration patterns](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html)

### Inferences
- Minimal durable-step contract common to all: `(stable_step_id, serializable_input) -> journaled serializable_output` with per-step `{initial_interval, backoff_factor, max_interval, max_attempts|max_duration, non_retryable_error_class, per-attempt timeout}` and an optional heartbeat/keep-alive for long attempts. The names differ, the shape doesn't (Temporal RetryPolicy ≈ Restate RunRetryPolicy ≈ DBOS step kwargs ≈ Trigger.dev retry ≈ Step Functions Retrier).
- Wrapping a long-running coding-agent process: the strongest-fit shapes are (a) Temporal: one Activity per model call/tool call with the agent loop in the Workflow (the OpenAI Agents plugin does exactly this), using heartbeats with progress payloads for a multi-minute `claude -p` or `codex exec` subprocess and Continue-as-New for long sessions; (b) a single long Activity/task running the whole agent subprocess (Temporal "Long-Running Activity" pattern, Trigger.dev task with `maxDuration`, Hatchet durable task with `executionTimeout`), which is simpler but loses per-step replay; (c) Inngest/Cloudflare serverless-step models are constrained by per-step limits (Inngest 2h/step, 4 MiB step output; Cloudflare 30 min/step, 1 MiB step output), so a long coding-agent run must be split into steps or offloaded.
- Human approval is a first-class primitive everywhere: Temporal Signals/Updates, Inngest `waitForEvent`/`waitForSignal`, Restate awakeables, DBOS `recv`, Hatchet event waits, Trigger.dev waitpoint tokens, Cloudflare `waitForApproval`/`waitForEvent`, Step Functions `.waitForTaskToken`. All need an explicit timeout to avoid indefinite waits.
- Idempotency is split into two layers everywhere: trigger/invocation dedup (workflow ID, idempotencyKey) and side-effect dedup inside a step (provider idempotency keys derived from stable run/attempt IDs, e.g. Restate `ctx.rand.uuidv4()`, Trigger.dev `ctx.run.id`).

### Gaps
- No engine documents a specific recipe for wrapping Claude Code or Codex CLI subprocesses as activities/steps; the Temporal OpenAI Agents integration explicitly excludes `LocalShellTool`/`ComputerTool`, so local shell-heavy coding agents must be run as ordinary activities.
- Inngest's exact backoff schedule and Temporal's Worker Deployment (build-ID) details were not on the fetched pages.
- Restate's HTTP `idempotency-key` header retention and Hatchet's `execution_timeout`/`schedule_timeout` defaults were not captured.

## KQ2. What do the OpenTelemetry GenAI semantic conventions currently standardize for agent/workflow spans, and which tools consume it? What does a multi-step agent trace look like, with cost/token attribution and replay?

### Takeaway
As of Oct 2026 the GenAI semconv (now in its own repo, `semantic-conventions-genai`) is still at "Development" stability; it defines `create_agent`, `invoke_agent` (CLIENT or INTERNAL), `execute_tool` (INTERNAL, with skill/command-execution refinements), the inference span, token/duration metrics, and opt-in content capture (`gen_ai.input.messages`/`gen_ai.output.messages`); `invoke_workflow` and `plan` exist only as operation-name values without their own span definitions. Langfuse, LangSmith and Datadog ingest `gen_ai.*` OTLP directly (plus OpenInference); Phoenix is OpenInference-native; Braintrust accepts OTLP; AgentOps/Helicone use their own SDK/header models; Honeycomb's documented LLM integration is Admin-API usage polling rather than gen_ai spans.

### Inferences
- A canonical multi-step agent-pipeline trace under current conventions: root `invoke_workflow` or `invoke_agent {name}` (INTERNAL) span carrying `gen_ai.conversation.id` = pipeline run/session id → per-node `invoke_agent` spans → `chat {model}` inference spans with `gen_ai.usage.*` and `gen_ai.response.id` → `execute_tool {tool}` spans (for coding agents: command-execution variant with `process.executable.name`/`process.exit.code`). Cost is not a semconv attribute (only `gen_ai.usage.cost` is understood by Langfuse); per-step cost must be computed by the backend from usage × model price (Langfuse model definitions, LangSmith pricing map, Braintrust `llm` span cost) or attached by the producer.
- For a pipeline that runs Claude Code sessions, the practical join key is `session.id` (Claude Code OTel) ↔ `gen_ai.conversation.id` / `langfuse.session.id` / Datadog `session_id` / Helicone-Session-Id; Datadog and Fiddler both say provider/proxy traces are not propagated and must be joined on session id.
- "Replay" means different things: durable engines replay journaled step outputs (deterministic recovery); observability tools offer prompt-edit-and-rerun from a step (Inngest) or trace→dataset→experiment loops (LangSmith/Braintrust), not true re-execution of a coding-agent session.

## KQ3. What per-step cost and token data is realistically available from Claude Code / Codex runs, and what cost-governance controls (budgets, max-turns, spend caps, usage APIs, OTel metrics) exist?

### Takeaway
Claude Code gives the richest per-run record: a `result` JSON with `total_cost_usd`, `usage`, and per-model `modelUsage` (input/output/cache tokens + `costUSD` + `costBasis`), per-step assistant-message usage (dedupe by message id; per-step `output_tokens` is a placeholder), OTel metrics `claude_code.cost.usage`/`claude_code.token.usage` with model/`query_source`/agent/skill/MCP attributes, and `claude_code.api_request` events with `cost_usd` per API call — all client-side estimates. Codex `exec --json` emits only `turn.completed` token counts (`input_tokens`, `cached_input_tokens`, `output_tokens`), no USD. Governance primitives: `--max-turns`, `--max-budget-usd` (subagent spend counts; cap can be overshot), subagent depth/concurrency/spend limits, org/workspace spend limits, and the Anthropic/OpenAI admin usage+cost APIs for reconciliation.

### Cited Findings

**Claude Code / Agent SDK per-run and per-step data**
- `claude -p ... --output-format json` returns structured JSON incl. `total_cost_usd` and a per-model cost breakdown; with `--continue`/`--resume` the run reports the whole conversation's total incl. earlier runs; "Both figures are client-side estimates." `stream-json` ends with a `result` message with cost and session metadata; `--json-schema` yields `structured_output`. Subagent messages carry `parent_tool_use_id`; `--forward-subagent-text` (v2.1.211+) forwards subagent text/thinking so transcripts can be reconstructed at every nesting depth (v2.1.219+). `system/api_retry` events expose `attempt`, `max_retries`, `retry_delay_ms`, `error_status`, `error` category (`rate_limit`, `overloaded`, `max_output_tokens`, …). `system/init` carries model, tools, MCP servers, plugins, `plugin_errors`, `mcp_server_errors`. Bare mode `--bare` recommended for CI. SIGTERM → exit 143, turn left unfinished. — [Claude Code: Run programmatically (headless)](https://code.claude.com/docs/en/headless)
- Agent SDK cost model: scopes are `query()` call → steps (one request/response each) → session (linked by `resume`). Each assistant message has `message.message.id` and `usage` (`input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`); parallel tool calls share one id — deduplicate. Per-step `output_tokens` is a placeholder (reported at `message_start`); read output totals from the `result` message or `modelUsage`. Result fields: `usage` (top-level loop only, excludes subagents), `total_cost_usd` (includes subagents), `modelUsage`/`model_usage` (per model: `inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`, `costUSD`, `costBasis` ∈ {`list`,`managed`,`unknown`}; v2.1.246+). Error results also carry cost; `error_max_budget_usd` results omit the crossing response from `usage` but include it in `total_cost_usd`; a crash's `error_during_execution` result may be zeroed. Resumed sessions restore totals (v2.1.277+). `maxBudgetUsd` counts only the call's own spend. Data-residency 1.1× multiplier applied client-side (TS SDK ≥0.3.239 / Py ≥0.2.144). `total_cost_usd`/`costUSD` are "client-side estimates, not authoritative billing data." — [Claude Agent SDK: Track cost and usage](https://code.claude.com/docs/en/agent-sdk/cost-tracking)
- CLI flags: `--max-turns` (print mode; exits with error at limit; no default limit); `--max-budget-usd` (print mode; checked against client-side estimate; subagent spend counts; "Spend can pass the cap"; at cap new subagent spawns fail with `Budget limit reached` and running background subagents are stopped, v2.1.217+); `--fallback-model sonnet,haiku`; `--effort low|medium|high|xhigh|max|ultracode`; `--session-id`, `--fork-session`, `--no-session-persistence`; `--restricted` for eval harnesses. — [Claude Code: CLI reference](https://code.claude.com/docs/en/cli-reference)
- OTel metrics (exported via `OTEL_METRICS_EXPORTER`, default interval 60s): `claude_code.session.count`, `claude_code.lines_of_code.count` (type added/removed), `claude_code.pull_request.count`, `claude_code.commit.count`, `claude_code.cost.usage` (USD), `claude_code.token.usage` (type input/output/cacheRead/cacheCreation), `claude_code.code_edit_tool.decision`, `claude_code.active_time.total`. Cost/token attributes: `model`, `query_source` (main/subagent/auxiliary), `speed`, `effort`, `agent.name`, `skill.name`, `plugin.name`, `mcp_server.name`, `mcp_tool.name`. Standard attrs: `session.id` (on by default), `user.id` (random anonymous), `user.email`, `organization.id`, `terminal.type`, `app.version`/`app.entrypoint` (off by default). Events (logs exporter, 5s interval): `claude_code.user_prompt` (`prompt_length`, `prompt` redacted unless `OTEL_LOG_USER_PROMPTS=1`), `claude_code.tool_result` (`tool_name`, `tool_use_id`, `success`, `duration_ms`, `error_type`, `decision_type/source`, sizes), `claude_code.api_request` (`model`, `cost_usd`, `cost_usd_micros`, `duration_ms`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `request_id`, `query_source`, `effort`), `claude_code.api_error` (`status_code`, `attempt`), `claude_code.tool_decision` (`decision`, `source` ∈ config/hook/user_permanent/user_temporary/user_abort/user_reject), plus `api_refusal`, `assistant_response`, `permission_mode_changed`, `skill_activated`, raw bodies with `OTEL_LOG_RAW_API_BODIES`. Correlation keys `prompt.id`, `event.sequence`. `OTEL_RESOURCE_ATTRIBUTES="department=engineering,team.id=platform,cost_center=eng-123"` for chargeback labels. Managed settings can pin the collector endpoint so telemetry can't be redirected; project `.claude/settings.json` can't enable telemetry. Third-party plugin/skill/agent/MCP names are replaced with "custom"/"third-party" unless `OTEL_LOG_TOOL_DETAILS=1`. — [Claude Code: Monitoring (OpenTelemetry)](https://code.claude.com/docs/en/monitoring-usage)
- `/usage` Session block computes dollars locally at list price (or an admin-set `modelPricing` table, v2.1.242+, flagged "at your organization's configured rates"); example `Usage by model: claude-sonnet-4-6: 1.2k input, 5.3k output, 940.0k cache read, 50.0k cache write ($0.55)`; totals reset on `/clear` (v2.1.211+); prompt-cache stats line (v2.1.251+); plan-usage attribution to skills/subagents/plugins/MCP servers; enterprise average ≈ $13/dev/active day, $150–250/dev/month, <$30/day for 90% of users; agent teams ≈ 7× tokens in plan mode; background usage typically <$0.04/session. Org controls: Teams/Enterprise spend limits + Enterprise Analytics API; Console workspace spend limits + Claude Code Analytics API; cloud providers → OTel or a gateway (LiteLLM named). Rate-limit sizing table (e.g. 1–5 users: 200–300k TPM/user). — [Claude Code: Manage costs](https://code.claude.com/docs/en/costs)

- Budget enforcement is soft at the agent layer (`--max-budget-usd` can overshoot; `MaxTurnsExceeded` loses the final output), so hard caps belong at the orchestrator (step/activity timeouts, max attempts) and at the gateway/workspace level.

## KQ4. What observability features do practitioners say are missing when running many coding-agent sessions?

### Takeaway
2026 practitioner sources converge on five gaps: (1) silent failures (loops, context loss, tool misuse, "green CI but wrong code") that produce no error signal; (2) no per-session record linking spend to outcomes (tickets/PRs/rework), with traces unable to distinguish retries vs never-cleared context vs subagent fan-out; (3) attribution of broken code to agent/model-version/cost; (4) harness drift (which CLAUDE.md/AGENTS.md, skills, MCP servers were loaded); (5) transcripts and content redacted by default and absent from trace spans, so session review requires explicit content flags or separate capture.

### Cited Findings
- XTrace (Sept 11 / Oct 10, 2026; vendor post): proposes four layers — execution (sessions, traces, tool calls, subagents), harness (CLAUDE.md, AGENTS.md, skills, MCP servers, memory), money (tokens, cache hit rate, per-session cost), outcomes (tickets, PRs, CI results, rework). Headline metric: cost per accepted ticket incl. failed attempts, retries and subagents. A trace must distinguish "retries from a never-cleared context from a subagent fan-out." Harness drift should be recorded per session. Month-over-month diffs of rework rate, human messages per PR, cost per ticket. Transcripts: engineers should open a session turn by turn; Claude Code OTel redacts prompt text by default. Claims vendor dashboards (Claude Code, Cursor, ChatGPT Enterprise) report per-user spend but don't link sessions to tickets; LLM-observability tools (Langfuse, Braintrust, Datadog) don't model tickets/PRs/harness files/budgets. Data points: 6,910 tool calls across 45 sessions (~154/session); illustrative 150k-token context resent 40× ≈ $3 warm / $30 cold at Opus 5 list price ($5/M input, $0.50 cache hit); Claude Code PR attribution matches sessions to PRs from 21 days before to 2 days after merge and drops lines rewritten >20%; in-house build ≈ 2–3 engineer-weeks. — [XTrace: What is coding agent observability in 2026](https://xtrace.ai/blog/coding-agent-observability)
- Fiddler (Jul 24, 2026; vendor post): coding agents "fail silently through loops, context loss, and tool misuse"; example of a Claude Code agent looping on a failing test, losing context about a validation rule and rewriting a currency-rounding helper so tests pass while CI stays green. Recommends execution traces (trace = session; spans = model calls, tool invocations, sub-agent handoffs), behavioural/code-quality signals (loop and step counts, context-window utilization, tool-call error rate; faithfulness to ticket, groundedness in codebase), and cost/attribution per session and per PR. Alert thresholds: `tool_call.count > 20`; prompt tokens > 80% of context; session tokens 10× median for routine task. Advice: join agent-side, gateway-side and MCP-side telemetry on a shared `session_id`; don't sample away rare sessions; redact at capture. — [Fiddler: Coding Agent Observability](https://www.fiddler.ai/blog/coding-agent-observability)
- Fiddler's Claude Code integration docs list what is NOT available in Claude Code trace spans: LLM response content, thinking content, cost data, trace propagation to providers/proxies, per-attribute redaction; tracing is beta and names may change. — [Fiddler: Claude Code integration](https://docs.fiddler.ai/integrations/agentic-ai/claude-code-integration)
- Augment Code (Apr 19, 2026, updated Jun 18; vendor post): traces, evals and cost tracking are "relatively mature" (LangSmith, Langfuse, Phoenix); attribution — linking broken code to a specific agent, model version and cost — "usually does not" get solved; recommends `session_id`, `agent_type`, `agent_version`, `model`, `user_id` on every span, a root span per agent run, cost aggregated by agent, alerts (tool calls >20/session, context >80%, error rate >1% over 5 min), tail-based sampling keeping all error/expensive traces, redaction in the span processor; minimum eval suite: compile checks, test runs, diff-size bounds. — [Augment Code: Agent observability for AI coding](https://www.augmentcode.com/guides/agent-observability-for-ai-coding)
- arXiv 2605.29442 (May 2026): 20,574 real coding-agent sessions from 1,639 repositories (IDE and CLI); misalignment defined by developer pushback; seven forms (how agents read projects, interpret intent, follow rules, bound actions, implement/execute, report progress); 90.50% of episodes impose effort/trust costs rather than irreversible damage; 91.49% of visible resolutions still require explicit user correction; constraint violations and inaccurate self-reporting growing as a share of failures. — [arXiv: How Coding Agents Fail Their Users](https://arxiv.org/abs/2605.29442)
- Claude Code docs: `/insights` writes an HTML report analysing up to 200 local sessions (friction points, misunderstood requests) — local only; `/usage` attribution covers skills/subagents/plugins/MCP but is local-machine only; cross-session messaging, scheduled tasks, goal check-ins and agent teams all inflate usage in ways the docs explicitly list as surprising. — [Claude Code: Manage costs](https://code.claude.com/docs/en/costs)
- Claude Code docs explicitly support reconstructing subagent transcripts via `parent_tool_use_id` and `--forward-subagent-text`, and linking sessions to PRs (`--from-pr` picker; sessions "are linked automatically when Claude creates the pull request"). — [Claude Code: headless](https://code.claude.com/docs/en/headless); [CLI reference](https://code.claude.com/docs/en/cli-reference)
- Tool reviews: one Claude Code or Cursor session can consume more tokens in an afternoon than a chatbot in a week (Monte Carlo); agent runs are long, deeply nested and resend the full conversation each turn, which general LLM tracing handles poorly (Laminar); "a tool without step-level and trace-level quality metrics is mostly a trace viewer" (Confident AI). — [Monte Carlo: Agent observability tools 2026](https://montecarlo.ai/blog-agent-observability-tools); [Laminar: Top 6 agent observability platforms](https://laminar.sh/article/top-6-agent-observability-platforms); [Confident AI: Agent observability platforms 2026](https://www.confident-ai.com/knowledge-base/compare/best-ai-agent-observability-tools-2026)

### Inferences
- The specific items the brief asked about map to sources as follows: *diffs over time* → XTrace's month-over-month rework/cost-per-ticket diffs and Augment's diff-size bounds (no tool documented as doing per-session diff history); *session transcripts linked to pipeline runs* → Claude Code's `.jsonl` transcript + session id + PR linking exists locally, but no observability vendor in the fetched docs ingests the transcript as a first-class object (Fiddler needs a plugin for response content); *retry diffs* → no fetched source offers "diff between attempt N and N+1" of an agent's output; the closest are Inngest's edit-and-rerun from a step and durable engines' per-attempt journals.
- All the practitioner sources are vendor-authored (XTrace, Fiddler, Augment, Monte Carlo, Laminar, Confident AI); the arXiv study is the only independent quantitative source and it studies misalignment, not tooling gaps.

### Gaps
- No independent survey quantifies which observability features teams running fleets of coding-agent sessions lack.
- No source documents a tool that stores per-attempt code diffs of an agent step alongside the trace.

## KQ5 (brief item d). Evaluation/regression testing of agent pipelines and how determinism is improved

### Takeaway
Eval tooling (Braintrust, LangSmith, promptfoo) treats an eval as data + task + scorers run as an "experiment," with CI integration via CLI/GitHub Actions and LLM-as-judge scorers layered over deterministic checks; agent-specific evals score trajectories/tool selection as well as final output. Determinism levers are explicitly best-effort: OpenAI `seed`+`system_fingerprint` ("mostly" identical), temperature 0 is not a guarantee on Claude, and structured outputs (Anthropic `output_config.format` with constrained decoding; strict tool use) guarantee schema conformance but not identical content; replay in durable engines only guarantees that *recorded* step outputs are reused.

### Cited Findings
- Braintrust evals: three parts — data, task, evaluators (scorers numeric, classifiers labels; built-in autoevals, LLM-as-judge, custom code); experiments are immutable and comparable over time; online evaluation scores production traces asynchronously (LLM-judge since no ground truth); traces can be promoted to dataset cases. — [Braintrust: Evals](https://www.braintrust.dev/docs/guides/evals)
- Braintrust CI: `braintrustdata/eval-action@v2` with `api_key`, `runtime` (node/python/go), `report_scores`, `report_metrics` (e.g. `Duration`, `Cost`), posts a PR comment (needs `pull-requests: write`); other CI: `bt eval evals/ --no-input --json`; `--first N`/`--sample N` for PR smoke tests; exit code non-zero only on exceptions by default — score-threshold gating needs a custom `Reporter()` whose `reportRun` returns true/false. — [Braintrust: Run in CI](https://www.braintrust.dev/docs/evaluate/run-in-ci)
- LangSmith evals: datasets/examples (reference outputs only visible to evaluators), experiments, workspace-level evaluators with sampling/filters/spend limits per attachment; techniques: human, code, LLM-as-judge, decision model, pairwise; reference-free evaluators work online; offline for regression/backtesting; agent evaluation = tool selection, argument formatting, trajectory; datasets auto-versioned and taggable for CI stability; evals writable in pytest or Vitest/Jest; "requiring a new version to beat a baseline" as a regression test. — [LangSmith: Evaluation concepts](https://docs.langchain.com/langsmith/evaluation-concepts)
- promptfoo CI: `npx promptfoo@latest eval -c promptfooconfig.yaml --share --fail-on-error --tag git.sha="$GITHUB_SHA" -o results.json -o results.junit.xml`; cache `~/.cache/promptfoo` with `PROMPTFOO_CACHE_PATH`/`PROMPTFOO_CACHE_TTL`; `-j 1` to reduce rate limits; pass-rate threshold computed from `results.json` with `exit 1`; PR comment via `gh pr comment`; GitLab JUnit upload; `promptfoo/promptfoo-action` shown for red-team. — [promptfoo: CI/CD integration](https://www.promptfoo.dev/docs/integrations/ci-cd/)
- promptfoo model-graded assertions: `llm-rubric` (general), `g-eval`, `factuality`, `model-graded-closedqa`, `select-best`, `max-score`, `similar`, `classifier`, `moderation`; default judge depends on available API keys; override via `defaultTest.options.provider`; guidance to layer deterministic assertions (e.g. `is-json`) before judges and to calibrate judges on labeled examples. — [promptfoo: llm-rubric](https://www.promptfoo.dev/docs/configuration/expected-outputs/model-graded/llm-rubric/); [promptfoo: LLM as a judge](https://www.promptfoo.dev/docs/guides/llm-as-a-judge/)
- OpenAI `seed`: "best effort" deterministic sampling; `system_fingerprint` identifies backend config and changes a few times a year; outputs "mostly" identical; must hold seed, messages, temperature/top_p, max_tokens constant; cookbook is archived and references 2023 models. — [OpenAI Cookbook: Reproducible outputs with seed](https://developers.openai.com/cookbook/examples/reproducible_outputs_with_the_seed_parameter)
- Anthropic structured outputs: `output_config.format: {type: "json_schema", schema}` (old `output_format` deprecated; beta header `structured-outputs-2025-11-13` only for legacy param); strict tool use `strict: true`; constrained decoding guarantees schema conformance (no parse errors/retries) except on `stop_reason: "refusal"` or `max_tokens` truncation; enum casing may change; required properties emitted first; JSON-schema subset (no recursive schemas, numeric/length constraints, `additionalProperties` must be `false`); limits 20 strict tools/request, 24 optional params, 16 union params; grammar compiled with 24h cache and 180s compile timeout; changing format invalidates prompt cache; supported on Claude Fable 5.1/5, Opus 5.5/5/4.8/4.7/4.6/4.5, Sonnet 5.5/5/4.6/4.5, Haiku 5.5/4.5. The page does not claim determinism of content. — [Anthropic: Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Secondary sources (prep sites/blogs) quote Anthropic that even at temperature 0 results "will not be fully deterministic and identical inputs may produce different outputs across API calls," and report that some newer adaptive-thinking Claude models return HTTP 400 for non-default temperature/top_p/top_k — conflicting accounts; treat as unverified. — [claudearchitectcertification: LLM fundamentals](https://claudearchitectcertification.com/concepts/llm-fundamentals-tokens-and-sampling.md); [TokenMix: Claude temperature control 2026](https://tokenmix.ai/blog/claude-temperature-control-2026)
- Claude Code `--json-schema` gives schema-validated `structured_output` after the agent finishes; `--bare` and `--restricted` exist for reproducible CI/eval-harness runs; `--system-prompt-snapshot` records the system prompt on first request for stable resumed runs. — [Claude Code: CLI reference](https://code.claude.com/docs/en/cli-reference); [headless](https://code.claude.com/docs/en/headless)
- Codex `--output-schema` validates final output against a JSON schema. — [Codex CLI reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli)
- AgentKit code-based routers "involve no LLM calls, so decisions are not subject to model variation." — [AgentKit: Routers](https://agentkit.inngest.com/concepts/routers)
- Durable engines' replay/determinism: Temporal replay testing to verify patches; DBOS raises `DBOSStepNondeterminismError` if a replay diverges; Restate seeds `ctx.rand`/`ctx.date` per invocation. — [Temporal versioning](https://docs.temporal.io/develop/python/versioning); [DBOS workflows](https://docs.dbos.dev/python/tutorials/workflow-tutorial); [Restate durable steps](https://docs.restate.dev/develop/ts/durable-steps)

### Inferences
- "Golden runs" for coding-agent pipelines are best realised as experiments in Braintrust/LangSmith (immutable, comparable, with traces attached) or as promptfoo evals tagged with `git.sha`, gated by deterministic checks (compile/tests/diff-size per Augment) before LLM-judge rubrics; repeated trials are needed because none of the vendors promise identical outputs.
- Determinism stack ordering, from strongest to weakest: deterministic routing/code in the orchestrator → journaled replay of recorded outputs → schema-constrained outputs → seed/temperature.

- Braintrust trial-count/repetition options and LangSmith's repetition setting were not on the fetched pages.
- No official Anthropic statement on temperature determinism was retrieved (only secondary quotes).

## KQ6 (brief item e). Audit/compliance expectations for autonomous agents acting on code (approval logs, provenance, SLSA-like attestations, signed artifacts)

### Takeaway
There is no GitHub-native attestation that a commit was authored by an AI agent; build provenance (GitHub Artifact Attestations: in-toto/SLSA predicate signed via Sigstore; SLSA Build L2 by default, L3 with reusable signing workflows) covers what CI built from a commit, not who/what authored it. The emerging pattern is a separate signed "agent run" record (e.g. `agentattest`'s in-toto Statement v1 binding run id, patch digest, PR, approval state, config digests, and trace IDs), plus the approval/permission logs that Claude Code already emits (`tool_decision` events, `permission_denials` in results, `tool.blocked_on_user` spans).

### Cited Findings
- GitHub Artifact Attestations (blog Dec 19–20, 2024): a "cryptographic record generated for each artifact," signed with GitHub-run Sigstore infrastructure (GitHub as root CA); SLSA Level 1 = generating provenance; Level 2 by default on GitHub-hosted runners; Level 3 by generating provenance via a reusable workflow that separates signing from the build job; verify with `gh attestation verify`. — [GitHub Blog: Reach SLSA Level 3 with Artifact Attestations](https://github.blog/enterprise-software/devsecops/enhance-build-security-and-reach-slsa-level-3-with-github-artifact-attestations/)
- Search summary: attestations identify an artifact by SHA-256 digest linked to workflow run, repository and commit; format is in-toto with a SLSA build-provenance predicate; the `actions/attest-build-provenance` action generates them; `slsa-verifier` verifies SLSA provenance. Sources disagree on default level (GitHub: L2 default; some posts claim L3). — [actions/attest-build-provenance](https://github.com/actions/attest-build-provenance); [slsa-verifier](https://github.com/slsa-framework/slsa-verifier); [Tenki: GitHub Artifact Attestations SLSA](https://tenki.cloud/blog/github-actions-artifact-attestations-slsa)
- `agentattest` (v0.1.0 tagged; Go ≥1.25; Apache 2.0; fork with 0 stars — early-stage): emits an in-toto Statement v1 with `predicateType` `https://agentattest.dev/predicate/v0` or `/v1`; required fields `predicateVersion`, `runId`, `verificationLevel`, `repo` (URL, base commit, `pullRequest.number`), `agent`, `environment`, `humanApproval` (`state` e.g. `approved-after-generation`; high-assurance requires `approved-before-merge` digest), `privacy` (raw prompts not stored: `rawPrompt.stored=false`), `timestamps`, `evidence`; subject is `patch.diff` SHA-256 plus per-file hashes; v1 adds `agentConfig` (digest of AGENTS.md), `mcpServers`/`tools` schema digests, `delegation`, `capture`, `--model-provider`/`--model-id`; optional `runtime` field holds OpenTelemetry/OpenInference trace IDs by URI+digest (required under `harness-native` capture). Signing delegated to DSSE/Sigstore/cosign/Fulcio/Rekor/GitHub attestation bundles; verify pipeline: Go pre-schema gate → JSON Schema 2020-12 → CUE → OPA Rego policy (subjects, repo/base match, identity, level, privacy, replay, freshness) → failure codes; evidence levels: local runs cap at "evidence-grade", "policy-grade" needs verified non-local builder/signer, "high-assurance" needs isolated runners, witnesses, protected merges; `agent.name`/`model.name` are self-asserted metadata, not trust roots. — [agentattest README](https://github.com/BlockTarioIQ/agentattest)
- Claude Code approval/permission audit signals: `claude_code.tool_decision` events (`decision` accept/reject; `source` config/hook/user_permanent/user_temporary/user_abort/user_reject; `tool_source` builtin/mcp), `claude_code.code_edit_tool.decision` metric, `permission_mode_changed` and `auth` events; managed settings can lock the OTel destination so audit telemetry can't be redirected. — [Claude Code: Monitoring](https://code.claude.com/docs/en/monitoring-usage)
- Claude Code headless: `--permission-prompts none` denies unanswerable prompts and lists them in the result's `permission_denials` (stream-json shows `permission_denied` system messages); `--restricted` mode for eval harnesses on shared machines; `--bare` avoids running repo hooks/MCP from untrusted folders; `-p` runs show no workspace-trust dialog, so repo-supplied hooks/MCP run unless `--bare`. — [Claude Code: headless](https://code.claude.com/docs/en/headless)
- Fiddler's Claude Code span model records permission decisions with source and wait time (`tool.blocked_on_user` span). — [Fiddler: Claude Code integration](https://docs.fiddler.ai/integrations/agentic-ai/claude-code-integration)
- Durable engines as audit logs: Temporal's Event History records every command/marker (patch markers, activity inputs/results; MCP `factory_argument` is "stored in Workflow history," hence keep secrets out); Restate journals every `ctx.run` result; DBOS persists steps/messages/events in Postgres; Step Functions redrive tracks retry attempts in console. — [Temporal OpenAI Agents integration](https://docs.temporal.io/develop/python/integrations/openai-agents); [Restate durable steps](https://docs.restate.dev/develop/ts/durable-steps); [DBOS workflows](https://docs.dbos.dev/python/tutorials/workflow-tutorial); [AWS error handling](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)
- Noqta's comparison recommends Temporal "for audit-critical workflows" (vendor-adjacent opinion). — [Noqta comparison](https://www.noqta.tn/blog/durable-execution-ai-agents-inngest-trigger-temporal-2026)

### Inferences
- A compliance-ready pipeline record for an agent step would combine: (1) the orchestrator's journal (inputs, attempts, outputs, approvals with timestamps), (2) the agent's own decision log (Claude Code `tool_decision`/`permission_denials`), (3) a signed statement binding run id → patch digest → PR → approval state → config/MCP digests → trace ids (agentattest-style), and (4) standard build provenance for the resulting artifacts (GitHub attestations / SLSA). Items 1–2 are available today; 3 is pre-1.0 tooling; 4 is mature.
- Because Temporal/Restate/DBOS histories persist step inputs/outputs, prompts and tool arguments passed through them become part of the audit record — privacy redaction must happen before journaling (consistent with agentattest's "digests not raw prompts" and Claude Code's redaction-by-default).

### Gaps
- No standards body document (SLSA, OpenSSF, NIST) specifically addressing AI-agent authorship/approval attestations was found in this pass; agentattest is a single early-stage project.
- Codex CLI's approval-log/export format was not retrieved.
