As of October 2026 no shipping product models what the brief describes: a versioned graph whose nodes are full coding-agent sessions with per-node presets of skills, subagents, hooks and MCP, approval gates between stages, retries of nodes and sub-graphs, typed artifacts on edges and pluggable runtimes. The market has split into three layers that do not meet. Classic and durable orchestrators (Airflow 3.3, Prefect/Dagster, Flyte 2, Kestra 2.0, Temporal, Inngest, Restate, DBOS) have DAGs, retries and human-in-the-loop primitives but treat an "agent" as an LLM tool-calling loop inside one task; model-vendor runtimes (Claude Code dynamic workflows and Routines, Claude Managed Agents, Codex cloud, Cursor Cloud Agents, Jules, Devin) run session-shaped work with sandboxes and, in Anthropic's case, dollar budgets, but offer no cross-session DAG and no mid-run approval between stages; and a tracked list of roughly 260 "run many Claude Codes" tools consists mostly of kanban, worktree and tmux managers in which DAG plus typed artifacts plus approvals appears only in solo-maintained open source ([awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators)). The phrase "Airflow for agents" is literally occupied by Airflow's own `common-ai` provider and by the Prefect–Dagster merger narrative, yet nobody owns it as a brand. The richest precedents to mirror are Airflow's `@task.<flavor>` DSL with versioned JSON serialization and layered `client_defaults`; GitHub Agentic Workflows' frontmatter-to-`.lock.yml` compile step with a per-field merge table; Claude Code's subagent frontmatter as the per-node preset vocabulary; the universal durable-step retry contract shared by Temporal, Restate, DBOS and Step Functions; Argo's `suspend`/`requeue`/artifact-repository trio; and the only two first-class dollar budgets in the field (`claude --max-budget-usd` and Managed Agents' session `budget`). The pain points the product must address are quantified: human review is the throughput ceiling (PR merge time **+49%**, AI-authored PRs wait **4.6×** longer), cost is opaque and bursty (Bun's Zig-to-Rust port consumed roughly **$165,000** of tokens), flaky verification poisons retry loops, and a "green" run does not mean the task succeeded. The genuinely open design space is sub-graph retry, cost as a scheduling constraint, artifact types with lineage, stage-level (not tool-level) approvals and per-attempt diff history, none of which any surveyed system ships.

## Three layers that never meet, and a brand nobody owns

The literal "Airflow for agents" is Apache Airflow itself. The `apache-airflow-providers-common-ai` package (0.1.0, announced April 2026, built on Pydantic AI with 20+ providers) adds `@task.llm`, `@task.agent` and `@task.llm_branch`, and its `HookToolset` lets an agent call existing Airflow connections as tools rather than standing up MCP servers ([Airflow common-ai provider blog](https://airflow.apache.org/blog/common-ai-provider/)). Astronomer defines "agent orchestration" as a model-and-tool loop that runs as a single Airflow task where "neither the number of model calls nor the sequence of actions is known before the task runs" ([Astronomer docs](https://www.astronomer.io/docs/learn/ai-orchestration-agent)). That is the ceiling of the classic layer: the agent is a task body, not a sandboxed coding session with a repo, a branch and a PR. Prefect's announced acquisition of Dagster Labs on **July 13, 2026** is the loudest signal that the data-orchestrator category is pivoting toward agents, but it is a strategy statement; Dagster stays a separate product and no shipped feature schedules coding-agent sessions ([Dagster blog](https://dagster.io/blog/prefect-is-acquiring-dagster); [Dagster customer FAQ](https://dagster.io/dagster-customer-faq)). Kestra 2.0 ships an `AIAgent` task with tools, MCP, memory and RAG, and Flyte 2 ships a `flyte.ai.agents.Agent` harness with tools, MCP servers, skills and per-tool approval, but both remain "LLM loop as a task" ([Kestra plugin-ai](https://kestra.io/plugins/plugin-ai); [Flyte Agent API](https://www.union.ai/docs/v2/flyte/api-reference/flyte-sdk/packages/flyte.ai.agents/agent/)).

"Kubernetes for agents" is press framing attached to Steve Yegge's Gas Town, whose own page only says its role names "map well to Gas Town's Kubernetes-like orchestration shape"; the system is a work ledger (Beads), long-lived worker identities (Polecats), a stuck-agent monitor (Witness) and a Bors-style merge queue (Refinery), with tmux as the primary UI ([yegge.ai/gastown](https://yegge.ai/gastown); [gastown](https://github.com/steveyegge/gastown)). Its successor Gas City (April 2026) is the only tool in this layer advertising pluggable "runtime providers" (tmux, subprocess, exec, ACP, Kubernetes), with a declarative `city.toml`, and its Hacker News reception was "overwhelmingly skeptical" ([rywalker.com](https://rywalker.com/research/gas-city)). "CI for agents" in 2026 means agents as CI jobs: GitHub Agentic Workflows compiles Markdown into pinned GitHub Actions, runs the agent read-only by default, applies writes through declared "safe outputs" in a separate job, and caps spend at **1,000 AI credits per run and 5,000 per workflow per day** by default ([gh-aw site](https://github.github.com/gh-aw/)). It supports Copilot, Claude, Codex, Gemini and Pi as engines but documents one agent job per workflow, not chained agent jobs with typed artifacts ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/about-github-agentic-workflows)).

The vendor runtimes are session-shaped by construction. Claude Code Routines each create an independent session, "Claude Code doesn't reuse sessions across events", there is no permission-mode picker, and "a green status in the run list ... does not mean the task in your prompt succeeded" ([Routines](https://code.claude.com/docs/en/routines)). Claude Code's dynamic workflows are the closest vendor artifact to a pipeline (a JavaScript script with `agent()`, `parallel()`, `pipeline()`, `phase()`), yet they allow "No mid-run user input", replay from the first failed agent, and have no persisted DAG outside the session directory ([Workflows](https://code.claude.com/docs/en/workflows)). Managed Agents (beta header `managed-agents-2026-04-01`) exposes sessions, events, server-executed `workflow_run.*` phases and a server-enforced budget, but delegation is "one level deep" with a 25-child-thread limit and approvals exist only as per-tool-call `user.tool_confirmation` events ([Managed Agents multiagent orchestration](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration); [Managed Agents reference](https://platform.claude.com/docs/en/managed-agents/reference)). OpenAI's Symphony, the closest thing to a published orchestration spec from a model vendor, explicitly lists as non-goals "A general-purpose workflow engine or distributed job scheduler" and "Durable state: there is no database, and restarts do not restore retry timers or running sessions" ([Symphony SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md)). OpenAI's visual Agent Builder is being shut down on **November 30, 2026** ([OpenAI Agent Builder docs](https://developers.openai.com/api/docs/guides/agent-builder)).

The third layer is crowded and thin. Paperclip (~102k stars) models an org chart with heartbeats, review stages and company/agent/project budgets whose enforcement "relies on recorded spend, so usage reporting and in-flight work can delay a stop"; pipelines are "experimental" ([Paperclip](https://github.com/paperclipai/paperclip)). Augment Code's review of nine open-source orchestrators finds a task graph with a deterministic scheduler only in Bernstein (49 adapters, solo-maintained, single-host), milestone gates in Agent Orchestrator where agents "idled 90+ s waiting on tool approval", and 34 CLI providers but no coordination in Emdash; Vibe Kanban's maker shut down on April 10, 2026 ([Augment Code](https://www.augmentcode.com/tools/open-source-agent-orchestrators)). Pluggable agent runtimes are becoming table stakes in this layer (Bernstein 49, Emdash 34, Paperclip 10+, gh-aw 5+), so single-vendor lock-in is a weakness chiefly of the vendor-native schedulers.

## Orchestrators and durable engines converge on one step contract and three approval shapes

Every mature orchestrator has pluggable compute behind a small base class, and the verb set is the same across all of them: submit, poll, cancel, adopt after restart, logs, heartbeat. Airflow's custom executor must implement `sync`, `execute_async` and `_process_workloads`, optionally `start`, `end`, `terminate`, `try_adopt_task_instances`, `get_cli_commands` and `get_task_log`, and declares capability flags (`supports_pickling`, `is_local`, `is_single_threaded`, `is_production`, `serve_logs`); the workload it receives is an `ExecuteTask` DTO carrying `token`, a `TaskInstanceDTO`, `dag_rel_path`, `bundle_info` and `log_path`, which cleanly decouples the executor from the task's code ([Airflow Executor docs 3.3.1](https://airflow.apache.org/docs/apache-airflow/3.3.1/core-concepts/executor/index.html)). Prefect's `BaseWorker` needs only `type`, a Pydantic `job_configuration` and `async run(flow_run, configuration, task_status) -> BaseWorkerResult`, with `kill_infrastructure(infrastructure_pid, configuration, grace_seconds=30)` for cancellation; the same Pydantic model doubles as the base job template's JSON schema, so Docker and Kubernetes workers differ only in config fields and the `run()` body ([Prefect custom worker](https://docs.prefect.io/v3/advanced/developing-a-custom-worker); [prefect.workers.base](https://docs.prefect.io/v3/api-ref/python/prefect-workers-base)). Dagster's `RunLauncher` is `launch_run(context)` plus `terminate(run_id) -> bool`, with opt-in `check_run_worker_health` returning `WorkerStatus` of `RUNNING, NOT_FOUND, FAILED, SUCCESS, UNKNOWN` and `resume_run(context)` ([dagster launcher/base.py](https://github.com/dagster-io/dagster/blob/master/python_modules/dagster/dagster/_core/launcher/base.py)). The smallest complete protocol found is Argo's executor plugin: one HTTP endpoint, `POST /api/v1/template.execute`, returning `{node: {phase: Succeeded|Failed|Pending|Running, message, outputs}, requeue: "2m"}`, where `requeue` with a `Pending`/`Running` phase is the poll loop and `{}` means "cannot execute this template" ([Argo executor plugins](https://argo-workflows.readthedocs.io/en/latest/executor_plugins/)). For hour-long sessions this controller-driven re-invocation model fits better than holding a worker slot.

Durable-execution engines converge even more tightly. Temporal, Inngest, Restate, DBOS, Hatchet, Trigger.dev, Cloudflare and Step Functions all define the same contract: a deterministic orchestrator function plus named side-effecting steps whose results are journaled so they are not re-executed on replay, per-step retry configured as `{initial interval, backoff factor, max interval, max attempts or max duration, non-retryable error class, per-attempt timeout}`, and long waits modelled as durable timers, signals or task tokens. Temporal's defaults are initial 1 s, coefficient 2.0, max interval 100× initial, unlimited attempts; Activities retry by default and Workflows do not ([Temporal retry policies](https://docs.temporal.io/encyclopedia/retry-policies)). Every one of them says the same thing about LLM calls: a model call is a non-deterministic side effect, so it goes inside a step, never in orchestrator code. Temporal's OpenAI Agents integration does exactly this ("Model Activities retry durably and are not repeated during replay"), with `activity_as_tool()` for I/O tools and `@function_tool` restricted to deterministic logic, and it explicitly excludes `LocalShellTool` and `ComputerTool`, so shell-heavy coding agents must run as ordinary long Activities ([Temporal OpenAI Agents SDK integration](https://docs.temporal.io/develop/python/integrations/openai-agents)). The practical consequence for a coding-agent pipeline is that two durability granularities exist: one Activity per model/tool call (full replay, requires a workflow engine in the loop) or one long Activity per agent subprocess with heartbeats carrying progress payloads (simpler, loses intra-session replay). Serverless-step engines constrain the second option hard: Inngest caps a step at **2 hours and 4 MiB** of output, Cloudflare at **30 minutes and 1 MiB** ([Inngest steps](https://www.inngest.com/docs/features/inngest-functions/steps-workflows); [Cloudflare Agents run workflows](https://developers.cloudflare.com/agents/api-reference/run-workflows/)).

The classic orchestrators are all patching the same hole, which Astronomer names candidly: pre-3.3 Airflow "could not survive a crash inside a long running task, so a job that died at minute forty of a fifty minute run started again at minute zero", and an agent whose 20th call times out "pays for all nineteen again"; with 3.3 "Airflow's durability boundary moves down a level, from between tasks to inside one" via a per-task-instance key-value state store (AIP-103) that survives retries, while XCom is still cleared on every retry ([Astronomer durable execution post](https://www.astronomer.io/blog/durable-execution-with-apache-airflow.md); [Airflow XCom docs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/xcoms.html)). The `durable=True` mode on `@task.agent` keys a cache entry by request fingerprint so a matching request replays and a mismatch re-runs live, guaranteeing "a side-effecting tool runs at most once per completed step", but it cannot be combined with `enable_hitl_review=True` and disables streaming ([Pydantic AI Airflow durable execution](https://pydantic.dev/docs/ai/integrations/durable_execution/airflow/)). Flyte 2 gets the same effect from `@flyte.trace` checkpoints; Prefect and Dagster re-execute the whole task body on retry. The design lesson is to make per-step memoization of LLM and tool calls a core primitive and to separate "outputs" (edge payloads) from "checkpoint state" (intra-node scratch that survives retry).

Human-in-the-loop primitives come in three recurring shapes, and a pipeline product needs two of them. The first is a gate task with a typed form, timeout and default: Airflow 3.1's `HITLOperator`, `ApprovalOperator`, `HITLBranchOperator` and `HITLEntryOperator` take `subject`, `body`, `options`, `defaults`, `assigned_users` ("ONLY the users within this list will be allowed to respond"), `notifiers` and a response timeout, and in 3.3 the task enters an `awaiting_input` state that "uses neither a worker slot nor the triggerer" ([Airflow HITL tutorial](https://airflow.apache.org/docs/apache-airflow/3.1.3/tutorial/hitl.html); [Airflow Tasks docs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/tasks.html)). Kestra's `Pause` task adds `onResume` typed inputs and a `behavior` on expiry of `RESUME`, `WARN`, `FAIL` or `CANCEL` ([Kestra Pause task](https://kestra.io/plugins/core/flow/io.kestra.plugin.core.flow.pause)). The second shape is a pause inside imperative code that returns a typed value: Prefect's `pause_flow_run(wait_for_input=UserInput)` with a `RunInput` Pydantic subclass rendered as a form, Temporal's `@workflow.signal` plus `workflow.wait_condition(..., timeout=)`, Mastra's `suspend()` with `suspendSchema`/`resumeSchema`, ADK's `RequestInput(payload=, response_schema=)` and Microsoft Agent Framework's `ctx.request_info(request_data=, response_type=)` ([Prefect interactive workflows](https://docs.prefect.io/v3/advanced/interactive.md); [Temporal HITL cookbook](https://docs.temporal.io/ai/cookbook/human-in-the-loop-python.md); [Mastra HITL](https://mastra.ai/docs/workflows/human-in-the-loop); [ADK human input](https://adk.dev/graphs/human-input/); [MAF HITL](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop)). The third shape is per-tool approval inside the agent loop: OpenAI's `@tool(needs_approval=True)` with `RunState.approve/reject`, Pydantic AI's `requires_approval=True` with `DeferredToolRequests`, Flyte's `requires_approval`, and Managed Agents' `user.tool_confirmation` ([OpenAI Agents SDK HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/); [Pydantic AI deferred tools](https://pydantic.dev/docs/ai/deferred-tools/)). Re-execution semantics on resume differ and matter for side effects: LangGraph re-runs the node from the top, so "Code before `interrupt()` must therefore be idempotent" ([LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)); ADK leaf nodes complete with the reply unless `rerun_on_resume=True` ([ADK dynamic workflows](https://adk.dev/graphs/dynamic/)); OpenAI and Pydantic AI start a new run with history. A graph product should ship the gate-task shape for stage approvals and delegate per-tool approval to the harness's own permission system.

The agent-graph frameworks add one structural lesson and one warning. The lesson is that "agent as node" is now table stakes: ADK 2.0 passes an `LlmAgent` directly as a graph node and calls it via `ctx.run_node()`; MAF has `AgentExecutor` and the inverse `Workflow.as_agent()`; CrewAI runs a whole `Crew.kickoff()` inside a `@listen` step; LangGraph composes subgraphs and Deep Agents as nodes ([ADK graphs](https://adk.dev/graphs/); [MAF workflow concepts](https://learn.microsoft.com/en-us/agent-framework/concepts/workflows/); [CrewAI Flows](https://docs.crewai.com/en/concepts/flows)). The warning is that fine-grained graphs are the wrong layer for open-ended reasoning. Practitioners describe a NestJS workflow engine that reached "8,692 lines of code spread across three executor layers" with a one-node graph ([braindetox.kr](https://braindetox.kr/en/posts/langgraph_complexity_lesson_2026.html)), and argue that business-process control needs "typed state, guards, retries, and audit trails" in a separate process engine where agents "choose from declared exits, never invent them" ([ebarroca.substack.com](https://ebarroca.substack.com/p/langgraph-control-flow-is-not-the-main-problem)). An arXiv catalogue of 63 budget-overrun incidents finds that LangGraph's `recursion_limit`, CrewAI's `max_iter` and AutoGen's `max_consecutive_auto_reply` "are structural step counters, not dollar-cap mechanisms" that operators nonetheless mis-deploy as cost proxies ([arXiv 2606.04056](https://arxiv.org/pdf/2606.04056)). Airflow's `@task.llm_branch`, where the model picks from "a constrained enum built from the task's downstream IDs", is the idiom that keeps a static graph intact while letting the model choose the path ([Airflow common-ai provider blog](https://airflow.apache.org/blog/common-ai-provider/)).

## Case studies quantify a review ceiling, cost opacity and flaky gates

Across Google, Airbnb, Anthropic, Dropbox, Stripe and Uber the published pipeline shape is strikingly uniform: deterministic targeting and queueing, a bounded per-unit agent retry loop, cheapest-first mechanical gates (parse, build, tests, sometimes 100+ CI runs), batched human review, and slow manual rollout. Google's FSE 2025 migration paper reports **74.45% of 595 changes LLM-generated** but only **35.97% untouched by humans**; its validation ladder runs Success → Whitespace → AST parse → "Punt" → Build → Tests, and it generates three attempts per file at temperature 0.0, picking one success at random ([arXiv HTML](https://arxiv.org/html/2504.09691v1)). Airbnb's Enzyme-to-RTL migration treated each of ~3,500 test files as an independent unit in a step-based state machine, re-prompted with all errors up to 10 iterations, migrated **75% of files in four hours** and reached **97%** after "sample, tune, sweep"; the authors conclude "retrying beat better prompting" ([InfoQ](https://www.infoq.com/news/2025/03/airbnb-llm-test-migration/)). Anthropic's Bun port moved ~1M lines in under two weeks at roughly **5.9B uncached input tokens and $165,000** at API pricing, using fan-out translation batches with two adversarial reviewers and a tie-breaker, deterministic scripts for dependency mapping and queue management ("output file exists" = done), and the advice to "front-load human effort on the rulebook and stress test; the rest is mostly queues" ([claude.com blog](https://claude.com/blog/ai-code-migration)). Dropbox's Nova platform gives each session an isolated sandbox at a specific commit, feeds failed validation back up to a max iteration count, validates flaky-test fixes with 100+ CI runs capped at five attempts, and draws the lesson "Not every step belongs inside the agent loop": trigger CI deterministically and bring the agent back on failure, because letting agents manage test execution "could leave sessions waiting for hours or validate against the wrong tests" ([Dropbox Tech](https://dropbox.tech/machine-learning/introducing-nova-our-internal-platform-for-coding-agents)). Stripe's Minions ship **over 1,300 PRs per week** from code-defined "blueprints" that mix deterministic routines with agent loops, and "All changes are human-reviewed but contain no human-written code" ([InfoQ](https://infoq.com/news/2026/03/stripe-autonomous-coding-agents/)). Every one of these companies built that shape bespoke, which is the strongest demand signal in the notes for a reusable layer whose artifacts are target list → candidate diff → validation report → approved changeset → rollout record.

The best-measured pain point is the human review ceiling. A Harvard job-market paper using ~300M Jellyfish work events across 718 firms finds that after adopting Claude Code, Cursor or Devin-class tools, lines of code per worker rose ~30% and PRs +23%, but completed epics did not rise significantly while **PR submit-to-merge time rose 49%** and revision requests nearly doubled ([AI Weekly summary](https://aiweekly.co/alerts/harvard-study-ai-coding-agents-lift-code-30-shipped-output-flat), secondary coverage of the paper). LinearB and Opsera independently report that AI-generated PRs **wait 4.6× longer** for review ([LinearB](https://linearb.io/state-of-software-delivery-2025/)). Simon Willison states the constraint directly: "the natural bottleneck on all of this is how fast I can review the results" ([simonwillison.net](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)), and Hacker News threads refine it to unstructured review and "architectural drift" when parallel agents rename the same type differently, which worktrees do not solve ([HN](https://news.ycombinator.com/item?id=45489884)). Both review and cost are aggregation problems across many sessions, which is precisely what a session-level product cannot see and a DAG-level product with per-node budgets, batched review and scoped nodes can.

Cost opacity is the second pain. Cost spikes come from many short sessions each reloading full context without cache hits, and compaction and retry loops are invisible without tooling ([Tribe.ai OTel guide](https://www.tribe.ai/applied-ai/a-quickstart-to-measuring-the-return-on-your-claude-code-investment)); XTrace's illustrative figure is a 150k-token context resent 40 times costing roughly $3 warm versus $30 cold at Opus 5 list price, and it argues the headline metric should be cost per accepted ticket including failed attempts, retries and subagents ([XTrace](https://xtrace.ai/blog/coding-agent-observability)). Durable engines meter on units that multiply inside agent loops ([WeTheFlywheel](https://wetheflywheel.com/en/comparisons/temporal-vs-inngest/), secondary). Flaky verification is the third: "Flaky Tests Poison Agent Loops Faster Than They Ever Hurt Humans" ([tianpan.co](https://tianpan.co/blog/2026/07/02/flaky-tests-poison-agent-loops)); Google's migrations were blocked by pre-existing test failures and developers "couldn't predict how many retries to try before switching to manual work" ([arXiv HTML](https://arxiv.org/html/2504.09691v1)); Thoughtworks Radar vol. 34 names the themes "putting coding agents on a leash" and "feedback sensors for coding agents", recommending compilers, linters, type checkers, mutation testing and fuzzers wired in as deterministic gates ([Thoughtworks](https://www.thoughtworks.com/insights/podcasts/technology-podcasts/themes-technology-radar-34)). Fourth is observability: coding agents "fail silently through loops, context loss, and tool misuse", and Fiddler's documented Claude Code span model carries model, tokens, tool names and permission decisions but not response content, thinking, cost or trace propagation to providers ([Fiddler](https://www.fiddler.ai/blog/coding-agent-observability); [Fiddler Claude Code integration](https://docs.fiddler.ai/integrations/agentic-ai/claude-code-integration)). An independent study of 20,574 real coding-agent sessions finds **91.49%** of visible resolutions still require explicit user correction ([arXiv 2605.29442](https://arxiv.org/abs/2605.29442)). Fifth is environment friction: worktrees lack untracked `.env` files, shared databases and ports collide, and Uber pre-provisions Kubernetes "balloon pods" with repo snapshots so agents never prepare workspaces from scratch ([HN](https://news.ycombinator.com/item?id=45489884); [ZenML summary](https://www.zenml.io/llmops-database/building-a-managed-software-factory-with-agentic-ai)). Sixth is security: `claude -p` without `--bare` "runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted" ([Headless docs](https://code.claude.com/docs/en/headless)), and the field's response is read-only-by-default agents with safe outputs, credential proxies and firewalls ([gh-aw site](https://github.github.com/gh-aw/)).

The framing consensus is the determinism-plus-agent split. Anthropic's "Building effective agents" distinguishes workflows ("orchestrated through predefined code paths") from agents and warns agents "cost more in latency and money and can compound errors" ([Anthropic](https://www.anthropic.com/research/building-effective-agents)); 12-Factor Agents argues for "Own your control flow", "Launch/Pause/Resume with simple APIs" and "Make your agent a stateless reducer" ([humanlayer/12-factor-agents](https://github.com/humanlayer/12-factor-agents)); Bernstein's design has "no model in the coordination loop" ([awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators)). The product's job is to be that deterministic outer loop.

## Six gaps no shipping system fills

The first gap is the brief's core object. No system in any layer ships a persisted DAG whose nodes are full coding-agent sessions with typed edges, stage approvals and per-node retry; the vendor layer has "one prompt → one session → one PR", the orchestrator layer has "LLM loop as one task", and the OSS layer has task lists, org charts and merge queues. Claude Code's agent teams, the nearest in-harness analogue, have tasks with dependencies but "No session resumption with in-process teammates", "One team per session", and "In non-interactive mode with the `-p` flag, including Agent SDK sessions, Claude doesn't spawn teammates" ([Agent teams](https://code.claude.com/docs/en/agent-teams)).

The second is sub-graph retry. No orchestrator in the notes treats "retry this group of nodes" as first-class: Airflow's docs cover task-level `retries` and AIP-105 policies but not TaskGroup retry; Prefect has flow-level `retries`; Temporal's closest analogue is a child workflow; Kestra's `Subflow` has `transmitFailed` ([Airflow Tasks docs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/tasks.html); [Kestra Subflows](https://kestra.io/docs/workflow-components/subflows)). The case studies, however, retry *units* (a file, an issue) through multi-step validation ladders, which is exactly a sub-graph retry with a rollback of intermediate artifacts.

The third is cost as a scheduling constraint. Only Claude Code (`--max-budget-usd`, a client-side estimate that "can pass the cap") and Managed Agents (a server-enforced list-cost `budget` that pauses the session with `stop_reason: budget_reached`) enforce dollar limits; Airflow lists "AIBudget" as future work, Kestra and Flyte expose token counts or `max_turns`, and Codex `exec --json` emits only a per-turn token triple with no USD ([CLI reference](https://code.claude.com/docs/en/cli-reference); [Budgets](https://platform.claude.com/docs/en/managed-agents/budgets); [Codex exec JSONL reference](https://codex.danielvaughan.com/2026/04/08/codex-exec-jsonl-reference/)). No system uses a budget to decide *whether to schedule* a node, to pick a model tier, or to stop a fan-out early.

The fourth is an artifact type with lineage. Graph frameworks pass typed in-memory state (TypedDict with reducers, Pydantic `Flow[State]`, zod schemas, typed handler messages); files are either serialized into state, referenced by path in a shared sandbox filesystem (Managed Agents, Deep Agents, Agent SDK), or kept in an external store ([LangGraph durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution); [Managed Agents multiagent](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration)). Workflow engines have artifacts but no types beyond a path and an archive mode. Claude Code's `result` object has no "files changed" field; it must be derived from git or `PostToolUse` hooks, and Anthropic warns that transcript JSONL "changes between versions, so scripts that parse these files directly can break on any release" ([Sessions](https://code.claude.com/docs/en/sessions)). A PR-diff-plus-build-log-plus-validation-report artifact contract has to be defined by the product.

The fifth is stage-level approval in agent runtimes and session-level resume in orchestrators. Vendor runtimes gate at tool-call granularity (Managed Agents `user.tool_confirmation`, Codex app-server `item/permissions/requestApproval`, Claude Code `--permission-prompt-tool`) or plan granularity (Jules `requirePlanApproval`), never between pipeline stages ([Codex app server](https://learn.chatgpt.com/docs/app-server); [Jules API](https://developers.google.com/jules/api)). Conversely no orchestrator HITL operator knows how to hand a reviewer's comment back into a *resumed* agent session; Airflow's `durable` and `enable_hitl_review` are mutually exclusive.

The sixth is observability and audit for the session as a unit. No vendor in the notes stores per-attempt code diffs alongside the trace, ingests the transcript as a first-class object, or links spend to tickets and PRs; XTrace proposes four layers (execution, harness, money, outcomes) and estimates an in-house build at 2–3 engineer-weeks ([XTrace](https://xtrace.ai/blog/coding-agent-observability)). The OTel GenAI conventions are still at "Development" stability, `invoke_workflow` exists only as an operation-name value without its own span table, and cost is not a semconv attribute ([semconv-genai agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)). Agent-authorship attestation exists only as the pre-1.0 `agentattest` in-toto predicate ([agentattest](https://github.com/BlockTarioIQ/agentattest)). Two smaller white spaces round this out: benchmark-driven selection among parallel hypotheses (Google's "3 attempts, pick one" and Anthropic's adversarial reviewers are the only published instances), and a documented recipe for wrapping a `claude -p` or `codex exec` subprocess as a durable activity, which no engine provides.

## Design precedents worth mirroring, with interface names and snippets

### Python DSL

Airflow's idioms have the widest recognition and the Airflow team itself extended them to agents. Mirror `from airflow.sdk import dag, task`, `a >> b >> [c, d]`, `default_args` propagated to all tasks, `TaskGroup` for nesting, and `.partial(y=10).expand(x=[1, 2, 3])` for fan-out with lazy mapped inputs ([Airflow Tasks docs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/tasks.html); [Task SDK dynamic task mapping](https://airflow.apache.org/docs/task-sdk/stable/dynamic-task-mapping.html)). Per-task runtime selection via `executor=` and `executor_config={"KubernetesExecutor": {"image": "myCustomDockerImage"}}` is the precedent for per-node runtime overrides ([Airflow Executor docs 3.3.1](https://airflow.apache.org/docs/apache-airflow/3.3.1/core-concepts/executor/index.html)). The `@task.<flavor>` namespace is the natural extension point for "agent as a task flavor":

```python
@task.agent(
    llm_conn_id="my_openai_conn",
    system_prompt="You are a SQL analyst. Use tools to answer questions with data.",
    toolsets=[SQLToolset(db_conn_id="postgres_default", allowed_tables=["customers", "orders"], max_rows=20)],
)
def analyze(question: str):
    return f"Answer this question about our data: {question}"
```

([Airflow common-ai provider blog](https://airflow.apache.org/blog/common-ai-provider/)). Flyte 2 contributes the cleanest config-layering story: `TaskEnvironment(name, image, resources, env_vars, secrets, cache, reusable, plugin_config, queue)` defaults → `@env.task(retries=3, timeout=60)` overrides → `task.override(...)` at call time, and "workflows are tasks that call other tasks", which suits agent-driven sub-graphs whose shape is only known at run time ([Union TaskEnvironment](https://www.union.ai/docs/v2/flyte/api-reference/flyte-sdk/flyte/taskenvironment/); [Union migration guide](https://docs.union.ai/docs/v2/byoc/api-reference/migration/tasks-and-workflows)). From Prefect take `task_run_name="hello-{name}-on-{date:%A}"` format strings and composable `cache_policy` (`INPUTS + TASK_SOURCE`) ([Prefect write-tasks](https://docs.prefect.io/v3/develop/write-tasks.md)); from Dagster `dg.RetryPolicy(max_retries=5, delay=0.2, backoff=dg.Backoff.EXPONENTIAL, jitter=dg.Jitter.PLUS_MINUS)` as the retry object shape ([Dagster defining assets](https://dagster.io/docs/guides/build/assets/defining-assets)); from pydantic-graph the trick that "The `run` return annotation defines outgoing edges" (`-> Increment | End[int]`) and free Mermaid rendering ([pydantic-graph](https://pydantic.dev/docs/ai/graph/graph/)); from Claude Code dynamic workflows the call shape `agent(prompt, {schema, model, isolation: 'worktree'|'remote', label, stallMs})` with `parallel()`, `pipeline()` and `phase()` ([Workflows](https://code.claude.com/docs/en/workflows)).

### YAML intermediate representation and compile step

Airflow is the only classic orchestrator with a documented, versioned, JSON-serialized static graph that the scheduler consumes without re-importing user code; since 3.1 the serialized DAG carries `__version` and optional `client_defaults`, and defaults resolve in the order schema defaults → client defaults → DAG `default_args` → mapped-operator partial args → explicit task values, which lets the Task SDK and server upgrade independently ([Airflow DAG serialization](https://airflow.apache.org/docs/apache-airflow/stable/administration-and-deployment/dag-serialization.html)). Mirror that root `version` field and that explicit precedence list. Windmill's OpenFlow is the closest general DAG IR: each module has `id`, `value`, `input_transforms` (`{type: static, value}` or `{type: javascript, expr}` over `results.<id>` and `flow_input`), `stop_after_if`, `skip_if`, `timeout`, `cache_ttl`, `continue_on_error`, `retry` (`constant`/`exponential` + `retry_if`) and `suspend` (`required_events`, `timeout`, `resume_form`, `user_groups_required`); module types include `flow` (subflow by `path`), `forloopflow` (`iterator`, `parallel`, `parallelism`, `skip_failures`), `branchone`/`branchall` and `aiagent` ([Windmill OpenFlow](https://www.windmill.dev/docs/openflow)):

```yaml
summary: Fetch data and notify
value:
  modules:
    - id: fetch_data
      value:
        type: rawscript
        language: bun
        content: !inline fetch_data.ts
        input_transforms:
          url: { type: javascript, expr: flow_input.url }
    - id: per_item
      value:
        type: forloopflow
        iterator: { type: javascript, expr: results.fetch_data }
        modules:
          - id: notify
            value:
              type: script
              path: f/folder/send_email
schema:
  type: object
  properties:
    url: { type: string }
```

([Windmill write-flow skill](https://tessl.io/registry/skills/github/windmill-labs/windmill/write-flow)). gh-aw supplies the compile discipline: `gh aw compile` runs parsing and validation, job construction, dependency resolution, action pinning and YAML generation; the `.lock.yml` carries a metadata header, a Mermaid dependency graph and pinned SHAs; frontmatter is embedded at compile time while the Markdown prompt body is loaded at runtime, so "Compilation is only required when changing frontmatter configuration", and lock files are written only when content changed ([gh-aw Compilation process](https://github.github.com/gh-aw/reference/compilation-process/)). Its documented per-field merge table for `imports:` (tools deep-merge, `allowed` arrays concatenated and deduped, `mcp-servers` imported-overrides-main, `env` main wins and duplicate keys across imports fail, `steps` prepended in dependency order, `post-steps` appended) is the model for preset inheritance ([gh-aw Imports reference](https://github.github.io/gh-aw/reference/imports/)). Kestra removed its three-level `pluginDefaults` in 2.0 ("Flows that contain a `pluginDefaults` block fail to parse after upgrading") in favour of explicit Policies with `override: true`, and DAG Factory's four-level precedence (DAG config > file `default` block > `default_args_config_dict` > hierarchical `defaults.yml`, nearest wins) shows the alternative; both argue for explicit, named layers with a documented order rather than implicit cascades ([Kestra plugin defaults](https://kestra.io/docs/workflow-components/plugin-defaults); [DAG Factory defaults](https://astronomer.github.io/dag-factory/latest/configuration/defaults/)). Further checklist items from the declarative-spec survey: publish a JSON Schema and reference it via a `$schema` key or `yaml-language-server` comment (Claude `plugin.json`, ADK `AgentConfig.json`, Codex `#:schema`); use stable string `id`s with expression references instead of positional edges; generate SDKs from the schema (Pulumi package schema, Flyte protobuf) rather than hand-port them; be lenient on unknown top-level keys and strict inside typed sub-objects, as Claude's plugin manifest is ([Claude Code plugin manifest reference](https://code.claude.com/docs/en/plugins-reference); [Pulumi Package Schema](https://www.pulumi.com/docs/iac/using-pulumi/pulumi-packages/schema/)). Dagster Components show how "Python class = schema, YAML = instance" works: a component adds `dg.Model` to get a Pydantic-generated YAML interface, with Jinja `{{ env.X }}` and a `post_processing` block for cross-cutting overrides ([Dagster creating a component](https://dagster.io/docs/guides/build/components/creating-new-components/creating-and-registering-a-component)). Keep three file classes distinct, as Windmill and gh-aw do: human-authored source, machine-generated lock files that are committed but never hand-edited, and secrets excluded from sync ([Windmill local development](https://www.windmill.dev/docs/advanced/local_development)). CDKTF's deprecation on December 10, 2025 is the cautionary case for a code-first layer over an IR someone else owns ([CDKTF architecture](https://developer.hashicorp.com/terraform/cdktf/concepts/cdktf-architecture)).

### Per-node preset vocabulary across harnesses

Claude Code's subagent frontmatter is the most complete per-node vocabulary found and should be the superset the IR targets: `name`, `description`, `tools`, `disallowedTools`, `model` (`sonnet|opus|haiku|fable|<id>|inherit`), `permissionMode`, `maxTurns`, `autoCompactWindow`, `skills` (preloaded), `mcpServers` (by name or inline), `hooks` (`PreToolUse`/`PostToolUse`/`Stop` scoped to the agent), `memory`, `background`, `omitClaudeMd`, `effort`, `isolation: worktree`, `initialPrompt`; inheritance rules are documented (tools inherit from parent minus a fixed set, `permissionMode` inherits unless the parent runs in `bypassPermissions`), and unrecognized fields are ignored without error ([Claude Code Subagents](https://code.claude.com/docs/en/sub-agents)). The same vocabulary is injectable per run without touching the repo: `claude --bare -p "..." --settings <file|json> --agents '<json>' --mcp-config ./mcp.json --strict-mcp-config --append-system-prompt-file ... --json-schema '{...}' --max-budget-usd 5.00 --max-turns 20 --permission-prompts none --output-format stream-json`, and `--bare` "is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release" ([CLI reference](https://code.claude.com/docs/en/cli-reference); [Headless docs](https://code.claude.com/docs/en/headless)). The Agent SDK `Options` mirror this (`maxTurns`, `maxBudgetUsd`, `permissionMode`, `allowedTools`, `mcpServers`, `agents`, `hooks`, `settingSources: []`, `resume`, `forkSession`, `outputFormat: {type:'json_schema', schema}`, `sandbox`, `plugins`, `env`, `cwd`) and the hosting guide's multi-tenant recipe is `settingSources: []`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, per-tenant `CLAUDE_CONFIG_DIR` and `cwd` ([TypeScript SDK](https://code.claude.com/docs/en/agent-sdk/typescript); [Hosting](https://code.claude.com/docs/en/agent-sdk/hosting)).

Codex maps onto a narrower but parallel surface: `codex exec --json --output-schema ./schema.json -o ./result.json --sandbox workspace-write --ask-for-approval never -c key=value --profile <name> --worktree`, with `config.toml` keys `model`, `approval_policy`, `sandbox_mode`, `permissions.<name>` profiles with `extends`, `mcp_servers.<id>` (`enabled_tools`, `startup_timeout_sec`, `tool_timeout_sec`), `hooks.<Event>` (same schema as Claude's `hooks.json`), `skills.config[]{path, enabled}`, and the rule that admin "Requirements set limits; configuration values provide defaults" ([Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode); [Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference)). OpenCode exposes `opencode run --format json --agent <name> --model provider/model --auto` plus an HTTP server (`POST /session`, `POST /session/:id/message`, `POST /session/:id/permissions/:permissionID`, `GET /event` SSE) and an `opencode.json` with `agent.<name>{description, model, prompt, tools, permission, mode, steps}`, `permission.{edit,bash,...}` as `allow|ask|deny` with per-pattern rules, and `mcp.<name>` ([OpenCode CLI](https://opencode.ai/docs/cli/); [OpenCode server](https://opencode.ai/docs/server/); [OpenCode config](https://opencode.ai/docs/config/)). Pi exposes `--mode json` (JSONL events to stdout) and `--mode rpc` (JSONL commands on stdin, events including `agent_end` and `agent_settled`, "the signal that Pi will not continue automatically"), `--system-prompt`, `-t/--tools`, `--skill`, `-e/--extension`, and "has no built-in permission system" ([pi rpc.md](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/rpc.md); [pi cli.md](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/cli.md)). The lowest common denominator a node preset can rely on across all four harnesses is: prompt, model, system-prompt append, allowed tools and permission mode, MCP server list, cwd, and a JSONL event stream ending in a result object. gh-aw's frontmatter adds the fields a CI-shaped node needs beyond the harness: `engine`, `tools`, `skills`, `plugins`, `network.allowed`, `safe-outputs`, `timeout-minutes`, `max-turns`, `max-ai-credits`, `strict` ([gh-aw Frontmatter reference](https://github.github.io/gh-aw/reference/frontmatter/)).

### Retry and durability semantics

Adopt the universal step contract `(stable_step_id, serializable_input) -> journaled serializable_output` with retry fields `{initial_interval, backoff_coefficient, maximum_interval, maximum_attempts | maximum_duration, non_retryable_error_types, per_attempt_timeout}`; the names differ across engines, the shape does not:

```python
retry_policy = RetryPolicy(
    initial_interval=timedelta(seconds=10),
    backoff_coefficient=3.0,
    maximum_interval=timedelta(minutes=5),
    maximum_attempts=20,
)
result = await workflow.execute_activity(
    call_external_service, order,
    start_to_close_timeout=timedelta(seconds=30),
    retry_policy=retry_policy,
)
```

([Temporal Python failure detection](https://docs.temporal.io/develop/python/failure-detection)). Step Functions adds `JitterStrategy: FULL|NONE` and `MaxDelaySeconds`, and documents that redriven executions reset retry counts ([AWS error handling](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)); DBOS's `@DBOS.step(retries_allowed, interval_seconds, max_attempts, backoff_rate, should_retry)` adds a predicate ([DBOS steps](https://docs.dbos.dev/python/tutorials/step-tutorial)). Argo's `retryStrategy` is the richest declarative form, with `retryPolicy: Always|OnFailure|OnError|OnTransientError`, an `expression` over `lastRetry.exitCode/status/duration/message`, and `backoff: {duration: "1", factor: "2", maxDuration: "1m", cap: "5"}`, settable per template or for the whole workflow ([Argo retries](https://argo-workflows.readthedocs.io/en/latest/retries/); [retry-backoff.yaml](https://raw.githubusercontent.com/argoproj/argo-workflows/main/examples/retry-backoff.yaml)). Airflow 3.3's AIP-105 maps exception types to RETRY/FAIL and replaced SLAs with Deadline Alerts; `AirflowFailException` bypasses the policy ([Airflow Tasks docs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/tasks.html)). Model Temporal's four activity timeouts (Schedule-To-Start to detect a crashed fleet, Start-To-Close per attempt, Schedule-To-Close across attempts, Heartbeat with a progress payload) and Airflow's task-instance heartbeat timeout, because a healthy container can host a stalled agent loop ([Temporal detecting activity failures](https://docs.temporal.io/encyclopedia/detecting-activity-failures)). Claude Code's own supervision primitives are a stall watchdog (`CLAUDE_ASYNC_AGENT_STALL_TIMEOUT_MS`), "No top-level session timeout", and a `-p` run that can stay open up to 10 minutes waiting for background subagents ([Hosting](https://code.claude.com/docs/en/agent-sdk/hosting); [Headless docs](https://code.claude.com/docs/en/headless)).

For resume semantics mirror ADK, where "successful sub-nodes are skipped when a workflow resumes", orchestrator nodes opt into `rerun_on_resume=True`, and execution IDs are "deterministic IDs from the parent ID and a counter" ([ADK dynamic workflows](https://adk.dev/graphs/dynamic/)), and MAF, whose checkpoints carry a hash of the graph signature so "resumption can detect graph drift" and whose docs state "Checkpoint storage is a trust boundary" ([MAF checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints); [ravichaganti.com](https://ravichaganti.com/blog/visualizing-and-checkpointing-workflows-in-microsoft-agent-framework/)). For intra-node durability, separate outputs from scratch state as Airflow 3.3 does: XCom keyed by `key + task_id + dag_id` and cleared on retry, versus a state store scoped to `(dag_id, run_id, task_id, map_index)` with `get/set/delete/clear`, retention, and a 64 KB soft limit ([Astronomer durable execution post](https://www.astronomer.io/blog/durable-execution-with-apache-airflow.md)). Idempotency splits into trigger dedup (workflow ID, `idempotencyKey`) and side-effect dedup inside a step using keys derived from stable run IDs, such as Restate's `ctx.rand.uuidv4()` ([Restate durable steps](https://docs.restate.dev/develop/ts/durable-steps)). Versioning should follow Restate's immutable deployments ("requests start and end on the same version") or DBOS's application-version tag that gates recovery, and Airflow's bundle versioning that lets clear/rerun default to the original code and backfills to latest ([Restate versioning](https://docs.restate.dev/operate/versioning); [DBOS upgrading workflows](https://docs.dbos.dev/python/tutorials/upgrading-workflows); [Airflow Dag bundles](https://airflow.apache.org/docs/apache-airflow/stable/administration-and-deployment/dag-bundles.html)).

### Approval gate semantics

Ship the gate as a node with its own state, a typed form, a timeout and a default, and surface approver identity. Airflow's operator is the reference signature:

```python
valid_input_and_options = ApprovalOperator(
    task_id="valid_input_and_options",
    subject="Are the following input and options valid?",
    defaults="Reject",
    response_timeout=datetime.timedelta(minutes=5),
    assigned_users=[{"id": "1", "name": "airflow"}, {"id": "admin", "name": "admin"}],
)
```

([Airflow HITL tutorial 3.3.2](https://airflow.apache.org/docs/apache-airflow/3.3.2/tutorial/hitl.html)); responses land in XCom under `chosen_options` and `params_input`, notifiers receive `notify(context)` on creation, and `HITLBranchOperator` routes to downstream task IDs. Argo's shape is minimal (`suspend: {}` or `suspend: {duration: "20"}`; `argo resume --node-field-selector inputs.parameters.myparam.value=abc` to resume a specific node) but has no notion of who approved beyond RBAC on the verb ([Argo suspending](https://argo-workflows.readthedocs.io/en/latest/walk-through/suspending/); [argo resume](https://argo-workflows.readthedocs.io/en/latest/cli/argo_resume/)). Buildkite's `block` step adds `fields`, `allowed_teams`, `blocked_state` and `depends_on`, GitHub environments add up to six required reviewers, a wait timer, self-review prevention and the rule that "Deployment protection rules must pass before a job that references the environment is sent to a runner" (secrets release only after approval), and the Tekton `ApprovalTask` adds `approvers`, `numberOfApprovalsRequired` and a timeout that rejects on expiry ([Buildkite block step](https://buildkite.com/docs/pipelines/configure/step-types/block-step); [GitHub manage environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments); [manual-approval-gate](https://github.com/openshift-pipelines/manual-approval-gate)). For the typed-payload form, Mastra's step contract is the clearest API:

```ts
const approvalStep = createStep({
  id: 'step-1', inputSchema, outputSchema,
  resumeSchema: z.object({ approved: z.boolean() }),
  suspendSchema: z.object({ reason: z.string() }),
  execute: async ({ inputData, resumeData, suspend, bail }) => {
    if (!resumeData?.approved) return await suspend({ reason: 'Human approval required.' });
  },
});
await run.resume({ step: 'step-1', resumeData: { approved: true } });
```

with `bail()` for explicit rejection without error and `resume()` callable "from any part of the app" ([Mastra HITL](https://mastra.ai/docs/workflows/human-in-the-loop)). Two durable-engine details are worth copying: Temporal's signal handler accepts a decision only if `decision.request_id == self.pending_request_id`, and Trigger.dev's waitpoint tokens carry `idempotencyKey`, `timeout` and a public completion URL ([Temporal HITL cookbook](https://docs.temporal.io/ai/cookbook/human-in-the-loop-python.md); [Trigger.dev wait for token](https://trigger.dev/docs/wait-for-token)). gh-aw's `safe-outputs` with `staged: true` is the precedent for "preview the agent's writes, then approve the application of them in a separate job" ([gh-aw site](https://github.github.com/gh-aw/)). CrewAI's `@human_feedback(emit=[...], llm=..., default_outcome=...)`, which lets an LLM collapse free-text reviewer feedback into one of the declared routing outcomes, is the one novel idea here for review-comment-driven branching ([CrewAI human feedback in flows](https://docs.crewai.com/en/learn/human-feedback-in-flows)). Note the security lesson: Airflow 3.3's `awaiting_input` sweep shipped with CVE-2026-67260 (unsafe deserialization in the scheduler), fixed in 3.3.1, so gate state must be data, not pickled callables ([CVE-2026-67260](https://app.opencve.io/cve/CVE-2026-67260)).

### Artifact semantics

Assemble the node's typed output from primitives that already exist. Claude Code's `SDKResultMessage` carries `session_id`, `num_turns`, `duration_ms`, `duration_api_ms`, `total_cost_usd`, `usage`, `modelUsage` (per model: `inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`, `costUSD`, `costBasis: list|managed|unknown`), `permission_denials[]`, `structured_output` and error subtypes `error_max_turns | error_during_execution | error_max_budget_usd | error_max_structured_output_retries`; `--json-schema` yields validated `structured_output` and `system/init` records `model`, `tools`, `mcp_servers`, `plugins` and errors for harness-drift auditing ([TypeScript SDK](https://code.claude.com/docs/en/agent-sdk/typescript); [Headless docs](https://code.claude.com/docs/en/headless)). Codex emits `thread_id`, `turn.completed.usage {input_tokens, cached_input_tokens, output_tokens}`, and items `file_change{changes[{path, kind: add|delete|update}]}`, `command_execution{command, exit_code, aggregated_output}`, `mcp_tool_call`, plus `--output-schema` JSON and `-o <file>` ([Codex items.ts](https://raw.githubusercontent.com/openai/codex/main/sdk/typescript/src/items.ts); [Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)). The resumable handle is `session_id` / `thread_id` (`claude -p --resume <id>`, `codex exec resume <id>`, `--fork-session` / `codex exec fork`), the workspace handle is branch plus commit plus PR URL from a worktree (`--worktree <name>` on branch `worktree-<name>`, `.worktreeinclude` for gitignored files) ([Worktrees](https://code.claude.com/docs/en/worktrees)). For file artifacts mirror Argo: producer `outputs.artifacts: [{name, path}]`, consumer `inputs.artifacts`, binding `arguments.artifacts: [{name, from: "{{tasks.X.outputs.artifacts.Y}}"}]`, `archive: {none: {}}` to skip tarring, per-artifact GC strategy `OnWorkflowCompletion|OnWorkflowDeletion|Never`, pluggable repository backends (S3, GCS, Azure, Git, HTTP, Plugin) with `keyFormat` templating ([Argo artifacts](https://argo-workflows.readthedocs.io/en/latest/walk-through/artifacts/); [Argo artifact repository](https://argo-workflows.readthedocs.io/en/latest/configure-artifact-repository/)). Pass repo checkouts as one snapshot reference rather than many files, given GitHub's 500-artifacts-per-job and Tekton's 4096-byte termination-message limits ([actions/upload-artifact](https://github.com/actions/upload-artifact)). Type each edge with JSON Schema generated from Pydantic (`model_json_schema()`, Draft 2020-12, `$defs`/`$ref`), reference large or binary outputs by digest with an OCI-style `artifactType` and `subject`, and wrap notifications in CloudEvents (`id`, `source`, `specversion`, `type`, `dataschema`) ([Pydantic JSON Schema](https://pydantic.dev/docs/validation/latest/concepts/json_schema/); [OCI image-spec manifest](https://github.com/opencontainers/image-spec/blob/main/manifest.md); [CloudEvents spec](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md)). Keep Prefect's distinction between data outputs and human-facing artifacts (`create_markdown_artifact`, `create_table_artifact`, `create_progress_artifact`, versioned by `key`) for agent summaries and transcripts in a UI ([Prefect artifacts](https://docs.prefect.io/v3/develop/artifacts.md)). Managed Agents' `user.define_outcome` with a `rubric` is the precedent for attaching an acceptance criterion to a node ([Managed Agents multiagent](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration)).

### Runtime protocol and sandboxes

Define the runtime plug-in as the cross-system verb union: `submit(workload)`, `poll()`/`sync()`, `cancel(grace)`, `adopt()` after controller restart (Airflow `try_adopt_task_instances`, Dagster `resume_run`, Nomad `RecoverTask`), `logs()`, `heartbeat()`, and declarative capability flags (Nomad's `Capabilities()` declares signals, exec, fs/network isolation modes) ([Nomad task driver plugins](https://developer.hashicorp.com/nomad/docs/concepts/plugins/task-drivers)). Express it as one typed config object per runtime, Prefect-style, rather than separate operators; keep three layers apart (scheduler placement, task-body isolation, intra-task fan-out) and surface the isolation class (container, gVisor, microVM, VM) as a capability, since Modal selects `runtime="gvisor"|"vm"` per sandbox and Daytona offers Container, Linux VM, Windows VM, GPU and macOS classes ([Modal sandbox guide](https://modal.com/docs/guide/sandbox); [Daytona sandboxes](https://www.daytona.io/docs/en/sandboxes)). On Kubernetes, use one Pod or `Sandbox` per session, `podFailurePolicy` with `onPodConditions: [{type: DisruptionTarget}]` so preemption is not counted as agent failure, `spec.suspend` for human waits, and `managedBy` to delegate Job ownership ([Kubernetes Jobs](https://kubernetes.io/docs/concepts/workloads/controllers/job/)); the `kubernetes-sigs/agent-sandbox` CRDs (`Sandbox`, `SandboxTemplate`, `SandboxWarmPool`, `SandboxClaim`, with gVisor/Kata via `RuntimeClass` and Python/Go SDKs) are the emerging native primitive ([agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox)). The sandbox-provider verb set is `create(image|snapshot, resources, env, network)`, `exec(cmd, timeout) → {stdout, exit}`, `files.read/write`, `pause/resume`, `snapshot/fork`, `kill`, `updateNetwork`; memory-snapshot pause (E2B ≈4 s/GiB to pause, ≈1 s to resume; Blaxel resume "under 25 ms") and proxy-side secret injection (E2B `Secret.fill`, Runloop Agent Gateways, Claude Code's sentinel-substituting proxy) are now table stakes, and pricing clusters at **$0.05–0.15 per vCPU-hour** billed per second with paused state billed as storage only ([E2B persistence](https://docs.e2b.dev/docs/sandbox/persistence); [E2B pricing](https://e2b.dev/pricing); [Blaxel sandboxes](https://docs.blaxel.ai/Sandboxes/Overview); [Runloop overview](https://docs.runloop.ai/)). The concrete pod recipe is a non-root user, `ANTHROPIC_API_KEY`/`CODEX_API_KEY` injected or proxied, an ephemeral clone, then `claude --bare -p ... --output-format json --max-budget-usd ... --max-turns ...` or `codex exec --json --sandbox workspace-write -o result.md ...`; in-container bubblewrap needs user namespaces or `enableWeakerNestedSandbox`, Ubuntu 24.04 AppArmor blocks it, `--dangerously-skip-permissions` is refused as root, and Anthropic's reference devcontainer is "a working example rather than a maintained base image" ([Sandboxing](https://code.claude.com/docs/en/sandboxing); [Dev containers](https://code.claude.com/docs/en/devcontainer); [Codex sandboxing](https://learn.chatgpt.com/docs/sandboxing)). Anthropic's self-hosted runners show the enterprise-CI shape to interoperate with: `claude self-hosted-runner` polls Anthropic's queue over outbound HTTPS, `claude -p "..." --environment ccpool_abc123 --ref main` dispatches to it from a script, the lease lapses ~60 s after polling stops, and the control plane stays Anthropic-hosted ([Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)); Managed Agents' `ant beta:worker poll --workdir /workspace` is the same pattern with "Keep [the API key] off the worker host" ([Self-hosted sandboxes](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes)). Enterprise CI runtimes in closed networks follow the same shape: YAML flow definitions of typed tasks over a pluggable execution layer, reached by workers that open only outbound connections.

### Cost controls

Two semantics exist and the product should offer both. Claude Code's `--max-budget-usd` is a client-side estimate checked between calls: "Spend can pass the cap, so leave headroom", subagent spend counts, and at the cap new subagent spawns fail with `Budget limit reached` while the run ends with `error_max_budget_usd` ([CLI reference](https://code.claude.com/docs/en/cli-reference)). Managed Agents' `budget: {type: "limit", max_list_cost: {amount: "125", currency: "USD"}}` is server-enforced at list rates (tokens, $10 per 1,000 searches, $0.08 per session-hour), attachable only at creation, and a session at the cap "pauses and goes idle" with `stop_reason: budget_reached` rather than being killed, emitting `session.usage` then `session.status_idle` ([Budgets](https://platform.claude.com/docs/en/managed-agents/budgets)). gh-aw's `max-ai-credits` per run and `max-daily-ai-credits` per workflow (1 AIC = $0.01) are the per-node and per-pipeline-per-day shape ([gh-aw site](https://github.github.com/gh-aw/)). Accounting should read `total_cost_usd` and `modelUsage[model].costUSD` with `costBasis`, dedupe per-step usage by assistant message id, treat per-step `output_tokens` as a placeholder, and never sum results across resumed sessions because resumed runs report whole-session totals; all figures are "client-side estimates, not authoritative billing data" to be reconciled against the Admin `usage_report/messages` and `cost_report` endpoints (1m/1h/1d buckets, group by `api_key_id`, `workspace_id`, `model`, `service_tier`) ([Cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking); [Anthropic Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api)). For Codex, cost must be computed from a price table over the per-turn token triple. Chargeback labels come free from `OTEL_RESOURCE_ATTRIBUTES="department=engineering,team.id=platform,cost_center=eng-123"` and the `claude_code.cost.usage` metric's attributes `model`, `query_source` (main/subagent/auxiliary), `agent.name`, `skill.name`, `plugin.name`, `mcp_server.name`, with managed settings able to pin the collector endpoint so telemetry cannot be redirected ([Claude Code Monitoring](https://code.claude.com/docs/en/monitoring-usage)). Because agent-layer caps are soft and framework loop limits are step counters, hard limits belong at the orchestrator (attempt timeouts, max attempts, node budgets that gate scheduling) and at the gateway or workspace level.

### Observability and audit

Emit OTel GenAI spans even though the conventions are still "Development": a root `invoke_agent {name}` (INTERNAL) span per node with `gen_ai.conversation.id` set to the pipeline run or session id, `chat {model}` inference spans with `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.usage.cache_read.input_tokens`, and `execute_tool {tool}` spans using the "Command execution" refinement (`process.executable.name`, `process.exit.code`) and the skill refinements (`gen_ai.skill.name`, `gen_ai.skill.source.uri`) that already target coding agents ([semconv-genai agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md); [semconv-genai client inference](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/client-inference.md)). The practical join key across Claude Code OTel (`session.id`), Langfuse (`langfuse.session.id`), LangSmith, Datadog (`session_id`) and Helicone (`Helicone-Session-Id`) is the session id, and Datadog and Fiddler both state provider-side traces are not propagated and must be joined on it ([Langfuse OpenTelemetry](https://langfuse.com/integrations/native/opentelemetry); [Datadog OTel LLM Observability](https://docs.datadoghq.com/llm_observability/instrumentation/otel_instrumentation/)). Claude Code's `--forward-subagent-text` and `parent_tool_use_id` reconstruct subagent transcripts at every nesting depth, `system/api_retry` events expose retry attempts and error categories, and `claude_code.tool_decision` events (`decision`, `source` ∈ config/hook/user_permanent/user_temporary/user_abort/user_reject) plus `permission_denials` in the result form the approval audit log ([Headless docs](https://code.claude.com/docs/en/headless); [Claude Code Monitoring](https://code.claude.com/docs/en/monitoring-usage)). Adopt XTrace's four layers (execution, harness, money, outcomes) and its rule that a trace must distinguish "retries from a never-cleared context from a subagent fan-out", Fiddler's alert thresholds (`tool_call.count > 20`, prompt tokens above 80% of context, session tokens 10× the median), and Augment's minimum eval gate of compile checks, test runs and diff-size bounds ([XTrace](https://xtrace.ai/blog/coding-agent-observability); [Fiddler](https://www.fiddler.ai/blog/coding-agent-observability); [Augment Code](https://www.augmentcode.com/guides/agent-observability-for-ai-coding)). For compliance, bind each node run to an in-toto statement in the `agentattest` shape (run id, patch digest, PR, `humanApproval.state`, config and MCP digests, trace ids by URI plus digest, raw prompts not stored) and layer standard GitHub artifact attestations on the build outputs; redact before journaling, because Temporal, Restate and DBOS persist step inputs and outputs verbatim ([agentattest](https://github.com/BlockTarioIQ/agentattest); [GitHub Artifact Attestations](https://github.blog/enterprise-software/devsecops/enhance-build-security-and-reach-slsa-level-3-with-github-artifact-attestations/)). For regression testing, run golden pipelines as immutable, comparable experiments (Braintrust `eval-action@v2` with `report_metrics: Cost`; promptfoo `--tag git.sha=$GITHUB_SHA`), gated by deterministic checks before LLM-judge rubrics, and expect repeated trials because no vendor promises identical outputs even at temperature 0 ([Braintrust run in CI](https://www.braintrust.dev/docs/evaluate/run-in-ci); [promptfoo CI/CD](https://www.promptfoo.dev/docs/integrations/ci-cd/)).

## Conclusion

The research reframes the brief from "build a better Airflow" to "build the missing middle layer". Classic orchestrators already own the graph vocabulary and are converging on intra-step durability; vendor harnesses already own the session, the sandbox and (in Anthropic's case) the budget; what no one owns is the contract between them: a node that is a resumable session handle with a typed output, a budget that gates scheduling, a sub-graph that can be retried as a unit with its artifacts rolled back, and an approval that is a stage, not a tool call. Because the harness surfaces are now scriptable in near-identical ways (`--bare -p` with injected settings, agents and MCP config; `codex exec` with `-c` overrides and an output schema; OpenCode's HTTP server; Pi's RPC mode), the per-node preset can be a single schema compiled to each harness's native injection, and gh-aw has already proven the compile-and-pin step works in production CI.

Two strategic implications follow. First, the product's defensible value is cross-agent, cross-run, approval-gated, cost-attributed composition, because in-harness fan-out (dynamic workflows, Managed Agents workflow runs, Cursor subagents) will keep absorbing single-session parallelism; the design should therefore treat each harness's own subagent and permission machinery as the inner loop and never re-implement it. Second, the two best-measured pain points, review throughput and cost opacity, are aggregation problems that only a pipeline-level product can see, so batched review artifacts, per-node spend and cost-per-accepted-change should be first-class outputs rather than afterthoughts. The uncertainties to track are whether the Prefect–Dagster entity ships a session-level node before this product does, whether the OTel GenAI `invoke_workflow` span stabilizes into something worth targeting, and whether Anthropic's `--bare` default and self-hosted runner contract stay stable enough to be the reference runtime.
