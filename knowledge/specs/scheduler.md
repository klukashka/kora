# kora MVP design — scheduler

Status: design draft for owner review (2026-10-15, revised after the design review, see [review-2026-10-15.md](../reviews/review-2026-10-15.md)). Scope: FR-6.1–6.10, FR-1.6, NFR-1, NFR-2, NFR-3, NFR-7. The scheduler is a stateless loop over the tables in [data-model.md](data-model.md); it submits work through the runtime protocol in [protocols.md](protocols.md). Owner decisions on design choices are referenced as **DD-n** ("design decision n") and recorded in [design-decisions.md](../reviews/design-decisions-2026-10-15.md).

## 1. Components and processes

| process | role | MVP deployment |
|---|---|---|
| `kora api` | HTTP API, webhook endpoints, worker endpoints, MCP endpoints, the static files of the `kora web` console | 1..n replicas, stateless |
| `kora scheduler` | the passes below: triggers, readiness, admission, waits, timeouts, completion, clear-downstream | 1 replica in MVP; designed for n with per-row claims and a per-run lock |
| `kora worker` | one per runtime: claims attempts, prepares workspaces, submits, tails the session's normalised event stream and relays the runner's counters, uploads segments and artifacts, finalises | 1..n per runtime name, registered in the `worker` table; a worker has **one path to the control plane, the HTTP API**, with a service token bound to a namespace list (design review finding [namespace-scoped principals](../reviews/review-2026-10-15.md#namespace-scoped-principals)), outbound only (DD-13); it may run inside an adopter's network; it never enforces limits (design review finding [one enforcement point](../reviews/review-2026-10-15.md#one-enforcement-point)) |
| retention task | section 13 | a low-priority coroutine inside the scheduler process, batch-paced; not a process of its own |
| `kora standalone` | api + scheduler + worker(local) in one process on SQLite; the worker uses the same API client over an in-process ASGI transport | development |

The split between scheduler and worker is a decision (DD-13) and follows the Airflow executor model: the scheduler decides and persists; workers perform the runtime calls and report through the API. There is no direct-SQL path for workers.

## 2. The scheduling loop

The scheduler runs the following passes continuously; each pass is a short transaction that claims rows, decides, and writes rows. No pass holds state in memory between passes (NFR-1.2). Passes 2 to 8 operate per run under the **run lock** (a transaction-scoped advisory lock on `run.id` on PostgreSQL, the single writer on SQLite), so two scheduler replicas never evaluate the same run concurrently (design review finding [per-run lock](../reviews/review-2026-10-15.md#per-run-lock)); triggers and timeouts stay per row.

1. **Triggers.** Fire due `trigger_binding` rows (cron `next_fire_at <= now`, sensor polls due through the sensor protocol); create `run` rows with derived idempotency keys; apply the graph's `overlap` (`allow`: always start; `skip`: no run if one is `running` for the graph; `queue`: create `pending` and start later; DD-12). When the graph sets no `overlap`, runs fired by a webhook use `queue`, so that a burst of events does not start a burst of runs, and runs from every other trigger kind use `allow` (FR-6.2, ADR-0006). Webhooks are authenticated by the API (HMAC or bearer per trigger, DD-17) and turned into `inbound_event` rows; the trigger pass converts those addressed to a trigger binding into runs and those addressed to waits into wake-ups.
2. **Materialise.** A `pending` run gets its top-level node instances created from the pinned graph version's IR; subgraph bodies and fan-out instances are materialised lazily when the containing node becomes `ready` (NFR-3.3).
3. **Readiness.** A query, not a dirty set: `pending` instances of the run whose upstream instances are all terminal under the trigger rule (design review finding [one downstream clear instead of generation counters](../reviews/review-2026-10-15.md#one-downstream-clear)). For each: resolve inputs to `current` artifact versions, write `consumed_versions`, move to `ready` or `skipped`/`upstream_failed`. Only runs touched since the last pass (`run.updated_at`) are visited, which keeps the pass incremental (NFR-3.3).
4. **Branch and collection.** `ready` branch instances evaluate their CEL expression over consumed artifacts and mark non-chosen targets `skipped`; a fan-out instance whose body instances are all terminal collects their `collect` outputs into its `List` artifact versions and completes (there is no fan-in node).
5. **Admission.** `ready` instances that need a runtime (`agent`, `command`) become `queued` with an `attempt` row (`created`), subject to concurrency limits and the namespace's daily soft cost limit (section 6); an instance held back gets an `admission` wait row rather than a field of its own. Waiting kinds (`human_input`, `wait_event`, `timer`) become `waiting` with a `wait` row and, for approvals, an `approval_request` row (section 5).
6. **Wake-ups.** `wait` rows with `wake_at <= now` or a matching `inbound_event` are resolved; the owning instance returns to `running` (sensor: evaluate `until`, else reschedule), `ready` (retry back-off) or completes (timer).
7. **Timeouts and liveness** (section 4).
8. **Completion.** Attempts in `finishing` whose declared outputs all have a `current`, schema-validated version (the API validated them at upload) move their instance to `succeeded`, otherwise `failed` with `artifact_invalid`; retry policy is applied (new `queued` attempt with back-off wait, or terminal failure); a sub-graph instance whose sub-graph attempt failed and may retry runs **clear downstream** for its body and re-materialises it with `subgraph_attempt + 1` (data-model.md section 6); the run completes when no instance is non-terminal (DD-36 finalisation ownership).

A manual retry from the API is the same clear-downstream transaction on the chosen node, followed by the ordinary passes. When an approval request is created (pass 5), the scheduler sums the run's usage records into `run_cost` on the request (DD-8).

Workers run a separate loop: claim `created` attempts of their runtime through the API (section 3), prepare the workspace, submit, stream, enforce, finalise.

## 3. At-most-once submission, leases and adoption

```
scheduler:  INSERT attempt(status=created)                                              -- committed; submission is keyed by the attempt id
worker:     POST /workers/{id}/claims {runtime, max: 1}  → one self-contained claim or none (polled every 1 s)
            claim = {attempt, lease: {epoch, until}, run: {params}, node: {config, limits, outputs, inputs: [{name, type, payload | storage_ref}]}, secret_aliases}
worker:     handle = runtime.submit(workload)                                           -- idempotent on attempt id
worker:     POST /attempts/{att}/transition {to: submitted, handle, lease_epoch}         -- committed; the node instance becomes running
worker:     every 15 s: POST /attempts/{att}/heartbeat {lease_epoch, counters} → {desired_state, lease_until}   -- also refreshes worker.last_seen_at
```

- **Fencing** (design review finding [lease fencing](../reviews/review-2026-10-15.md#lease-fencing)). Every claim increments `lease_epoch`; every heartbeat, segment upload, artifact upload and transition carries it; the API rejects a stale epoch with `API008`. A worker whose renewal is rejected stops relaying and abandons the attempt locally; it never writes again under that epoch. The claim query excludes attempts of cancelled runs, attempts with `desired_state = cancel`, and namespaces outside the service token's list (design review finding [namespace-scoped principals](../reviews/review-2026-10-15.md#namespace-scoped-principals)). The epoch travels in API calls only, never inside the `Workload` handed to the runtime (design review finding [redundant liveness and keys](../reviews/review-2026-10-15.md#redundant-liveness-and-keys)).
- **Lease**: 120 s, renewed every 15 s with the heartbeat. An expired lease alone makes the row reclaimable: the scheduler marks it so in its timeout pass, and the worker that next claims it receives a new epoch, which fences the previous holder ([architecture critique of 2026-10-16, finding A07](../reviews/architecture-critique-2026-10-16.md#a07-execution-domain)). The scheduler calls no runtime and no worker; every observation of the runtime is made by a worker and reported through the API.
- **Execution domain.** A handle is meaningful only where the runtime stores it: the `local` and `docker` runtimes keep handles, process groups and `host_path` workspaces on one machine, an enterprise runtime keeps task ids in a shared service. A runtime declares `portable_handles` in its capabilities ([protocols.md](protocols.md) section 2). When it is false, the reclaimed row is offered only to the worker whose stable id submitted it (`attempt.worker_id`), which is the same host after a process restart; when it is true, any worker of the runtime may claim it. A non-portable attempt whose lease has been expired for a second lease period without a claim is `lost`.
- A crash between claim and handle persistence leaves `status=claimed` with an expired lease. The claiming worker calls `runtime.lookup(attempt_id)`: a handle means the submission happened and is persisted now; `None` means the runtime confirmed that it never happened and the attempt returns to `created`; `KoraProtocolError(retryable=True)` means the runtime could not answer, and the attempt stays `claimed` under the new lease and is looked up again on the next claim cycle, never resubmitted on that answer. Either way no second session is started (FR-6.1a, NFR-2.1).
- A crash after `submitted` leaves an expired lease on a live handle. The claiming worker calls `runtime.adopt(handle)`, which resumes tailing the normalised event stream from the stored offset (`counters.stream_offset`) against the event file the runtime keeps in the workspace (section 4); the session runner inside the runtime kept enforcing all along. Adoption is by attempt-id lookup when the handle is missing and by handle otherwise.
- Adoption of a runtime that confirms it does not know the handle any more yields `lost`, classified `infrastructure`; the runtime-level `infrastructure_retry` policy decides whether to resubmit, and it does not consume the node's agent attempts (NFR-2.4). An unreachable runtime is not a confirmation: the attempt stays `claimed` as above.
- The integration test `test_submit_crash_recovers_in_original_execution_domain` fixes this: two hosts run workers of one runtime name; a worker crashes after `submit` and before the handle is persisted while the session keeps running and the control plane cannot reach the host; with the runtime reachable from the right worker the same session is adopted and no second submission happens; with the runtime unreachable the attempt stays `claimed` and is not resubmitted; with a confirmed absence the infrastructure retry applies; an absence reported by the wrong host never permits a new start.
- **Cancellation delivery** (design review finding [cancellation through heartbeats](../reviews/review-2026-10-15.md#cancellation-through-heartbeats)): the API sets `desired_state = cancel`; the worker reads it from the heartbeat response and calls `runtime.cancel(handle, grace)`. Two attempts of one node instance can never share a `number` (unique constraint).

## 4. Heartbeats, stall detection and timeouts

Two liveness signals are kept apart (NFR-2.3):

- **Runtime liveness**: the worker's lease (`lease_until`), and `runtime.heartbeat(handle)` as observed by the worker that holds the lease. A lease that expires means the worker is gone; the row is re-claimable under the domain rule of section 3. A runtime that confirms the session gone means `lost`; a runtime that cannot answer means nothing yet.
- **Agent-loop liveness**: `last_event_at`, advanced by every normalised event and relayed in `counters`. A session whose SDK event stream has been silent for `stall_after` is classified `stalled` by the **session runner**, the only enforcer of `max_events`, the soft budget and `stall_after` (design review finding [one enforcement point](../reviews/review-2026-10-15.md#one-enforcement-point)): it terminates the session (interrupt, 30 s grace, kill), the attempt fails with class `stalled`, and the node's retry policy decides (design review finding [`stalled` in node policy](../reviews/review-2026-10-15.md#stalled-in-node-policy)). `stall_after` comes from the node's `limits.stall_after`, else the graph's `runtime.stall_after`, else the runtime's `default_stall_after` (15 minutes in the reference runtimes; DD-15). The window is **extended while the last event is an unanswered tool call** (a long dev-run inside one `Bash` call is not a stall) up to the node timeout; it applies in full only when the harness is between tool calls (design review finding [stall detection and orphaned processes](../reviews/review-2026-10-15.md#stall-detection-and-orphans)).

The session's normalised event stream is written by the runner to a file in the workspace (`.kora/events.jsonl`) as the resumable source of truth, one line per event `{i, at, kind, data}` (DD-36); the worker tails it, so adoption after a worker crash resumes from the recorded offset. The local runtime spawns each session in its own process group tagged with the attempt id and kills orphaned groups it finds when it claims work.

Timeouts (FR-6.5): the scheduler's timeout pass compares `attempt.started_at + limits.timeout` and `run.started_at + runtime.limits.timeout` with `now`; breaches cancel with grace and fail with class `timeout`. The node timeout also travels to the runner as an absolute deadline in `Workload.limits`, and the runner terminates the session at that deadline itself (interrupt, 30 s grace, kill) when the control plane is unreachable, so a hard timeout stops the computation during a partition and not only the state in the database; the scheduler's transition remains the authority for the attempt's state (`test_runtime_enforces_deadline_during_control_plane_partition`). Every wait expiry, timers, approvals and sensors alike, is the `wake_at` of its `wait` row (design review finding [one clock for approvals](../reviews/review-2026-10-15.md#one-approval-clock)); expiry applies `on_expiry` (NFR-2.5). Subgraph timeouts are checked against the subgraph instance across attempts (data-model.md section 5).

**Aggregate budgets** (FR-6.6, ADR-0010; [architecture critique of 2026-10-16, finding A11](../reviews/architecture-critique-2026-10-16.md#a11-aggregate-budget)). The session runner enforces only the attempt's own `budget_usd`; it cannot see the other sessions of a run. The same timeout pass therefore sums, for every run and every sub-graph instance touched since the last tick, `usage_record.usd_estimate` of finished attempts plus `attempt.counters.usd` of non-terminal ones, which the runner relays with every heartbeat, so the figure is at most one heartbeat interval stale; previous sub-graph attempts are included (data-model.md section 5) and `resume` attempts count their delta only. When the sum exceeds the scope's `budget_usd` plus `budget_headroom_pct`, the scope is budget-exhausted, with the same rule as the namespace daily budget (section 6): the admission pass admits no further attempt in it, and a `ready` instance in that scope fails with class `budget_exhausted` instead of waiting, so the run ends deterministically; running attempts are not cancelled, they finish and keep their outputs, because killing a nearly finished session over an aggregate costs more than the overshoot of what is already running. The limit stays soft: a scope can overshoot by what its running sessions spend until they finish, plus one heartbeat interval of staleness (NFR-8.2). Tests: `test_parallel_attempts_share_run_budget` (two sessions at 6 under a run budget of 10 both finish, and the third ready node of the run fails with `budget_exhausted` instead of starting), `test_subgraph_budget_includes_previous_iterations`, `test_resumed_session_does_not_double_count_usage`; each drives controlled usage events and checks the documented action at the threshold, with `partial` and `unavailable` records included at their recorded value.

Grace handling (FR-6.7): `cancel(handle, grace)` sends the harness a termination signal, waits `grace`, then kills; artifacts the session already wrote are collected as `partial`, usage records are marked `partial` (FR-9.1), and the workspace is released after collection.

## 5. Waits hold no worker (NFR-1.3)

A waiting instance is one `wait` row and, for approvals, one `approval_request` row. Nothing else exists: no coroutine, no container, no lease. Three resolution paths:

- **Time**: `wake_at` scanned by the wake-up pass; timers and retry back-off.
- **Event**: the API writes an `inbound_event`; the wake-up pass matches it against open `wait.subscription` rows (`name` equality, then the `match` expression over payload and inputs), marks the wait `satisfied`, records `consumed_by`.
- **Poll**: sensors are polled by the scheduler at `interval` through the sensor protocol (`observe` returns an observation the node's `until` CEL expression is evaluated on); the `vcs` approval channel is polled through the approval protocol. A poll is a short call, not a held slot. Sensors that declare `supports_push` and chat channels with push notifications (post-MVP) deliver through the same `inbound_event` path.

An approval response from any channel is applied through one function: load the request, check that it is still `pending`, compare `(commit_sha, digests)` with the bound values, then transition. The channel is only a transport (FR-7.2a).

## 6. Concurrency limits (FR-6.10)

Limits are evaluated in the admission pass, in this order, each as a count over rows: global `max_running_attempts` (deployment config), per namespace (`namespace.policy.concurrency`, and `max_pending_runs` checked at trigger time, design review finding [namespace-scoped principals](../reviews/review-2026-10-15.md#namespace-scoped-principals)), per graph (`runtime.concurrency.max_running_nodes`, `max_running_runs`), per runtime (`RuntimeCapabilities.max_concurrent` and NFR-7.4 configured limit), per fan-out (`max_parallel`, counted over body instances of the same fan-out instance). A `ready` instance that fails any check gets an `admission` wait row with `wake_at = now + admission_interval`; the oldest ready instance wins (FIFO by `node_instance.id`). Limits live in rows and config reloaded every pass, so they change without restart (NFR-7.4).

**Reservation** ([architecture critique of 2026-10-16, finding A12](../reviews/architecture-critique-2026-10-16.md#a12-capacity-reservations)). Capacity is occupied by every non-terminal attempt, from `created` through `claimed`, `submitted`, `running` and `finishing`: an attempt reserves its slot when its row is inserted and releases it when it reaches a terminal state, which happens exactly once because terminal transitions are idempotent. The count and the insert run in one transaction under a lock per limit scope: on PostgreSQL the admission pass takes `pg_advisory_xact_lock` on the global scope, then the namespace, the graph, the runtime and the fan-out instance, always in that order, so two scheduler replicas holding different run locks serialise on the shared scope and never admit over a limit; on SQLite the single writer serialises. Tests: `test_last_slot_reserved_once` (two admission participants on PostgreSQL, one free global slot, one attempt created), `test_created_attempt_reserves_capacity` (a `created` attempt not yet claimed counts), `test_capacity_released_once` (a terminal transition frees one slot and a repeated terminal transition changes nothing); SQLite is checked for the same observable outcome.

**Daily soft cost limit** (DD-31): `namespace.policy.daily_budget_usd`. When the namespace's estimated spend for the current day (sum of `usage_record.usd_estimate` over attempts started today, in the namespace's timezone) exceeds it, no new attempts are admitted; running ones finish. The state is visible in `/metrics` (`kora_namespace_daily_spend_usd`, `kora_namespace_budget_blocked`) and on `GET /namespaces/{ns}/cost/daily`.

## 7. Retry handling

On attempt failure with class `c`: if `c` is in `non_retryable` or not in `retry_on`, or `attempt_count >= max_attempts`, or `predicate` evaluates false, the instance fails. Otherwise a `wait` row of kind `retry_backoff` is created with `wake_at = now + min(initial_interval × backoff^(n−1), max_interval)`; on wake the instance becomes `ready` again and the next attempt is created with the chosen strategy: `fresh` (new workspace from the declared revision), `fresh_with_feedback` (new workspace from the previous attempt's `VcsRef` when present, `Feedback` DTO passed to `build_session_spec`, carrying review comments with author and association per DD-35), `resume` (previous attempt's `scratch.session_handle`; falls back to `fresh_with_feedback` with `strategy_fallback` set when the runtime lacks `supports_resume`, when the handle is gone, or when the installed harness version differs from the one recorded on the previous attempt, design review finding [per-attempt version snapshots](../reviews/review-2026-10-15.md#per-attempt-version-snapshots)). Sub-graph attempts follow the retry policy of the sub-graph with clear-downstream and body re-materialisation instead of a new runtime attempt.

Manual retry (FR-6.8) is the clear-downstream transaction started by the API (data-model.md section 6); readiness does the rest. It stays within the run's pinned graph version: `run.graph_version_id` never changes after creation, so a graph version that adds a required node, removes one or changes an artifact type never meets an existing run (FR-1.7, ADR-0007, [architecture critique of 2026-10-16, finding A09](../reviews/architecture-critique-2026-10-16.md#a09-graph-version-retry)). Running again on another version is a **rerun**: `POST …/runs/{run}/rerun` creates a new run of the same graph with `rerun_of_run_id` pointing at the original, on the pinned version by default or on the latest or a named one, with the original's parameters unless overridden; it enters the trigger pass like any manually triggered run, consumes none of the original's artifact versions and leaves the original untouched (api-and-agent-surface.md section 2). Each attempt snapshots `price_table_id`, the runtime `image_digest` and the installed `harness_version`, so a price table or image changed mid-run is attributable per attempt, and its resolved configuration is reconstructible from the pinned document, the preset snapshot under `meta.presets`, the run parameters and the consumed artifact versions, with `resolved_config_digest` as the check (data-model.md section 5).

`test_latest_graph_creates_explicit_new_execution` fixes this: version 1 of a graph is `build → approve`; version 2 adds a mandatory gate before `approve`, removes a node and changes the type of an output. A run pinned to version 1 fails in `build`; a manual retry of `build` keeps running version 1 and never materialises the gate. A rerun with `graph_version: latest` creates a new run with `rerun_of_run_id` set, materialises the gate so that `approve` is unreachable without it, and consumes no artifact version of the original run, so no artifact of the removed node or of the old type is read under the new type. The original run's attempts still resolve to version 1, and recomputing their configuration from the pinned document, the parameters and the consumed versions reproduces their `resolved_config_digest`. On PostgreSQL and SQLite.

## 8. Restart and multi-scheduler safety

- Per-row passes (triggers, timeouts) claim rows with `UPDATE … WHERE status = … AND (lease_until IS NULL OR lease_until < now)`; per-run passes take the run lock first.
- **Tick semantics** (DD-36): for each run touched since the last tick, passes 2 to 8 repeat until no row changes, capped at 10 rounds per run per tick; every table carries `created_at` and `updated_at`. MVP runs one scheduler but the statements are already claim-based (NFR-1.2 HA path).
- Actions are idempotent on `(run id, node path, attempt id)` (NFR-2.2): re-running a pass after a crash re-derives the same decisions from rows; side effects are guarded by the attempt id as submission key, `approval_request.id`, `inbound_event` idempotency per `(namespace, name)` and the `idempotency_record` table.
- On restart the scheduler performs a **recovery pass** first: expired leases on `claimed`/`submitted`/`running`/`finishing` attempts are marked reclaimable under the domain rule of section 3; lookup and adoption are performed by the workers that claim them. Nothing else needs rebuilding because readiness is a query.

## 9. Scheduling latency (NFR-3.1)

Passes run every 1 s when idle and immediately after any transition (a lightweight in-process notification, or Postgres `LISTEN/NOTIFY`, wakes the loop; SQLite polls). Admission to `runtime.submit` is therefore bounded by one pass plus the worker claim interval, under 5 s at MVP scale. Runtime start-up latency (container start, checkout) is measured separately between `submitted` and the first event and exposed as a metric and on the attempt (`startup_ms`).

## 10. Standalone (SQLite) versus Postgres

| concern | Postgres | SQLite (standalone) |
|---|---|---|
| row claims | `SELECT … FOR UPDATE SKIP LOCKED` | single-writer connection with `BEGIN IMMEDIATE`; one process owns all loops, so claims are plain updates |
| run lock | `pg_advisory_xact_lock(hash(run.id))` | implicit: one writer |
| admission scope locks | `pg_advisory_xact_lock` per limit scope in the fixed order of section 6 | implicit: one writer |
| connection | pool | one connection, WAL mode, `busy_timeout` 5 s, one `asyncio` lock per transaction |
| wake-up | `LISTEN/NOTIFY` plus 1 s poll | in-process event plus 1 s poll |
| JSON columns | `jsonb`, indexed on `consumed_versions` keys | `json` text, no partial indexes; sufficient at standalone scale |
| concurrency | n api replicas, n workers | all coroutines in one process; local runtime only by default (Docker allowed) |
| migrations | `kora db upgrade`, online (NFR-7.2) | same migration files |

The schema and all queries are shared; the repository layer has exactly two dialect-specific statements (claim and notify). Anything that works only on SQLite or only on Postgres is a bug by NFR-0.1.

**Standalone bootstrap** (DD-36): `kora standalone` reads `kora.toml` (or defaults), creates the namespace `default` and the data directory `./.kora-data/{kora.db,artifacts,workspaces}`, prints a personal user token once (with `approve` and `platform` set, namespace `default`, transcripts readable) and mints an internal service token for the in-process worker; the CLI and the MCP servers read `KORA_URL` and `KORA_TOKEN`.

## 11. Metrics and health (NFR-7.3)

`/metrics` exposes: queue depth per runtime (`created` + `queued`), age of the oldest `created` attempt, failed-to-submit count per runtime (design review finding [missing metric and native limit](../reviews/review-2026-10-15.md#missing-metric-and-native-limit)), running attempts, waiting instances by kind, scheduling latency histogram (ready → submitted), startup latency, stalled and lost counts, worker liveness (registered workers by runtime and seconds since last seen), webhook authentication failures, retention last success timestamp and backlog, pending approval age, daily spend and budget-blocked flag per namespace, exporter drops. `/readyz` fails when the DB is unreachable or the recovery pass has not completed.

## 12. Execution backend boundary (NFR-5.5)

The passes in section 2 are the only code that moves `run`, `node_instance`, `attempt` and `wait` rows between states, and the API reaches them through three entry points: start a run, deliver a signal (approval response, inbound event, cancel, manual retry) and tick. That boundary is documented in prose rather than as a Python interface with one implementation (DD-7, design review finding [speculative mechanisms](../reviews/review-2026-10-15.md#speculative-mechanisms)): when the Temporal-backed backend is prototyped after MVP, the generic interpreter workflow replaces the passes and projects transitions into the same rows (data-model.md section 9); readers always read kora's tables.

## 13. Retention task (DD-4)

Retention runs as a separate low-priority task in the scheduler process, paced in small batches with a sleep between them, never inside a scheduling pass. Each batch: select up to N versions past their retention, mark `expiring`, delete each blob only when no other `present` or `expiring` version references the same `storage_ref`, mark `expired`, write `retention.expired` events. The task records its last successful completion for the metric and is safe to re-run at any point (data-model.md section 10).

## 14. Migrations (NFR-7.2)

Alembic migrations are **additive only within a minor version**: columns are added nullable or with defaults, nothing is dropped or renamed until the next minor, and every release runs against the previous schema (N−1 compatibility) so components can be upgraded one at a time. Index creation on PostgreSQL uses `CREATE INDEX CONCURRENTLY` outside a transaction; every DDL statement sets `lock_timeout` so a migration fails fast rather than blocking the scheduler. Upgrade order: database → scheduler → API → workers; a worker on the previous version keeps working because the API accepts the previous request shapes.

## 15. Operability runbook

- **Workers**: `GET /workers` lists the registry (runtime, version, capacity, last seen from claims and attempt heartbeats); a worker that stops claiming is visible before any attempt stalls. A worker refuses to start, and `kora doctor` reports, when an installed harness lies outside the version range its adapter declares as tested (design review finding [harness version health check](../reviews/review-2026-10-15.md#harness-version-health-check)).
- **Storage consistency**: `kora db verify-storage` walks `artifact_version` and `session_segment` rows against the blob store and reports missing or orphaned blobs.
- **Backup and restore**: back up the metadata database first, then the blob store; on restore apply in the same order. Blobs are immutable and content-addressed, so the blob store is backed up by copying new objects: the `artifacts/` directory for `local`, bucket replication or versioning of the S3-compatible service (or a copy with its own tooling) for `s3`. Rows whose blobs are missing are marked `expired` by `verify-storage --repair`. Approval channels search for an existing comment carrying the request id before posting, so a restore does not duplicate change-request comments; triggers replay from `trigger_binding.last_fired_key`, so a restored cron does not double-fire.
