# Local startup I/O ownership and activation

## Status and authority

Design contract for #615/#616, accepted by the project owner on 2026-11-03; runtime activation remains pending. The accepted proposal has SHA-256 `afaa8696eccc36ee9316d3806db956cd321d15b2f5c71564cfda3d2731c618be`. This specification reconciles that contract with the [startup record/checkpoint schema](protocols.md#startup-durability-contract-issue-615). It supersedes the earlier in-process daemon-writer ownership and startup per-sync-clock proposal, not running-state guarantees.

[ADR-0016](../../docs/decisions/0016-trusted-execution-and-publication.md), [ADR-0017](../../docs/decisions/0017-execution-uncertainty-and-safe-replacement.md), [ADR-0018](../../docs/decisions/0018-immutable-attempt-history.md), [ADR-0022](../../docs/decisions/0022-inherited-execution-deadlines.md) and [ADR-0026](../../docs/decisions/0026-package-layers.md) govern execution authority, immutable bindings, deadlines and package boundaries. The current entry point still performs registration and file-backed diagnostics inside the runner. The explicit prepared-resource ownership prerequisite landed in #655; it does not implement the isolation described here.

## Scope and guarantees

Keep one startup journal line and one checkpoint, each at most 16,384 encoded bytes; canonical closed schemas; Linux fdatasync for journal data and fsync for directories, macOS F_FULLFSYNC; original attempt/request/workload/deadline bindings; no workload execution before successful activation; no deletion under uncertain ownership. Running-state journaling, execution, general adoption and full Running retirement remain #196/#197 work.

Replace “writer process exits before registration CAS” with “journal/checkpoint descriptors close before CAS; the helper owns registry CAS, its sync and close; runner activation requires actual helper exit and a successful bounded result.” The checkpoint's runner field identifies the runner, not the storage process. Helper identity belongs to the operation intent.

The five-second protected startup interval begins at T0 when the controller starts arming the prepared runner; the absolute monotonic deadline D is T0 plus 5,000,000,000 ns, capped by any earlier inherited deadline. It includes all protected journal/registry work, IPC and runner failure exit; it is never restarted at individual syncs, retries or recovery. This approved whole-transaction interval replaces the startup per-sync clock. Stop waiting for success at C = D minus 250,000,000 ns and initiate the approved fatal exit then; the final 250 ms is the approved exit reserve inside the five seconds, not an extension or tolerated overrun. Neither controller nor runner accepts a grant at/after C. Qualification measures actual runner disappearance by D, not timeout callback or kill request. This reserve has not been measured or shown sufficient; an actual late exit still fails, and any later reserve change needs a reviewed timing decision. No claim of hard realtime under a frozen OS, scheduler or faults in the runner's executable mappings is made.

Helper disappearance, physical write cessation and storage-resource release are explicitly outside that five-second guarantee. No native I/O cancellation guarantee is introduced. An already-entered write/rename/CAS may finish late. Late completion cannot grant activation. runtime.close stops admission and drains actual owned native work; it may remain pending indefinitely. Outer fixture, job and CI deadlines are unchanged. Old failed evidence is never reclassified as passed.

## Owners and exclusion

The LocalRuntime controller, on the worker side, owns admission, runner/helper identity records, independent exit watches, the absolute deadline and activation. The helper is a separate process, never a runner thread or runner child. It may not fork descendants or start workloads. Runner exit cannot kill, wait for or close helper storage resources.

For the first implementation, serialize protected startup operations across one provisioned local runtime root: one occupied slot, no queued operations. Count preparation, launching, active, finishing, unresolved and reconciliation as occupied. Existing admitted waiters may observe the same operation only within the existing bounded caller limits; they cannot create another operation or extend its deadline. This is a root-wide capacity restriction, not a host-wide guarantee. Dynamic creation of replacement roots/domains to escape unresolved ownership is unsupported. Multiple independently provisioned roots multiply the bound and require an explicit deployment capacity decision; do not claim host-global admission has been implemented.

Provision a permanent private regular single-link slot lock in a fixed trusted coordination directory separate from the potentially faulted state filesystem, never unlink or atomically replace that lock. The coordination directory is bound to one state-root identity at provisioning; it is not selected by a workload or changed on retry. Persist the operation record there as well. This adds a deployment prerequisite: coordination storage and OS process observation must remain responsive for bootstrap/admission. It is not a guarantee under simultaneous coordination-store failure. Merely choosing another pathname on the same failed filesystem does not establish fault independence. Use exclusive nonblocking flock. The worker retains its lock descriptor; the helper inherits the same open-file description before it can perform storage work. Neither side uses LOCK_UN; parent-side handoff closes only its duplicate when appropriate. No lock-mode conversion. The runner never inherits the lease or any regular-file storage descriptor. The helper must close all operation descriptors before closing its lease; the controller retains its duplicate through actual helper exit and reconciliation.

The lease alone is not proof of process exit or completed I/O. Recovery requires both exclusion and complete process-identity/exit evidence. Retain the root and lock object identities (device/inode), host, boot and PID namespace. Path recreation, a changed inode, missing metadata or unavailable identity is a refusal, not a fresh empty root. Cooperative same-user trust remains; flock is not hostile-same-user containment.

Provisioning/bootstrap is explicit: acquire the coordination lease before opening the faultable state root, writing intent or spawning either protected child. Each LocalRuntime admits at most one bootstrap job with no queue; it remains worker-owned through actual completion and close. After lease acquisition that job counts as the root slot. Concurrent workers can attempt only nonblocking coordination-lock acquisition and must refuse a busy slot before touching state storage. If state preparation blocks, the acquired lease is retained, so worker restart cannot admit another helper. A failure of the coordination filesystem itself may leave pre-lease worker jobs blocked: the one-root-slot claim expressly does not bound that population across arbitrary worker restarts. Automatic restart must stop on unconfirmed pre-lease worker exit; existing process-supervision ownership must prove its absence before replacement. This is an explicit deployment prerequisite and limitation, not an implemented host-global gate. If the product requires enforcement against arbitrary restarts during coordination-store failure, a separately owned host admission service is necessary and outside the size estimate. No five-second runner guarantee is claimed before T0. From T0 onward the controller owns actual runner-exit observation by D, including failed or partial ARM.

## Persistent operation record

One fixed operation record per slot, canonical JSON, strict unknown/duplicate-member rejection and byte-before-decode validation; maximum 16 KiB including envelope. This is a new format, not reuse of a journal record. Write through a unique temporary, file sync, atomic replacement and parent sync under the slot lease. A failed or interrupted replacement has an uncertain result and must be reread; readable bytes do not establish prior acknowledgement.

Closed format `local-startup-operation/1` fields:

- `format`; `operation_nonce` (128-bit lower-case hex); `execution_domain_id`, `attempt_id` (existing Identifier).
- `root_device`, `root_inode`, `coordination_device`, `coordination_inode`, `lock_device`, `lock_inode` (bounded nonnegative integer); `owner` (complete ProcessIdentity of worker); `helper`, `runner` (complete ProcessIdentity or null before registration of that child).
- `launch_nonce`; `request_digest`, `workload_digest`; original nullable `ExecutionDeadline`.
- `startup_directory` (the fixed launch_nonce-writer_nonce component); `startup_reference` (null until determined, otherwise the existing closed reference).
- `phase`: `reserved`, `bound`, `activation_possible`, `resolved`; `resolution`: null, `activated`, `aborted`, or `no_registration` (nonnull only for resolved).
- `protected_deadline_ns`: null before START is bound, otherwise bounded monotonic integer valid only for the recorded boot; never reused after reboot.

The record contains no workload, environment, credentials, arbitrary paths, commands or exception text. Identifiers are schema-bounded before encoding. Worst-case encoded bound must pass a real model test before acceptance. Keep constant storage: one current record and at most one owned temporary. Never overwrite an unresolved generation. All required tuple fields and phase implications are validated, not merely typed independently.

`reserved` is durable before child creation. The helper starts inert with inherited lease and a private socketpair. It proves its actual identity to the live controller; runner preparation and full identities are persisted as `bound` with protected_deadline_ns=null before arming. A crash before bound leaves an inert helper: no START, no startup journal mutation, registration or activation; only owned preparation effects (intent, directories/listener and diagnostics setup) may exist and remain accounted for cleanup. Missing child identity requires complete bounded carrier discovery plus absence confirmation; an incomplete scan keeps the slot unresolved. A helper that has not received START exits on parent channel loss and may not continue a stale launch. After durable bound, controller chooses T0/D/C and sends one ARM frame to the runner. Runner installs its independent absolute abort timer at C and replies ARMED with the exact operation/deadline tuple. Controller installs its own C/D watchdog before sending ARM. Missing/partial ARM or ARMED prevents START and grant; the controller requests termination through the existing pinned runner exit/signal authority at C (or immediately on a fatal protocol failure) and still requires actual disappearance by D. During preparation runner treats parent-channel EOF/malformed ARM as fatal without waiting for the ordinary readiness timeout. The controller is the sole holder of the peer endpoint: neither helper nor launcher retains a duplicate that could conceal worker death. Thus worker death before a complete ARM closes that channel; after complete ARM the runner timer is independent. Controller disappearance, signal delivery or EOF is not itself counted as runner exit. Only after that exact ACK, while now < C, controller sends START(D,C) to the helper. Helper durably updates bound with D before journal/CAS; that update consumes the same budget. Runner death, missing ARM ACK or worker death in this gap cannot leave authorized helper I/O without an armed runner timer. A preexisting nonnull differing D or repeated START is refused. Reboot recovery never resumes START from a persisted deadline.

After START, helper owns every potentially blocking operation on the faulted state filesystem: opens, validations, journal/checkpoint write/sync/rename/close, registry reads/lock/CAS/sync/close and intent updates. Avoid passing any of those descriptors to the runner. Prepare and transfer the bound listener before START; any filesystem binding/unlink and crash/log file setup is helper/worker-owned. During the protected interval runner uses only bounded nonblocking IPC, in-memory state, monotonic timing and the approved failure-exit primitive, still pending implementation. Diagnostics go to a nonblocking bounded channel; runner has no file-backed diagnostic thread or crash-file FD that can recreate the exit blocker. Later ControlServer registry work remains outside this startup-only guarantee and must be stated explicitly.

## Activation protocol

One closed START envelope, at most 16 KiB of metadata; helper constructs the two bounded storage buffers from checked registry bindings. One result frame, at most 4 KiB, containing operation identity, closed outcome/reason and startup reference. No arbitrary operation/path/argv interface and no payload stream. Partial, duplicate, foreign, oversized or reordered messages fail closed. Nonblocking sends cannot wait past the original deadline.

The helper validates matching unfenced Starting under the existing registry lock before admitting the private startup directory. It durably writes startup data, closes journal/checkpoint FDs, then performs the existing fresh Starting-to-Running CAS with exact launch identity, request binding and no fence. This does not bypass the registry lock or its shorter existing acquisition limit.

After a definitely successful CAS and before any success result, helper durably changes the operation phase to `activation_possible`. It checks deadline and channel state before starting that write and again after it returns. If cutoff C, cancellation or parent loss has occurred, no success result is sent. A phase write itself may finish late: activation_possible conservatively means a grant could have been produced, never that it was received.

Controller grants the runner permission to serve only if it receives the exact success result, independently proves helper exit with successful status, has not fenced/cancelled, and current time is before C. Runner independently rejects a grant at or after C. Receipt of the grant atomically disables its startup abort timer before serving/readiness. Old results never attach to another runner/generation. Readiness byte loss after activation retains current C1 semantics; absence of that byte is not evidence of nonactivation.

Worker loss before grant causes runner startup failure, but recovery must not infer that grant was absent from EOF or missing ACK. Activation_possible is deliberately conservative. Worker loss after actual activation must preserve normal runner survival and C1 reconnect behavior.

Successful settlement is separate from the protected runner transaction. After authenticated C1 serving observation of the same runner (or a positive activation ACK from that exact inherited channel), controller keeps its lease and starts one worker-owned reconciliation job to durably write resolved/activated. This job replaces the already-exited helper as the single slot operation; it never overlaps live helper I/O, runs off the controller event loop and owns its own anchors. No additional runner grant is sent. On timeout/cancellation/uncertain write the slot remains occupied and the job retained; close drains it. Only successful durable record write and actual reconciliation-job closure permit closing the last controller lease and freeing admission. A crash before this write is handled as activation_possible; a durable resolved/activated record is terminal for startup ownership and is never reopened merely because the runner later exits. That later Running lifetime belongs to ordinary runtime recovery, with its startup reference retained.

The earlier approval for the unmerged #616 implementation allowed a pre-registration-only abort exception; master has no corresponding exit call or policy allowance yet. A helper may now have written Running before the runner aborts. Amend the exception to “before activation/workload admission” with the same single call site and fixed status; architecture enforcement must land with the implementation. The owner approved this pre-activation scope with the helper contract; the old pre-registration-only exception alone is insufficient.

## Unresolved and recovery

Unresolved is an ownership/outcome classification, not success, termination evidence or permission to release. Enter it on timeout, caller cancellation with unfinished work, lost IPC, worker death, uncertain registry/intent write, identity mismatch, failed reap or incomplete scan. Do not require a new disk write to remember an I/O failure: every non-resolved intent is recovered as unresolved by default; live controller state may be stricter. Retry returns existing content-free retryable refusal while the operation is unsettled.

Never start a second helper against the slot while the prior helper may still run. A recovery controller may acquire exclusion only after the old controller/helper have released it, then confirm full identity absence. If native I/O is still live, continue refusing; do not detach, close foreign FDs or erase the marker. A recovery I/O job itself occupies the same slot, owns its descriptors and may become unresolved; it is not run in the timed runner. Reboot only changes the process-absence proof; it does not prove disk consistency or successful commit.

Under retained slot exclusion, reread and validate the current registry head under its lock and both operation/startup bindings. Decisions:

1. Starting still matches, no helper/runner/carrier remains: install/preserve its existing retirement fence, clean only proven-owned unreferenced startup files, and use existing Starting retirement semantics. Missing/corrupt/unreadable state refuses. No new generation before cleanup and durable resolution.
2. Running exactly matches this operation and phase is durably `bound` (never activation_possible): once helper/runner absence is proved, it cannot have received a grant under this protocol. Preserve all binding/reference fields and atomically replace it with the `StartupAborted` state below. Never roll it back to Starting or emit `no_runner_started`.
3. Running matches and phase is activation_possible or uncertain: no automatic abort/cleanup on the basis of missing ACK/readiness. If the same runner is live, use existing authenticated C1 observation/reconnection; no replayed activation grant. Confirmed successful serving can settle the startup slot without deleting referenced files. If runner is dead or observation remains unknown, retain Running plus unresolved ownership; full registered-runner retirement/recovery belongs to #197. This is an explicit availability limit, not completed recovery.
4. A different registry generation/reference, foreign root, malformed intent, or missing head after possible CAS: preserve files and refuse. Do not overwrite a newer head or infer a rollback.
5. A valid durable resolved record matching this root and operation is terminal for startup ownership. After exclusion and old job absence, release startup admission without requiring the old runner to remain alive. Do not delete its Running reference or infer runtime termination; an inconsistent head/record still refuses.
6. Failure after registry rename but before its directory sync: treat the result as uncertain. Recovery repeats the required durability operation under valid ownership before acknowledging its own transition; a readable head alone does not prove durability. Late callbacks cannot resolve or delete anything.

The approved `StartupAborted` head is a new closed registry variant. Fields: state=`startup_aborted`; the original Running deadline/gate/request/workload/submitter/runner/socket_path/startup fields preserved exactly; operation_nonce; reason=`startup_not_activated`; cleanup=`pending` or `complete`. It is an internal failed-startup outcome, not a TerminationReceipt or proof of general runtime termination. lookup returns the existing handle; status reports exited/failed only with confirmed runner absence represented by this transition; submit refuses nonretryably with `startup_aborted`; retire continues refusing `retirement_unavailable` until #197 supplies honest receipt behavior. No automatic same-attempt restart.

After durable StartupAborted(pending), clean only its exact startup directory, under current-head checks before each deletion, after actual helper/runner absence. This is the only new reference-release permission; Running references remain protected. Then persist StartupAborted(complete), resolve the intent as aborted and release the slot. A crash in any of these steps retains enough identity/reference to retry idempotently. complete retains the reference as historical provenance, not a claim that files still exist. Socket cleanup follows the same identity and absence rules. Do not fabricate a receipt to release capacity.

For uncertainty after activation_possible, #616 intentionally sacrifices availability: unresolved may block the root indefinitely until legitimate #197 recovery or separately designed administrative recovery. Operator marker deletion, lock replacement, timeout expiry and changing roots are not recovery procedures. This availability limitation is accepted for #616. If automatic recovery of that case is later required, move the corresponding #197 work into scope and re-estimate before implementation.

## Registration-only delivery and journal dependency

The independently useful registration-isolation stage uses closed `local-registration-operation/1`: exactly the operation fields above except `startup_directory` and `startup_reference`; result frames omit `startup_reference`. It moves existing registration I/O out of the protected runner and retains the complete lease, activation and unresolved ownership contract. Recovery compares Starting launch nonce and complete Running identity/request/workload/submitter binding. A late Running without proven serving remains unresolved: this stage adds neither StartupAborted nor journal-file deletion.

The dependent journal stage introduces `local-startup-operation/1`, the startup fields and StartupAborted reconciliation described above. An unresolved registration-only record must be reconciled by its matching recovery logic before upgrade; it is never relabelled or backfilled. An empty or resolved slot may admit the new version. Old Running heads follow the existing interim-format refusal policy; populated external deployments need a separate migration decision.

Every business-logic PR remains limited to 1,000 added plus deleted production lines. The earlier 950-line isolation estimate was withdrawn because it omitted serving-anchor reconstruction and diagnostic ownership. The next implementation plan must budget those actual consumers and every failure path; no unused protocol or disabled alternate startup path is an acceptable split. Diagnostic ownership may be a separate prerequisite only with a real runner consumer and a complete independently useful lifetime.

After a valid grant, ControlServer needs revalidated BoundSocket and Registry authority. Its later filesystem work is outside the startup-only five-second guarantee. The implementation plan must specify ownership reconstruction and the disposition of failure or blocking in that post-grant boundary before implementation activation; the contract does not authorize a false readiness or silently discard these obligations.

## Required evidence and remaining implementation limits

The implementation must preserve all of the following real-path checks on Linux and macOS:

- Inherited lease survival across worker death, exact lock/root identity, no release gap or replacement under unknown process identity; incomplete discovery preserves unresolved.
- Separate coordination-store and state-store failure, bounded bootstrap ownership, no false host-global capacity claim, and crash windows before reserved/bound/ARM/START.
- Malformed, duplicate, stale, partial and oversized frames; closed descriptor inheritance and no hidden channel peer; actual runner disappearance by D after failed ARM or blocked native open/write/sync/close/CAS.
- Native helper I/O remains owned until actual completion; late result cannot grant; runtime close drains real work. Record runner exit, helper exit, durable reconciliation and slot release separately.
- Late CAS, rename-before-sync, blocked activation_possible update, lost result/grant/ACK, worker death on either side of grant, cutoff rejection and terminal resolved behavior.
- Every startup journal/checkpoint crash barrier, native EDQUOT/ENOSPC/sync failure, reference-preserving transitions, exact StartupAborted cleanup and per-delete authority checks.
- C1 attach, workload delivery, takeover and lost-readiness behavior; content-free diagnostics with positive canaries, blocked/broken sinks and worker loss; exact process/task/FD/connection/buffer release or retained unresolved ownership.

The earlier native actual-controller run requested exit at 5.000948 seconds but observed runner exit at 6.513024 seconds. That is failed actual-exit evidence, not successful qualification. Separate-helper isolation, macOS native blocked-I/O barriers and the 250 ms exit reserve remain unverified. A pipe-only test or a successful collection workflow is not a native filesystem or actual-exit substitute. Job/fixture deadlines remain unchanged. Startup latency/RSS remain diagnostics except for the approved safety gates.
