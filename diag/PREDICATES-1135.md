### 1. Cycle schedule (identical on both hosts)

**Indices.** Cycles are numbered 0–849 and run in index order, each exactly once.

**Positive controls:** indices `50·k` for k = 1–16 (50, 100, …, 800).
- None falls in cycles 0–49. The macOS 15 acquisition stall at job start hit only cycles 0–18 in all three earlier runs.

**Arms.** The 834 other indices are ranked in index order from 0. Even ranks are arm O (observe only), odd ranks arm C (clearance).
- That gives **417 O and 417 C per host, and 834 C scheduled pooled**.
- Up to 74 C cycles pooled may fail to give a qualifying eject (rows H1–H4 in section 2) before the result becomes inconclusive.
- The cycle after a control is O for 8 controls and C for 8.

**Schedule file.** `diag/schedule-1135.csv` (columns `index` and `arm`, with values `O`, `C` or `control`) is generated from this rule. Its SHA-256 is posted here before the run.
- The driver takes each cycle's arm only from this file.
- The verdict script regenerates the file and rejects a run whose hash or per-cycle arm differs.

**Order inside every cycle.** Create, `acquire("enospc")`, a 4 MiB fsynced write, then `cleanup`. Inside `release_native`:

1. discover, unmount, and the post-unmount check (the **arm point**);
2. the arm's step;
3. the post-step `discover` comparison, in **both** arms;
4. one option-zero eject;
5. the existing post-eject absence check.

The arm steps:
- **Arm O:** one `Open` read, `pre_eject_open`, taken after the post-step `discover` and immediately before the helper starts.
- **Arm C:** the clearance step of the experiment plan's section 3, with the approved parameters. Sleeps are clamped to `min(20 ms, window end − now)`. After the post-step `discover` it takes one diagnostic `Open` read, `pre_helper_open`, immediately before the helper starts **(addition)**. Its true or false value decides nothing. An `unavailable` value counts under criterion 3, as for `pre_eject_open` in arm O.

One `/usr/bin/yes` per CPU runs for the whole job.

**Clean start (addition).** Before each cycle, the driver checks that no attachment of a fixture image from this job remains and records the leftover count as `0`, `1`, `2` or `3+`. Section 3 gives the stop rule.

### 2. Counting rules

Each cycle produces exactly one record. `helper_started` is taken from the persisted native request: yes when its helper token is set, otherwise no. Every record falls into exactly one row of this table:

| Row | Where the cycle ended | Counted as |
|---|---|---|
| P1 | before the arm point: acquisition failure, unmount failure or refusal, initial `attachment_identity`, attachment absent at cleanup | excluded in both arms; reported by count |
| A1 | arm point reached; the post-step `discover` differs, returns no attachment, or raises `attachment_identity` or `mount_identity` | criterion 3 failure; no helper start |
| A2 | arm point reached, `native_release_deadline` or `native_completion_unknown` before helper start | criterion 9 event; no helper start |
| A3 | arm point reached, an error before helper start whose code is not one of the fixture failure codes named in rows A1 and A2 | incomplete record: the job counts as incomplete |
| A4 | helper started, `native_result = not_requested`: the eject was never submitted, for example after `native_admission_deadline` or a failed disk lookup. The cause is recorded as `a4_cause`: `admission_deadline`, `lookup_failed` or `other`. | **(addition)** criterion 9 event in arm C only, whatever the cause; arm O A4 is reported with `a4_cause` and not counted; **not** a qualifying eject |
| H1 | helper started, `native_result = success`, the post-eject absence check and the rest of `cleanup` pass | qualifying eject, success |
| H2 | helper started, `native_result = refused` (any code, any dissenter) | qualifying eject, **refusal** |
| H3 | helper started, `native_release_deadline` or `native_completion_unknown` at the eject or at the post-eject check (including success followed by a post-eject deadline) | qualifying eject and criterion 9 event |
| H4 | helper started, success, then `attachment_still_present`; **(addition)** or a later `cleanup` failure (`mountpoint_identity`, `source_directory_identity` or the image unlink) | qualifying eject and criterion 3 failure |

The criteria are evaluated on these rows:

- **Qualifying C eject:** rows H1–H4 in arm C, never a control.
  - The count is intention-to-treat: every clearance result (`cleared`, `none`, `persisted`, `unavailable`, `skipped_fixture_holder`, `skipped_incomplete`, `skipped_budget`) stays in it.
  - A treatment that blocks the eject in arm C cannot hide: it lands in A1, A2 or A4, which criteria 3 and 9 count for arm C.
- **Residual numerator (criterion 8):** H2 in arm C.
- **Arm O:** the same rows give qualifying O ejects and O refusals, used for criteria 6, 7 and 9.
- **Criterion 3, both arms:** A1, H4, any `unavailable` read (including `pre_eject_open` and `pre_helper_open`), an unstable entry ID or an unbalanced handle counts.
  - **(addition)** The retained wording "while the attachment is present" could excuse an absent attachment. Here the post-step `discover` returning no attachment is A1 and counts as a failure too. This is stricter and cannot cause a false pass.
- **Criterion 4, cleared foreign hold:** a C cycle with a first read of `Open = true`, a complete observer result, `fixture_holder = no` and clearance `cleared`.
  - `fixture_holder = yes` means the observer found **any** same-user holder of a bound node, whatever its role.
- **Criterion 5:** per host, `persisted` C cycles divided by C cycles past the arm point.
- **Criterion 9:** pooled, A2 + A4 + H3 in arm C, compared with A2 + H3 in arm O. **(addition)** The retained criterion counts only `release_deadline` and `completion_unknown`. A4 is added only on the C side, as a C event, and never to O, so it can only tighten the comparison. A4 in arm O is reported with its `a4_cause` but not counted.
- **Controls:** excluded from every rate, numerator and denominator, including their cleanup. They count only under criterion 2, as mapped in section 3. One exception: an `unavailable` read, an unstable entry or an unbalanced handle in a control counts under criterion 3.
- **Pooling:** criteria 6, 7, 8 and 9 are pooled over both hosts; criteria 2–5 apply per host (see owner question 1).

**Order of evaluation, which fixes the outcome:**

1. **Fail, final even on partial data:**
   - 2 or more qualifying C refusals pooled;
   - a control classed as foreign, waited, or hold not seen (section 3);
   - any criterion 3 failure;
   - criterion 5 on a host, once that host has recorded all 850 cycles or already has at least 9 `persisted` C cycles. Criterion 5 is evaluated over that host's C cycles past the arm point that recorded a clearance result, even if an A3 record makes the job incomplete. 9 already exceed 2 % of any denominator up to 417, so more cycles cannot bring the rate back under 2 %.
   - L1–L5 failed locally.
2. **Inconclusive, incomplete evidence:**
   - a job that did not record all 850 indices;
   - an A3 record;
   - a stop under section 3 (`control_setup_failed`, a control child that does not exit, or 3 leftover attachments).
3. **Fail on pooled criteria, evaluated once both jobs are complete:**
   - criterion 7: at least 3 O refusals, none with `pre_eject_open = true`;
   - criterion 9: C events (A2 + A4 + H3 in arm C) above O events (A2 + H3 in arm O) + 2, subject to owner question 2.

   These pooled fails take precedence over the inconclusive items of step 4, but more data could still reverse them, so they wait for both jobs. Criterion 5 is per host and is final in step 1. A host whose `Open` stays true therefore fails through criterion 5, even though it also records no cleared hold, and even if the other host's job is incomplete.
4. **Inconclusive, insufficient data:**
   - fewer than 760 qualifying C ejects pooled;
   - fewer than 3 qualifying O refusals pooled;
   - the criterion 4 shortfall;
   - an inconclusive control (section 3), which leaves criterion 2 unestablished.
5. **Pass:** everything else holds.

### 3. Positive controls and cleanup of a finished cycle

**Control procedure:**

1. After the arm point, the driver starts a same-user child process. The child opens the raw whole-disk node read-only and writes one byte on a pipe once the open has succeeded.
   - The driver waits for that byte, an explicit condition with a 5 s deadline.
   - The child exits on EOF of its control pipe, so a driver crash releases the node.
   - The driver kills and reaps the child in `finally`.
   - If the byte does not arrive within the deadline, the cycle is recorded as `control_setup_failed` and the job stops (inconclusive).
2. The clearance step runs with arm C logic, through a hook injected only into the experiment controller's constructor for control cycles.
3. **Criterion 2:** clearance records `skipped_fixture_holder` and **no wait**. "No wait" is structural, not a wall-clock time: zero poll sleeps and zero `Open` reads after the observer returns. The record carries `poll_sleeps` (`0` or `1+`) and the observer's duration as a bucket.

   The control's outcomes are mapped as follows:

   | Control outcome | Result |
   |---|---|
   | `skipped_fixture_holder` with `poll_sleeps = 0` | criterion 2 holds |
   | `none`, `cleared` or `persisted`; a complete observer with `fixture_holder = no`; or `poll_sleeps = 1+` | **classed as foreign, waited, or hold not seen: final fail** |
   | `skipped_incomplete` or `skipped_budget` | inconclusive control: recorded, and **the job continues**. Criterion 2 is then unestablished (step 4 of the order of evaluation), but later fail evidence is still collected. |
   | `unavailable`, an unstable entry or an unbalanced handle | criterion 3 failure |
4. **Informative only, not criteria (addition):** `Open = true` at the first read, the eject refused with 49168, and dissenter class `other`.
5. The driver closes the child's pipe and waits for its exit, with a 5 s deadline. If the deadline expires, the job stops (inconclusive).

A control stops the job only in two cases: `control_setup_failed` (step 1) or a child that does not exit (step 5). Every other control outcome is recorded, and the job continues.

**Cleanup of a finished cycle (addition, co-author choice 1).** This applies to a control, or to any cycle whose attachment remains after its record was written, whatever its row.
- After the cycle's controller process has exited, the driver runs the fixture's existing recovery in a new process, one time.
- The recovery controller runs master behaviour, with no arm step and no `Open` reads.
- This cleanup never changes the cycle's recorded outcome and is excluded from every count. Its result goes into `cycle_cleanup`: `none_needed`, `released`, `refused` or `other`.
- If the attachment still remains, the cycle continues to count as recorded, and the next cycles run with the leftover recorded.
- The job stops (inconclusive) only when 3 leftover fixture attachments are present at a cycle start.
- Without such a rule, a single refused control cleanup would stop the run. With p0 = 0.86 %, that would happen in 24 % of runs.

### 4. Per-cycle record (categorical only)

The allowed values are fixed in `diag/PREDICATES-1135.md`, and the writer rejects anything else. No PID, path, BSD name, registry entry ID, volume name or free text is recorded. The fields of the experiment plan's section 5, plus:

- `row` (P1, A1–A4, H1–H4), `helper_started` and, for A4, `a4_cause` (`admission_deadline`, `lookup_failed`, `other`);
- `poll_sleeps` (`0` or `1+`);
- `max_poll_gap` (<40 ms, 40–100 ms, 0.1–0.5 s, ≥0.5 s, or `none` when the loop made fewer than two reads after the observer). This is the largest interval between consecutive clearance-loop `Open` reads taken after the observer returns. The observer scan itself is recorded separately as `observer_duration`.
- `open_reads` (1, 2–10, 11–100, 101+): the clearance step's `Open` reads, without `pre_helper_open`;
- `observer_duration`, `discover_duration` and `time_to_clearance_start` (buckets);
- `last_read_to_helper_start` (<0.5 s, 0.5–1 s, 1–2 s, 2–5 s, ≥5 s):
  - in arm C, from the last `Open` read of the clearance step, not `pre_helper_open`;
  - in arm O, from `pre_eject_open`;
  - in both arms, it ends when the helper process is spawned. Helper start-up until `DADiskEject` is the remaining exposure, which this field does not cover.
- arm C `pre_helper_open` (true, false or unavailable);
- `cycle_cleanup`, `leftover_at_start` (`0`, `1`, `2`, `3+`), and the runner's macOS product version and runner image version.

Hold duration runs from the first true read to the first false read. The hold began at an unknown time before the first true read, so this measures only the part of the hold remaining after that read. It overestimates that remainder by at most one interval:
- if the hold cleared during the observer scan: `observer_duration` plus one poll interval;
- otherwise: `max_poll_gap`.

It is diagnostic only.

### 6. Known risks to the outcome

- **False pass.** With p0 taken as exact, P(at most 1 refusal in 760 ejects with no real improvement) is 1.1 %.
  - Allowing for the uncertainty of p0 from 10 events, it is about 3.2 %.
  - At the unprivileged-only baseline of 2/380 (0.53 %), it is 9.2 %.
  - The concurrent arm O is reported so this can be judged on the run itself.
- **Inconclusive from criterion 4.** If foreign holds at the first C read are about as frequent as refusals, about 3.6 per host are expected. Then P(at least 5 on each host) ≈ 9 %, while P(at least 5 pooled) ≈ 84 %. See owner question 1.
- **Slow-runner state.** In the slow macOS 26 state seen once (O arm alone had 9 release deadlines in 200 cycles), the extra post-step `discover` in arm C can push criterion 9 over its limit regardless of the signal. See owner question 2.
- **Residual race.** A hold that starts between the last clear read and the eject still refuses it. `last_read_to_helper_start` and `pre_helper_open` measure this gap; the order fixed by the owner (recheck after the wait) is unchanged.

2. **Additions.** The following are adopted. None changes an approved parameter or relaxes a retained predicate.

   - counting a `cleanup` failure after a successful eject (row H4) as a criterion 3 failure;

   Three of these extend retained criteria, all in the stricter direction:
   - the absent attachment and the H4 extension add failure cases to criterion 3, which is one-sided;
   - A4 is added to criterion 9 on the C side only, never to O, so it can only raise the C count against an unchanged O count.

   Each can only turn a pass into a fail or an inconclusive result, never the reverse.
3. **Order of evaluation.** The five-step order in section 2 is adopted. Its consequences:
   - **Final on partial data:** these are a fail even if a job stops early:
     - 2 qualifying C refusals;
     - a control classed as foreign, waited, or hold not seen;
     - any criterion 3 failure;
     - criterion 5 on a host that has recorded all 850 cycles or at least 9 `persisted` C cycles.

     Through criterion 5 in step 1, a host whose `Open` stays true is a fail, not an inconclusive result, even if the other host's job is incomplete.
   - **Incomplete evidence:** an incomplete job, an A3 record or a stop under section 3 is inconclusive, and the pooled criteria 7 and 9 are then not evaluated. An inconclusive control does not stop the job; it only prevents a pass.
   - **Fails before insufficient data:** on complete jobs, the pooled fails of criteria 7 and 9 come before the inconclusive items "fewer than 760", "fewer than 3 O refusals" and the criterion 4 shortfall.

## Part 3. Retained predicates of the experiment plan (comment 6767547337)

### 3. Clearance parameters under test (inside the unchanged 30 s release deadline)

`cleanup()` sets the release deadline to `T0 + 30 s`. The helper's request deadline is `T0 + 25 s` and its own cap stays 25 s after admission. Nothing here changes those values.

- **Window.** Clearance may start only before `T0 + 13 s`; otherwise it is skipped (`skipped_budget`) and the eject goes ahead at once. It ends at the first `Open = false` read, at clearance start + 5 s, or at `T0 + 13 s`, whichever comes first.
- **Eject reserve.** This leaves at least 12 s before the helper's request deadline for the fresh `discover` and the single eject. The longest eject wait measured on hosted runners was 8.23 s (macOS 26, run 42493548318), and 10.5 s locally under load.
- **Poll interval.** 20 ms with the injected clock, so at most 250 reads in a 5 s window. Each read is a registry property read, not a device open.
- **Observer.** The existing same-user descriptor observer runs once, when `Open` is first seen true, with its time limit cut to the remaining clearance window. A fixture or kora holder, an incomplete scan or an unavailable scan ends clearance without waiting.
- **No clearance from missing evidence.** `unavailable`, a changed entry, `persisted` and `skipped_*` are not clearance. In all of them the single eject goes ahead exactly as today.
- **Eject unchanged.** One option-zero `DADiskEject`, the same helper, activation and post-eject absence check. A refusal stays final.

The owner may change the 5 s window, the 13 s bound or the 20 ms interval before the run; the predicates then use the changed values.

### 7. Success criteria, fixed in advance

**Pass. Every item must hold; then the implementation goes ahead under the plan comment's section 3 with the parameters above:**

1. **Local phase:** L1–L5 pass.
2. **Positive control:** all 32 hosted control cycles record `skipped_fixture_holder` with no wait. A fixture holder must never be classed as foreign.
3. **Availability:** no arm C or arm O cycle records `unavailable`, an unstable entry, unbalanced handles or a failed fresh check while the attachment is present.
4. **Foreign holds seen and cleared:** at least 5 arm C cycles per host with `Open` true, a complete observer, no fixture holder and `cleared`.
5. **Not stuck:** `persisted` in at most 2 % of arm C cycles on each host.
6. **Exposure in the run (validity):** at least 3 arm O refusals pooled across both hosts.
7. **Signal not blind:** at least one arm O refusal had `pre_eject_open = true`.
8. **Residual rate (the threshold the owner is asked to agree):** **at most 1 refusal pooled in at least 760 arm C ejects, that is at most 0.13 %.**
   - At the baseline p0 = 0.86 %, 760 ejects are expected to give about 6.5 refusals, and the chance of seeing at most 1 without any improvement is about 1 %.
   - If the true residual rate is 0.1 %, the run passes with about 82 % probability; at 0.2 %, with about 55 %.
   - Formula, if the recomputed p0 differs: the largest k with P(Poisson(n_C · p0) ≤ k) ≤ 0.01, where n_C is the number of arm C ejects.
   - The owner may name a different threshold instead.
9. **Release deadlines not worse:** arm C `release_deadline` plus `completion_unknown` is at most the arm O count + 2, pooled.

**Fail. Any of these items sends the work to the Decision B fallback** (section 6 of the plan comment: no fixture change for the refusal, the owner closes or defers #1135, #1159 is closed unmerged, and the research record lands):

- any L1–L5 failure, in particular `Open` not false at rest (the run then never starts);
- a positive control classed as foreign;
- any `unavailable`, unstable entry, unbalanced handle or failed fresh check;
- `persisted` above 2 % of arm C cycles on either host;
- at least 3 arm O refusals, none of them with `pre_eject_open = true`, which means the hold starts after the last read and clearance cannot help;
- 2 or more arm C refusals pooled;
- arm C deadlines above the arm O count + 2.

**Inconclusive. No decision and no automatic second run;** the owner decides between a new run, which needs a new co-author approval, and the fallback:

- fewer than 3 arm O refusals pooled (about 3 % likely at the baseline rate);
- fewer than 5 cleared foreign holds on a host;
- fewer than 760 arm C ejects pooled, for example after acquisition stalls;
- a job that ends early for runner reasons.

## Part 4. Implementation notes

Every point here was fixed before the local phase ran. None changes a parameter or a predicate above.

### Where the code lives

- **Controller step.** The controller step is a subclass, `ExperimentController` in `diag/media_open_controller.py`, not an edit of `tests/plugins/storage/pressure_controller.py`.
  - Its `release_native` repeats master's sequence: discover, compare, unmount, post-unmount check.
  - It then adds, in order: the arm step, the post-step `discover` comparison in both arms, the arm O `pre_eject_open` or arm C `pre_helper_open` read, one option-zero eject through master's `native_phase`, and master's post-eject absence check.
  - The reader, the arm, the trace, the arm-point hook and the clock come in through the constructor.
- **Cycle process.** Every cycle runs its controller in its own process (`diag/media_open_cycle.py`). The driver (`diag/media_open_cycles.py`) therefore runs the cleanup of a finished cycle only after that controller process has exited. The cleanup is master's `pressure_controller --recover`.

### Clearance step

- **Window.** `T0` is the release deadline set by master's `cleanup()` minus 30 s. The window ends at the earliest of clearance start + 5 s and `T0 + 13 s`, or at the first `Open = false` read.
- **Poll.** Sleeps are `min(20 ms, window end − now)`, using `time.monotonic` and `time.sleep` through an injected timing object.
- **Observer.** It runs once, when the first read is true, with its time limit set to the remaining window.
  - It uses master's `Scan` and binding checks and returns a structured result.
  - The result is **complete** when all of these hold: the binding is unchanged; there is no query failure; all listed processes were visited; nothing was truncated; the entity list was not truncated.
  - **Fixture holder = yes** means any same-user holder of a bound node, whatever its role.
- **Reader.** It uses `IOServiceGetMatchingServices` with `IOBSDNameMatching` on the whole-disk BSD name.
  - Lookup requires exactly one match that conforms to `IOMedia`, `Whole = true` and a nonzero registry entry ID.
  - Every read first checks that the held entry is still attached to the IOService plane (`IORegistryEntryInPlane`), then rechecks the entry ID and `Whole`, then reads `Open`. The plane check was added after the first local reader check showed that a held handle keeps its entry ID and `Whole = true` and reads `Open = false` after the media terminates. Without it, an absent media would not read `unavailable`.
  - The iterator, every service object, every property value and every key string are counted when acquired and when released. The matching dictionary consumed by `IOServiceGetMatchingServices` is not counted.
  - The session is closed before the eject helper is spawned.

### Records

- **`open_reads`.** It has an added value, `0`, for a cycle whose clearance was `skipped_budget`, which makes no read.
- **Duplicate start fields.** `clearance_start_bucket` and `time_to_clearance_start` carry the same 2.5 s buckets. One field name comes from each of the two plan texts.
- **`last_read_to_helper_start`.** It runs from the last clearance-step read (arm C) or from `pre_eject_open` (arm O) until the controller calls the eject `native_phase`, which spawns the helper.
- **`a4_cause`.** It is derived from the helper's saved standard error:
  - `admission_deadline` for `native_admission_deadline`;
  - `lookup_failed` for a missing session, target or disk;
  - `other` otherwise.
- **H4.** It covers a successful eject followed by any other fixture failure, including an `OSError` from master's cleanup (recorded as `cleanup_os_error`). This is the conservative reading of "a later `cleanup` failure".
- **H3 fallback.** A started eject with no published outcome is H3 whatever the failure code, including codes other than `native_release_deadline` and `native_completion_unknown`: it counts as a qualifying eject and a criterion 9 event.
- **`pre_helper_open`.** Arm C takes it after the post-step `discover` in every case, including after `skipped_budget`, through a new session.
- **Entry stability.** `entry_stable` is `no` when any session of the cycle saw an unavailable read or a changed entry, or when the cycle's sessions found more than one registry entry ID.
- **Criterion 3 and A3.** Only a driver-synthesised record (`driver_record_missing`) is left out of criterion 3. Any other A3 record with an unavailable read, an unstable entry or an unbalanced handle counts.
- **Control without arm point.** A control that ends before the arm point (clearance `not_run`) is an inconclusive control.
- **Driver error.** A cycle process that writes no record (crash or its 600 s driver timeout) is recorded as A3 with failure `driver_record_missing`.
- **Allowed values.** All values are checked against `diag/media_open_records.py` when written and again when read.

### Local phase

- **Order.** It runs the first 10 L1 (`rest`) cycles, then 40 more `rest` cycles, then 50 `holder` cycles.
- **Gate.** The driver stops after the first 10 if any of them fails the L1 probe or reports an unbalanced handle or an unstable entry.
- **L6 not run.** L6 was not approved. L3–L5 are therefore evaluated over the 100 cycles that run instead of 150.
- **Holder cycles.**
  - A `holder` cycle uses the positive-control procedure and arm C logic.
  - After the refused eject and the child's exit, it reads `Open` until false, for at most 5 s (`after_holder_open`).
  - Its image is released by the cleanup of a finished cycle.
- **L3–L5 reading.** They are evaluated over cycles that reached the arm point. A shortfall from 100 such cycles makes them inconclusive, and any failing cycle makes them fail. For L4, "the existing `resources_closed` evidence holds" means the cycle's resources were closed by the cycle itself or by the cleanup of the finished cycle.
- **L4.** It also requires `diag/media_open_reader_check.py` to pass. That script checks that:
  - the reader finds no media for an absent disk and for a slice name, both through the name guard and directly through IOKit, where a slice fails the `Whole` check;
  - the reader reads true on a mounted owned image and `unavailable` after master's cleanup detached it;
  - every acquired handle is released.

### Owner questions and hosted verdict

- **Retained forms.** No owner answer to questions 1 and 2 was posted before the freeze, so the verdict uses the retained forms:
  - criterion 4: at least 5 cleared foreign holds **per host**;
  - criterion 9: C events (A2 + A4 + H3) above O events (A2 + H3) + 2, with no slow-state exception.
- **Where the verdict runs.** The hosted verdict needs both hosts, so it runs in a separate workflow job after both cycle jobs, and again locally on the downloaded artifacts.
- **Local outcome input.** The verdict job reads `diag/local-outcome.txt`. It holds the `outcome` of the local verdict (`pass`, `fail` or `inconclusive`) and is committed at the freeze, together with the local result posted on #1135. A local outcome other than `pass` is a step 1 fail.
- **Run checks.** The verdict also checks that the schedule file equals the fixed rule, that the two hosts are 15 and 26, and that every `run.json` value is inside the record schema.
