- Status: accepted, 2026-10-15
- Deciders: project owner, after the design review of 2026-10-15 (first cycle, findings S7 and A25 in [review-2026-10-15.md](../../knowledge/reviews/review-2026-10-15.md))
- Absorbs: requirements decision 18 (stack part; its "harness CLI + JSONL" part was replaced by requirements decision 19, see ADR-0004), the stack table in `knowledge/architecture/detailed.md` section 7
- Related: [0001-own-control-plane.md](0001-own-control-plane.md), [0002-ai-first-api-and-thin-clients.md](0002-ai-first-api-and-thin-clients.md), [0003-scheduler-and-workers-over-http.md](0003-scheduler-and-workers-over-http.md), [0004-harness-adapters-over-vendor-sdks.md](0004-harness-adapters-over-vendor-sdks.md), [0011-namespaces-and-personal-tokens.md](0011-namespaces-and-personal-tokens.md)

## Context

The architecture fixes a control plane, outbound-only workers per runtime, protocol implementations loaded by entry points, and four thin clients of the API. The stack had to serve all of these from one repository and keep standalone mode (one process on SQLite) identical in behaviour to the platform deployment on PostgreSQL (NFR-0.1). The design review of 2026-10-15 refined two rows: one shared client instead of three generated ones (finding S7), and the build backend and CEL binding (finding A25).

## Decision

Rows marked *proposed* are defaults the owner has not objected to and can change without affecting the architecture.

- **Python 3.11+ with `asyncio` throughout** (NFR-11.1).
- **`uv` + `hatchling`, one distribution `kora`** with extras (`kora[postgres]`, `kora[docker]`, `kora[otel]`), `src/` layout, monorepo with the frontend in `web/`. `hatchling` is kept over `uv_build` because the embedded web build needs a custom build hook.
- **FastAPI + Pydantic v2** for the HTTP API. Pydantic models are the single definition of the intermediate representation (IR) and publish `ir.schema.json`; OpenAPI feeds the web client generator and the parity coverage test.
- **SQLAlchemy 2.0 + Alembic** over **PostgreSQL via `asyncpg`** and **SQLite via `aiosqlite`** for standalone. Row claims use `SELECT … FOR UPDATE SKIP LOCKED` on PostgreSQL and a single-writer process on SQLite; an external queue was rejected because run state must live only in the database (NFR-1.2).
- **One hand-written `httpx` client** sharing the Pydantic models with the API, used by the CLI, the MCP tools and the worker, contract-tested against OpenAPI.
- **Typer CLI** over that client; the **official `mcp` Python SDK** for the two curated MCP servers (ADR-0002).
- **CEL through the Rust-backed `common-expression-language` binding**, with kora's own schema-driven checker for the `inputs.*` environment and the CEL conformance suite in CI; `cel-python` has no static checking.
- **Jinja2 `SandboxedEnvironment`** for prompt templates (DD-11).
- **`ruamel.yaml`** for IR read and write, because it round-trips comments (*proposed*).
- **`aiodocker`** for the Docker runtime through the Docker Engine API, one container per attempt (*proposed*; the `docker` CLI is simpler but harder to test).
- **OpenTelemetry Python SDK with the OTLP exporter** as the only MVP exporter, loaded in the control plane only and replaying the append-only event table with the GenAI semantic conventions; `prometheus-client` metrics and `structlog` JSON logs (*proposed*).
- **`pytest` + `pytest-asyncio`, `hypothesis`** for IR and compiler properties, **`testcontainers`** for PostgreSQL; conformance suites as pytest plugins (*proposed*).
- **React + TypeScript + Vite, TanStack Query, shadcn/ui** for `kora web`, built from a locked pnpm lockfile, with the TypeScript client generated by **`@hey-api/openapi-ts`**; a production frontend from the start, approvals views in the MVP.

## Alternatives considered

Per row, as recorded in the architecture: Poetry, `uv_build`; Litestar, Django REST; raw SQL with `psycopg` 3, SQLModel; a generated `openapi-python-client`; Click, argparse; `cel-python`; PyYAML; server-rendered Jinja2 + HTMX, Next.js, SvelteKit; vendor observability SDKs only; CLI JSONL parsing for harnesses (replaced, ADR-0004).

## Consequences

The stack must preserve the boundaries of the architecture: the API is the only writer of operations and the clients hold no logic; agent sessions never reach kora and the policy decision point runs in the session runner; the scheduler never imports user Python, only IR rows; workers execute one attempt and report through the API under their lease epoch; protocol implementations are loaded by entry points, never imported by name; nothing may exist only in standalone mode; the session runner inside the runtime is the only enforcer of session limits.

Practical effects: a pnpm toolchain is needed to build the package; CEL depends on a compiled binding; Docker-dependent tests run on the Linux CI job only; protocol implementations are written against async interfaces.
